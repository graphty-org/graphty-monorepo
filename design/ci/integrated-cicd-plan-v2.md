# graphty CI/CD: the integrated plan, version 2 (as of 2026-10-24)

Status: proposed, 2026-10-24, revised after an adversarial review the same day (section 8). Issue
#3316. It joins every CI/CD and testing change proposed or built between 2026-10-13 and 2026-10-24
into one process. It supersedes most of `design/ci/integrated-cicd-plan.md` (version 1, written
before full testing moved to CI); that file marks which of its sections still stand. It builds on
`design/ci/ci-full-testing.md` (the light local gate with the full suite in CI, built and not yet
switched on) and keeps the parts of `design/ci/fast-pipeline.md` and `design/ci/golden-local.md` it
does not replace.

Words used throughout:

- **golden** is the local integration branch every change lands in (`tools/land.mjs`), pushed to
  `golden` on GitHub.
- **the gate** is `tools/prepush.sh`, run by `tools/push-queue.sh` for every push and landing.
- **the light gate** is the gate with its test stage and screenshot capture switched off
  (`PREPUSH_LIGHT=1`): checks, build, lint, SonarQube and the NVIDIA GPU tests only.
- **verification** is `tools/verify.mjs`: it tests golden's newest commit after landings and moves
  the ref `golden-verified` when it passes, then bisects a failure to the landing that caused it.
- **the cut** is the verified golden commit chosen for master (`golden-cut`), opened as a pull
  request whose screenshots the owner approves.
- **the release train** is `.github/workflows/release.yml`: full suite, paid T4 GPU, Hosts, macOS
  autosave, security audit and LLM tests on master's tip, then version, push the tags, publish to npm.
- **a retry-pass** is a test that failed and then passed when `tools/test-quarantine.mjs` re-ran its
  file inside the same CI job.
- **R** is the owner's time to review and Finish a cut's screenshots after being asked.

Figures marked "measured" come from `tmp/push-log.jsonl` (main checkout), `tmp/golden/verify.json`,
the gate logs, GitHub run times or git history. Figures marked "estimate" are not measured yet; each
has a check in section 6 that measures it.

## Short answers

- **The end state is short.** Land with a light local gate (about 10 to 15 minutes, estimate). The
  full suite runs once per batch in GitHub Actions on golden's tip (48 to 64 minutes measured on the
  full-build path that verification uses; 31 minutes once its 20-minute Build is brought down to the
  pull-request path's 6, which rollout step 2 does). The newest verified commit with clean captures
  is cut, the owner approves its screenshots, and its CI runs once more on the merge with master. The
  release train runs the GPU and platform lanes on what reached master. Failures found after landing
  are bisected in CI and the culprit is reverted.
- **Much of the machinery built this week becomes unneeded, and so does the local verification
  backend.** Once no test runs in the local gate: test selection in the gate, deferring downstream
  tests, per-shard pass reuse, the "known failing on golden" excuse, the test ledger's SQLite index,
  mid-run switching of verification, nx 24's task-level affected, the nightly flake hunt, the gate's
  screenshot capture, the gate lanes of the test slots and local verification all lose their
  purpose. Section 2 drops or shrinks 24 of 66 mechanisms. What must be added before the switch is
  small but not optional: a flaky-test writer that reads CI results, the "newly intermittent is a
  regression" rule at verification and release, a log budget, a capture check in verification, and
  the Build fix.
- **Will it release faster?** Yes. Nothing has reached npm since 2026-10-21 04:46 UTC, and golden is
  427 commits ahead of master. For a typical change the end state takes about 2.7 to 3.9 hours plus
  1.5 R from desktop to master, and about 4.1 to 5.4 hours plus 1.5 R to npm, falling to about 3.1
  to 4.1 hours plus 1.5 R after the Build fix and release reuse (section 4). R counts one and a half
  times because the cut is frozen while the owner reviews it: on average a change waits for half of
  the current cut's cycle as well as its own review.
- **Under six hours?** To master: yes, when the owner reviews each cut within about 1.5 hours of
  being asked. To npm: yes after rollout step 6, when the owner reviews within about an hour.
  Overnight it will not happen, because only the owner approves screenshots. On a day with a real
  failure in a batch, the innocent landings of that batch wait out a broken golden of about 2.5 to 4
  hours and miss six hours. A tier-3-sized branch cannot land in six hours under any design here;
  only landing it in pieces does.
- **Tier 3's root cause was tests whose pass depends on CPU timing, run under heavy load that the
  pipeline itself made on one machine.** 31 test-step failures hit 23 different files, most of them
  once, while 8 to 9 gates ran at once. The React act() warning flood roughly doubled that
  sensitivity, but it was an amplifier, not the largest single cause: golden passed every graphty
  shard twice with the flood present, and the fix's own landings failed on other things (a real
  product race, a click-stability flake, a docs build, then repackaging). The other big cause was a
  17-day branch that was never gated or merged with golden (about 11 hours). Section 3 ranks them.
- **Two things this plan corrects in the earlier analysis.** "Six times slower" was mostly five
  times more real-element test files, not slower code. The release block (#3318) did not come with
  tier 3; it came from `feat/style-specimens`, landed on golden on 2026-10-21.

Notes on the table:

- Step 1 runs no test. That is the owner's order of 2026-10-23: "replace our local full-test gate
  with a lighter test that is lint, build, sonarqube, and gpu and put our full testing in CI". It
  supersedes the earlier stage-1 target, "fast, smallest tests ... that only test the exact
  changes". Section 1.3 says why no test lane is added back before landing.
- Steps 3 and 5 both run the full suite on nearly the same tree. That is deliberate. A run on a
  public repository's standard runners costs nothing, and the wall time of step 5 is set by the
  screenshot capture (about 20 minutes for the graph-io fidelity Storybook), not by the tests. Step
  5 is our version of the merge-queue re-run ("re-runs every check against main with the change
  applied"), and it is the only run that applies the owner's screenshot gate.
- Step 6 no longer re-runs the Linux suite on a tree step 5 already tested. It keeps the T4 on every
  release (the owner, 2026-10-13: "no, I'd rather run the T4 to be sure our release works"). Reuse
  saves about 29 jobs and a third chance for a flaky run, but only about 10 minutes of wall time,
  because the T4 lane is the critical path.

### 1.2 Where it follows Anthropic's process, and where it does not

Anthropic publishes two processes. Its large monorepo drops the merge queue for "post-merge and
pre-deploy automated testing" with automated bisect-and-revert, and lets main be briefly broken. Its
Claude Code repositories check before the pull request, require CI and re-run every check in a merge
queue against main. Our design uses the monorepo shape up to master and the Claude Code shape at
master and at release.

| Anthropic                                                                               | Ours                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Agent tests and reviews its own work before the pull request exists                     | Step 0: `test:changed`, plus the fresh-context review CLAUDE.md requires                                                                                                                                                 |
| Pull request runs selected tests ("listener" and "selector")                            | Different: the landing runs no tests (owner's order). Selection would add a CI round trip and API calls to each landing for a signal verification gives within the hour                                                  |
| No global merge lock; post-merge testing                                                | A lock of seconds (one machine, a few dozen landings a day); verification after landing                                                                                                                                  |
| Automated bisect and revert                                                             | Steps 3b and 6b                                                                                                                                                                                                          |
| Main may be broken briefly                                                              | golden may be broken for a few hours; master may not be broken by anything CI can see                                                                                                                                    |
| Merge queue re-runs every check against main                                            | Step 5, the cut's CI on the merge with master                                                                                                                                                                            |
| Pre-deploy testing, flags, employees first, latest then stable channels, canaries, soak | Step 6. No flags on graphty-element options (they are published API) and no staged npm channel (a published version cannot be pulled back). beta.graphty.app is the only staged exposure, and it is optional (section 2) |

"Eventually consistent" is the owner's phrase and appears in neither Anthropic post. The nearest
statement is "post-merge and pre-deploy automated testing" that repairs main before deploy. Section 5
defines what it means here.

### 1.3 Why no test lane before landing

There are three ways to put tests back before a change reaches golden:

- selected tests locally, the minimal-tests design;
- selected tests in CI per landing;
- history-based selection, issue #3324.

None is worth it now:

- **Running tests locally is what failed.** The machine ran up to 8 or 9 gates at once. Of tier 3's
  31 test-step failures (23 files), 7 were in the 3 files that also failed in CI (Groups,
  KeyboardStopsEscape, BulkPilot) and 2 were a real product race (GraphPlace, fixed by 7d7efcecb9).
  The other 22 failures, in 20 files, never appeared in CI; each failed once or twice, with passes on
  the same base in between. Up to 5 of those were Node-project tests in other branches' land checks
  that may have been those branches' own defects; they were not re-checked. Selection still picked
  376 of graphty-element's 416 browser tests for one source change.
- **A CI lane per landing means a push, a run and a poll for every landing.** That is about 20 to
  40 more runs a day against the shared 60-job and 5,000-request limits. It would catch a failure
  about half an hour sooner than verification does.
- **A culprit that slips through costs one bisect.** By the classification above, about 9 of tier
  3's 31 test failures (7 that reproduced in CI, 2 for the product race), and at most 5 more, would
  have reached golden under the light gate. Verification plus the CI bisect finds such a culprit in
  about 2.5 to 4 hours today and about 1.5 to 2.5 hours after the Build fix (estimate). The light
  gate still catches the 20 of 52 failures that were not tests.

Revisit this if section 6's check shows more than one golden revert a day for two weeks running.
The first thing to add then is history-based selection in CI, using the result records kept for
quarantine.

### 3.3 Where this analysis could be wrong

- **The split between timing-dependent tests and machine load is a judgment.** The two are one
  mechanism seen from two sides: a test with little margin, and a machine that takes the margin
  away. The evidence for load is the pattern (23 files, most failing once, passes on the same base
  in between, 8 to 9 gates at once); the evidence for the tests is that CI's runners also failed
  College football and BulkPilot. What would change the conclusion: CI verification failing more
  than twice a week on tests that never failed locally.
- **The act() flood's weight rests on one reproduction.** Starving vitest's Node process reproduced
  the gate's failure signatures: 19 of 41 tests failed with the warnings, 10 of 41 without them. Its
  fix also arrived with test splits, so part of the measured speed-up (graphty-2 from 660 to 492 s)
  may belong to the splits.
- **Moving tests to CI removes the load, not the defects.** A test that does 14 seconds of work
  under a 15-second limit fails anywhere. #3284 stops it failing by raising the limit, so the
  duration report (row 42) is what keeps it from growing into a hang unseen. That is why #3284, the
  log budget and the listener come before the switch (rollout step 2), and why the switch alone is
  not the fix.
- **The light gate trades local failures for golden reverts.** By section 1.3's classification,
  about 9 of tier 3's 31 test failures, and at most 5 more, were defects that would have reached
  golden; the other 22 were local load. Tier 3 was one huge branch; a stream of small landings may
  break golden more or less often. If golden needs more than one revert a day, section 1.3 says what
  to add.
- **The counterfactual hours overlap**, especially the test, load and flood rows and the cut re-gate
  on 10-22. Read them as a ranking, not a sum.
- **The verification figures are two runs of the full-build path** (48 projected and 64). Why its
  Build takes 19 to 21 minutes against 6 on the pull-request path, for the same `nx run-many -t
build --parallel=3`, is not known yet; the release train's full Build took 4 minutes before tier
  3 (39540908824). Rollout step 2 finds and fixes it, and step 3 measures 10 runs.

How a failing commit is removed before release:

1. **Verification fails, or passes only on a retry.** The in-job retry has already re-run each
   failed file once. A file that failed and then passed is checked against the result records: if
   the same test failed or passed only on a retry before this batch (at or before
   `golden-verified`), it is an old flake, its issue gets a comment and the run counts as green. If
   not, it is newly intermittent and treated as a regression, like a failure that stayed red.
2. **Find the culprit.** When the failing test's file was changed by exactly one landing of the
   batch, that landing is the culprit. Otherwise `verify.mjs` bisects the `land:` merges (first
   parent) since `golden-verified` in CI, one point at a time, each point building its commit and
   running only the failed shards. A newly intermittent test is run 5 times at a point, and the point
   is bad when it fails at least once (the built rule). The culprit is the first merge that fails,
   provided its parent passes.
3. **Remove.** The pipeline round runs `land.mjs revert <branch>` and opens the fix work on the
   branch's issue. Verification of the new tip follows. Landings never stop for a red golden,
   because the light gate does not run tests.
4. **At release**, the same rule runs with the last release tag as the baseline: a retry-pass with
   no earlier failure since that tag holds the release. The culprit is found over the release batch's
   `land:` merges (T4 probes on the local NVIDIA card, Hosts and macOS probes by dispatching their
   workflows). Removal: point `golden-cut` back at master's tip (a new `cut` option, row 17), branch
   the revert from it, and `cut-fix` it, so master receives only the revert and the same branch lands
   on golden. Ship it; the master push restarts the held train. Then re-cut the newer batch from
   golden. Until composed approvals (#3264) land, a revert that changes `visual-baselines/` needs a
   new Finish, and so does the re-cut batch.
5. **GPU tests are never quarantined or excused**, in verification or at release.

## 7. Risks and corners

| Risk                                                        | What happens                                                                          | Handling                                                                                                                                                                                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GitHub Actions outage or a push that creates no run         | No verification, no ship, no release                                                  | `verify.mjs` records `noRun`, re-pushes once by deleting and recreating the ref, then alarms. Landings continue. No local fallback: it could not ship anything.                                                          |
| The 60-job limit, shared with the release train             | A full run peaks at 31 jobs; verification plus a cut plus a release ask for about 91  | No yield: GitHub queues the jobs over 60, which costs minutes, against an hour or more of waiting for a whole cut CI or train. A train that reuses the cut run needs only its 5 lanes. Measure the queue time in step 3. |
| GitHub API budget (5,000 an hour, shared)                   | Polling every verification and bisect                                                 | Polls every 300 s, read the broker file first, one point at a time. Estimate under 100 calls an hour in total.                                                                                                           |
| Flaky CI                                                    | A red verification or cut run with no culprit                                         | The in-job retry; an old flake gets its `priority:critical` issue (owner rule) naming the mechanism, never "it was load"; a new one is a regression of its batch. Never for GPU tests.                                   |
| An intermittent regression that never fails in CI           | It reaches npm                                                                        | Not detected by any design here. The weekly restricted-CPU run is the only standing probe for it.                                                                                                                        |
| A hang                                                      | A test waits up to the 25-minute guard, twice with the retry                          | Accepted cost of #3284. The duration report shows tests drifting toward it.                                                                                                                                              |
| Golden broken for a long time                               | Verification red twice in a row on different culprits, or a bisect that names nothing | The pipeline round reverts every landing since `golden-verified` that touches a failing package, and re-lands the innocent ones. Landings continue meanwhile; cuts keep using `golden-verified`, which stays good.       |
| Tests never run before landing                              | Authors land broken tests more often                                                  | `test:changed` stays one command away. The revert rate is measured (step 13's trigger). The weekly restricted-CPU run stays the check for load sensitivity.                                                              |
| Screenshot approvals on a moving target                     | A new cut or accept commit restarts the review or cancels CI                          | The cut is frozen during review. With composed approvals, an approval covers an image wherever it reappears. One preview per verified commit, and a stale preview is cancelled.                                          |
| A screenshot regression after verification                  | Verification does not run the screenshot gate                                         | The cut takes only commits whose captures are clean and stable; image changes are the owner's at Finish; ship CI's gate is the final check.                                                                              |
| A release removal while a newer cut is under review         | `cut-fix` would ship the unreviewed batch                                             | Point `golden-cut` at master's tip first, `cut-fix` the revert alone, then re-cut the newer batch (section 5).                                                                                                           |
| Multiple sessions landing at once                           | Conflicts and queue contention                                                        | The lock lasts seconds, and light gates run 4 at a time in about 15 min. A big landing still uses the freeze rule. `--priority` only for `priority:critical`.                                                            |
| Disk                                                        | 10 GB worktrees, 93% full                                                             | Slimming and automatic cleanup (row 25). Light gates need no test outputs.                                                                                                                                               |
| Live-copy drift                                             | The gate and land tool run code no landing recorded (today 13 and 11 commits)         | The alarm in step 1. A gate or land change goes live and lands the same day.                                                                                                                                             |
| CLAUDE.md on master lags golden by hundreds of commits      | Sessions follow instructions for a pipeline that no longer exists                     | Ship a cut as soon as step 1 lands. Pipeline-round reads the golden copy of the skills until then.                                                                                                                       |
| Both CI runs on near-identical trees disagree               | Verification green, cut CI red (or the reverse)                                       | The difference is master's newer commits or a flaky test. The cut's red is handled like a verification failure: the same retry-pass rule, else bisect over the merge with master.                                        |
| The release train runs while verification needs the runners | Slower verification                                                                   | Accepted; jobs queue. The release is the priority.                                                                                                                                                                       |
| A public-repository workflow pushed from this machine       | `golden-candidate` runs with `secrets: inherit`                                       | Only the owner's token on this machine pushes those refs. Checks are named `Verify / ...`, so they can never satisfy master's required check.                                                                            |
| No self-hosted runner                                       | No way to add capacity cheaply                                                        | Not needed: 60 standard jobs run a full suite in 31 to 64 min. Paid overflow runners (RunsOn about $140 to $180 for September's usage) only if job queueing costs more than an hour a day.                               |

## 8. Review notes

An adversarial review of the first draft (2026-10-24) raised 27 problems. Each was checked against
the push log, the gate logs, the code on `origin/golden` and `origin/design/3316-full-tests-in-ci`,
and the run times it cited. One line each, in the order raised:

1. The act() flood did not keep golden red for 20 hours: fixed. Golden passed every graphty shard
   at f3402561e5 and 2920317b69 with it present; it is now an amplifier, and the fix's delay is
   given to the GraphPlace race, the T8 flake, the docs failure and the repackaging (3.1, 3.2).
2. Machine load is mostly the pipeline's own concurrency: fixed. Its own row, with 8 to 9 gates at
   once on 10-23 and failures continuing after the flood was gone (3.2).
3. The cut re-gate did not cost 10 hours on a known-good commit: fixed. 1 to 2 hours, "Partly", and
   the same defects failed cut CI (rows 35, 3.2).
4. Timings assumed an unbuilt matrix bisect: fixed. The plan keeps the built CI bisect, costs it at
   log2(n) points of 35 to 40 min, and defers the matrix (row 67); the log budget moved before the
   switch.
5. #3284 trades fast failures for 25-minute hangs: fixed. The hang is budgeted, a non-gating
   duration report replaces the 50% rule, and the plan says #3284 hides the slow class (rows 40, 42).
6. Sections 1.3 and 3.3 contradicted each other: fixed. The 31 test-step failures are classified
   (7 in files that failed in CI, 2 a product race, 22 local only, up to 5 of them unchecked) and
   the same figures are used in both places.
7. The "changed since the last release tag" rule was unbuilt and file-based: fixed. Replaced by the
   history rule (a new retry-pass is a regression) and the file-changed culprit shortcut (rows 38,
   58; section 5).
8. Verification was costed at the pull-request path's 31 min: fixed. 48 to 64 min on the full-build
   path, with finding the 20-minute Build as rollout step 2(f).
9. The yield to cut CI and trains was left out of the wait: fixed by dropping the yield (row 29).
10. The frozen cut was costed at 15 min and is not built: fixed. F (half a cut cycle on average) is
    added, the six-hour claim is conditional on R, and the freeze and the skill change are rollout
    step 5.
11. The master push build before the train and the 105-minute figure: fixed. 27 min added until the
    train starts on the push; 65 min measured; 105 removed.
12. Verification does not run the screenshot gate: fixed. Stated, and verification now marks failed
    captures and unstable images not clean, so such a commit is never cut.
13. One preview of the cut only leaves `cut` no candidate: fixed. One preview per passing
    verification (row 41).
14. The matrix bisect cannot be done with the built workflow: fixed as in 4.
15. With the light gate on, no new flaky test would get an issue until the listener was built:
    fixed. The listener moved into rollout step 2(d), before the switch.
16. Release removal contradicted the cut-fix rule: fixed. Point `golden-cut` at master's tip,
    `cut-fix` the revert alone, re-cut the newer batch, and count a Finish until composed approvals.
17. Step 0 cannot ship alone: fixed. It ships with the 4 landings on `golden-cut`, which are
    verified (ancestors of `golden-verified`) and change no baselines.
18. The broken-golden window did not add up: fixed. 2.5 to 4 h today, 1.5 to 2.5 h after the Build
    fix, carried into the bad day, which now misses six hours.
19. The log budget came after the switch: fixed (rollout step 2).
20. A new intermittent regression could reach npm: fixed. The history rule runs at verification and
    release, and the npm row now says plainly what is still undetectable.
21. The quarantine list lost its only writer: fixed. Verification writes it from CI results; the
    local counter and the 14-day expiry are dropped.
22. "Pipeline-only cut" was undefined: fixed as in 16; the phrase is gone.
23. T4 probes outside the train would break the T4 rule: fixed. Probes run on the local NVIDIA card.
24. The local verification backend buys nothing: fixed. Dropped, with its dependencies (rows 18, 30).
25. The release train re-runs the Linux suite: fixed in part. It now reuses step 5's run when the
    trees match. Rejected in part: the saving is about 10 minutes, not 30 to 60, because the T4 lane
    (51 min of run 39540908824's 65) is the critical path.
26. The local preview duplicates CI's captures: fixed in part. Serving the verification run's
    captures is rollout step 10. Until then one local preview per verified commit stays, because the
    review page can decide only a local preview or the pull request's own CI capture today.
27. The typical estimate left out the yield: fixed as in 9.

Reviewers' verdicts, one line each:

- Timeline and causes: the tier-3 analysis was wrong about the largest cause; corrected, the root
  cause is timing-dependent tests under the pipeline's own load, with the act() flood as amplifier.
- Built code against the plan: several mechanisms the timings relied on (matrix bisect, freeze,
  release rule, yield) were unbuilt or contradicted by the code; the plan now uses what is built or
  lists the build as a rollout step.
- Timings: the estimates were optimistic by about 1 to 2 hours to master; restated, six hours holds
  only with prompt owner review and a clean batch.
- Flaky tests and eventual consistency: the first draft let new intermittent regressions through to
  npm and left the quarantine list without a writer; both are now handled before the switch.
- Simplification: the local backend, the yield and the third Linux run are unneeded; dropped or
  reused.
