# CX2 (Cytoscape Exchange format, version 2): research for a graph-io reader

CX2 is the JSON network format of NDEx (the Network Data Exchange, ndexbio.org), Cytoscape Desktop
3.10+ and Cytoscape Web. A CX2 file is one JSON array: a descriptor object, then "aspect" blocks
(`nodes`, `edges`, `attributeDeclarations`, `visualProperties`, ...), then a `status` object. It is
a different format from CX version 1 (`.cx`, separate `nodeAttributes` / `cartesianLayout`
aspects), which this note covers only where a CX2 reader meets CX1 leftovers.

This note lists the authoritative sources, every feature and variant a comprehensive reader must
handle (with the spec revision that introduced it), every error and edge case together with what
the three reference readers do with it, how each construct maps onto the graph-format snapshot,
24 candidate sample files plus a list of fixtures to author, and the independent reader the
conformance suite should take its expectations from.

Scratch evidence for every claim below (the cloned reader sources, the downloaded files, the
survey scripts and their output) is in `tmp/samples-cx2/` of this worktree:
`tools/survey.py` (aspects, counts, duplicates, dangling references, parallel edges),
`tools/quirks.py` (value-level deviations from the declarations) and `tools/ndex2_oracle.py`
(what ndex2 reads from each file).

## 3. Feature inventory

### 3.1 Top-level structure

- The document is ONE JSON array (RFC 8259, UTF-8). Element 0 is the descriptor; then an
  optional pre-`metaData` block; then `attributeDeclarations` (required when any attribute
  exists); then aspect blocks; then an optional post-`metaData` block; then exactly one
  `status` block, last.
- Every element after the descriptor is an object with exactly ONE key, the aspect name, whose
  value is an array of elements ("aspect data block"). All elements of one aspect have the same
  structure.
- No aspect blocks at all means an empty network. The smallest valid file is
  `[{"CXVersion":"2.0","hasFragments":false},{"status":[{"success":true}]}]`
  (`cx2_empty.cx` below).
- Descriptor fields: `CXVersion` (required, `"major.minor"`, only `"2.0"` exists) and
  `hasFragments` (boolean, default false). Key order varies: the Java writer emits
  `hasFragments` first. Unknown descriptor keys: none defined; ignore with a warning.
- Fragments (`hasFragments: true`): any aspect may be split into several blocks, interleaved in
  any order; a consumer concatenates the blocks of one aspect in encounter order.
  `attributeDeclarations` may itself be fragmented, but an attribute must be declared before
  the first element that uses it.
- `metaData` elements: `{ "name": string (required), "elementCount": long (optional) }`.
  At most two `metaData` blocks (pre and post). Real files carry CX1 leftovers in metadata
  elements (`version`, `idCounter`, `propertyCounter`, `consistencyGroup`, seen in every
  Cytoscape Web fixture); they are ignorable.
- `status`: `[{ "error": string, "success": boolean }]`, exactly one element. `success: false`
  means the producer failed mid-stream and the document must not be used; `success: true` with
  a non-empty `error` is a warning. Both fields may be absent in practice (`{"success": true}`
  alone is the common form).

### 3.2 Core aspects

| Aspect                   | Elements                       | Shape                                                                                                             | Notes                                                                                                           |
| ------------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `attributeDeclarations`  | exactly 1 (unless fragmented)  | `{ "networkAttributes": {name: decl}, "nodes": {name: decl}, "edges": {name: decl}, <opaque aspect>: {...} }`     | decl = `{ "d": type, "v": default, "a": alias }`; `d` required by the spec                                      |
| `networkAttributes`      | exactly 1 for a single network | `{ name: value, ... }`                                                                                            | reserved `name`, `description`, `version`; every key must be declared                                           |
| `nodes`                  | any                            | `{ "id": long, "x": double, "y": double, "z": double, "v": {attrs} }`                                             | `id` required and unique among nodes; `v` must not contain `id`; `x`/`y`/`z` inside `v` are ordinary attributes |
| `edges`                  | any                            | `{ "id": long, "s": long, "t": long, "v": {attrs} }`                                                              | `id` unique among edges; `s`, `t` node ids; `v` must not contain `id`; `s`/`t` inside `v` are ordinary          |
| `visualProperties`       | exactly 1, never fragmented    | `{ "default": {"network":{}, "node":{}, "edge":{}}, "nodeMapping": {VP: mapping}, "edgeMapping": {VP: mapping} }` | portable properties only; Cytoscape-only properties belong in an opaque aspect (e.g. `cyVisualProperties`)      |
| `nodeBypasses`           | any                            | `{ "id": node id, "v": {VP: value} }`                                                                             | per-node visual overrides                                                                                       |
| `edgeBypasses`           | any                            | `{ "id": edge id, "v": {VP: value} }`                                                                             | per-edge visual overrides                                                                                       |
| `visualEditorProperties` | exactly 1                      | spec: flat object; every real writer: `{ "properties": {...} }`                                                   | see 3.6                                                                                                         |
| opaque aspects           | any                            | any object, one structure per aspect                                                                              | attributes in them may be declared in `attributeDeclarations`                                                   |

Reserved node attributes: `name` (string, the label), `represents` (string, a standard
identifier such as a gene id), `alias` (list_of_string, alternative identifiers). Reserved edge
attribute by convention (not in the spec text, but written by every Cytoscape and NDEx producer):
`interaction` (string, the SIF relation type, usually aliased to `i`). Cytoscape Desktop also
writes `shared interaction` / `shared name` when the file was not declared with them.

### 3.3 Data types (`d`)

`string`, `long`, `integer`, `double`, `boolean`, and `list_of_string`, `list_of_long`,
`list_of_integer`, `list_of_double`, `list_of_boolean`. Exactly these ten; the Java enum
`ATTRIBUTE_DATA_TYPE` and the Cytoscape Web `CxTypeName` agree. ndex2 additionally accepts the
Python spellings `str`, `int`, `bool`, `float` (`VALID_ATTRIBUTE_DATATYPES_PLUS_SHORT`), which the
spec does not define.

- "All values of an attribute must have the same data type in an aspect."
- Numbers are JSON numbers; the declaration is what makes `1` a `double` or a `long`. A `long`
  can exceed 2^53 (JSON allows it; `JSON.parse` would round it).
- NaN / Infinity cannot be written; NDEx writes null in their place (since 2023-05-24) and
  recommends a string column when NaN must survive.
- A declaration without `d`: not allowed by the spec, but the Java reader treats it as `string`
  and the ndex-object-model test files contain it (`cx2_tiny.cx2`: `"name": {"a": "n"}`).

### 3.4 Aliases and defaults

- `a` (alias): a shorter key used INSTEAD of the full name inside `nodes[].v` / `edges[].v`.
  Once an alias is declared, "the full attribute name can no longer be used" in those blocks.
  Aliases are not permitted for `networkAttributes` (2023-08-30). Mappings, bypasses and
  `tableDisplayConfiguration` always use the full name, never the alias.
- An alias may equal the full name (`"n": {"a": "n", "d": "string"}` in every Cytoscape Web
  fixture) -- legal and a no-op.
- `v` (default): "If an element is missing this attribute, it will be automatically assigned the
  default value." It cannot express null for that attribute. Not permitted for
  `networkAttributes` (2023-08-30). Real defaults seen: strings (including HTML and SVG data
  URLs), booleans `false`, the string `"0.0"` for a double in the spec's own example (a TYPE
  MISMATCH in the specification text: `"expression_level": { "d": "double", "v": "0.0" }`).

### 3.5 Coordinates

- `x`, `y` (CSS pixels, +x right, +y down) on the node element itself, never in `v`.
- If any node has `x`/`y`, all nodes must have both; a node with `x` must have `y`.
- `z` is "z coordinate or z-order, depending on how the renderer interprets it"; it requires
  `x` and `y`; if one node has it, all should. Every real file with `z` uses it as a stacking
  order: WikiPathways networks on NDEx carry `z` values 0, 4096, 16384, 28672, 32768, 32771
  (`ndex-72288e93...cx2`), i.e. Cytoscape's `NODE_Z_LOCATION`, not depth.
- The CX1 `cartesianLayout` aspect does not exist in CX2 for single networks; it is still used
  for collections and "never both" may appear in one file.
- `NODE_X_LOCATION` / `NODE_Y_LOCATION` / `NODE_Z_LOCATION` also exist as visual properties (in
  `default.node`, and in principle in bypasses); the node's own `x`/`y` wins.

### 3.6 Visual aspects (preserved, not interpreted, by graph-io)

- `default.network` / `default.node` / `default.edge`: visual property name -> value. Values are
  scalars, or objects for composite properties: `NODE_LABEL_FONT_FACE`
  `{FONT_FAMILY, FONT_STYLE, FONT_WEIGHT}`, `NODE_LABEL_POSITION`
  `{HORIZONTAL_ALIGN, HORIZONTAL_ANCHOR, VERTICAL_ALIGN, VERTICAL_ANCHOR, MARGIN_X, MARGIN_Y,
JUSTIFICATION}`, `NODE_IMAGE_<n>_POSITION`, `NODE_IMAGE_<n>_SIZE {HEIGHT, WIDTH}`,
  `EDGE_CONTROL_POINTS [{cos, sin, ratio}]`, custom graphics. Some booleans and numbers are
  written as strings by Cytoscape (`"EDGE_SELECTED": "false"`, `"COMPOUND_NODE_PADDING": "10.0"`).
- Mappings: `{ "type": "PASSTHROUGH" | "DISCRETE" | "CONTINUOUS", "definition": {...} }`.
  `definition.attribute` is the FULL attribute name; `definition.type` is only needed when the
  attribute is undeclared. DISCRETE `map: [{v, vp}]` (values of the attribute's type, e.g.
  integers for a declared integer). CONTINUOUS `map: [{min, includeMin, max, includeMax,
minVPValue, maxVPValue}]` where the first and last intervals are open-ended: `min` (or `max`)
  and its VP value are ABSENT (`demo.cx2`, `NODE_LABEL_FONT_SIZE`). A mapping may name an
  attribute that no element carries.
- `nodeBypasses` / `edgeBypasses`: `{id, v: {VP: value}}`; `id` refers to a node / edge id.
- `visualEditorProperties`: `arrowColorMatchesEdge`, `nodeSizeLocked`,
  `nodeCustomGraphicsSizeSync` (written by Cytoscape, not in the spec), `NETWORK_CENTER_X_LOCATION`,
  `NETWORK_CENTER_Y_LOCATION`, `NETWORK_SCALE_FACTOR` (all three or none take effect),
  `tableDisplayConfiguration` (2025-06-12: `nodeTable` / `edgeTable` / `networkTable` each with
  `columnConfiguration [{attributeName, visible, columnWidth?}]`, `sortColumn?`,
  `sortDirection: "ascending" | "descending"`). The spec shows these keys directly on the element;
  the Java writer (`VisualEditorProperties`, `@JsonProperty("properties")`) and therefore EVERY
  file NDEx and Cytoscape produce wraps them in `{"properties": {...}}`. A reader must accept both.
- `tableVisualProperties` (`AbstractTableVisualProperty.ASPECT_NAME` in ndex-object-model): a
  Cytoscape table-cell style aspect, not in the spec; treat as opaque.

### 3.8 HCX profile (hierarchies, CX2-only)

Network attributes `ndexSchema: "hierarchy_v0.1"`, `HCX::modelFileCount`,
`HCX::interactionNetworkUUID` / `HCX::interactionNetworkName` / `HCX::interactionNetworkURL`;
node attributes `HCX::isRoot` (boolean), `HCX::members` (list_of_long: node ids in ANOTHER
network), `HCX::memberEdges`, `HCX::memberNames` (list_of_string), `HCX::memberQuery` (a JSON
string). Edges are directed parent -> child. HCX adds no syntax: a CX2 reader reads it as
ordinary attributes. `HCX::members` refers to a different file, so it is NOT a graph-format
`parent` column.

## 4. Errors and edge cases

Columns: what the spec says; what ndex2 3.12.0 does (`create_from_raw_cx2`, verified by running
it, `tools/ndex2_oracle.py`); what the Java reader + Cytoscape Desktop do (`CXReader` +
`Cx2Importer`, read from source); what Cytoscape Web's validator does; the recommended graph-io
behavior. Codes in the last column follow graph-io's rule: a shared concept uses the shared code

## 5. Mapping onto the graph-format snapshot

### 5.1 Topology

- Every CX2 edge is DIRECTED. The format has no undirected flag and no per-edge direction;
  Cytoscape Desktop creates every edge with `addEdge(src, tgt, true)`, ndex2's networkx factory
  builds a `MultiDiGraph`, NDEx draws arrows from the style only. Import with
  `DirectionResolver` set to directed for all edges; `defaultDirected` is ignored
  (`W_OPTION_IGNORED`). Whether an `interaction` like `"interacts with"` is semantically
  symmetric is a style question (`EDGE_TARGET_ARROW_SHAPE: "none"`), not topology.
- Multigraph: parallel edges with distinct ids are normal (`flags.multigraph`), and self-loops
  occur.
- Node ids: CX2 ids are integers. Keep them as numeric ids through `IdCoercer` (integer ids,
  `meta.idType: "integer"`), exact above 2^53 as described in 4.2. The label is the `name`
  attribute, never the id.
- Edge ids: an edge column `id` with role `id`, `unique`, dtype `f64` (or `u32` when every id
  fits), so the exporter can write the same ids back and bypasses can be resolved.
- Nested graphs: CX2 has none. Cytoscape groups (CX1 `cyGroups`) are not written to CX2 (the
  CX2 path of `CxExporter` flattens them); HCX hierarchies are ordinary directed edges plus
  cross-file member lists. No `parent` column is produced. Collections (several networks) are a
  CX1 feature; a CX2 file is one network, so `importAll()` is not needed.

### 5.2 Attribute columns

| CX2 `d`           | graph-format dtype                                                              | Notes                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `string`          | `string` (or `dict` when the cardinality heuristic fires, as for other formats) | `origin.type: "string"`                                                                                                  |
| `long`            | `f64`                                                                           | `W_PRECISION` above 2^53; importer option `long: "string"` makes the column `string` (design 5.1 rule for declared long) |
| `integer`         | `i32`                                                                           |                                                                                                                          |
| `double`          | `f64`                                                                           |                                                                                                                          |
| `boolean`         | `bool`                                                                          |                                                                                                                          |
| `list_of_string`  | `list` of `string`                                                              |                                                                                                                          |
| `list_of_long`    | `list` of `f64`                                                                 | `HCX::members`                                                                                                           |
| `list_of_integer` | `list` of `i32`                                                                 |                                                                                                                          |
| `list_of_double`  | `list` of `f64`                                                                 |                                                                                                                          |
| `list_of_boolean` | `list` of `bool`                                                                |                                                                                                                          |
| undeclared        | inferred per column (design 5.1: `typeof`, widening; arrays -> `json`)          | `W_CX2_UNDECLARED_ATTRIBUTE`                                                                                             |

- Column name = the FULL attribute name; `origin` = `{ format: "cx2", id: <alias or null>,
type: <d> }` so the exporter restores the alias; `meta.default` = the declared default
  (representable in the dtype), and rows without a value are unset with `fill` = the default, so
  `value()` returns the default exactly as the spec says. The exporter writes `v` back.
- Roles: `name` -> role `label` (the only label); `represents`, `alias` keep their names with no
  role (no role fits; `alias` is a list of identifiers, not graph-format's `labels`).
  `interaction` stays an edge column with no role (it is a relation type; `kind` would be the
  nearest role, but assigning it is a reader's choice the JSON importer also avoids). No column
  becomes the `weight` role implicitly: CX2 has no weight convention, and a plain column named
  `weight` follows the shared importer rule that every format already applies.
- Name collisions with the importer's own columns (`id`, the position column) use
  `declareResolved` (`<name>#<origin.id>`, design 5.6) with `W_COLUMN_RENAMED`.
- Network attributes: `snapshot.graph` columns with the declared dtypes; `name` and
  `description` also fill `GraphMeta.name` / `GraphMeta.description`; `version` stays a graph
  column. `GraphMeta.sourceFormat: "cx2"`, `sourceVersion`: the `CXVersion` text.

### 5.3 Positions

- `x`, `y` -> the canonical `position` column (f32 x3, z component 0),
  `origin.extra.sourceDims: 2`, `origin.extra.units: "file"`. CSS pixels with +y DOWN: the column
  holds the file's values unchanged; graphty-element flips/rescales at import like it does for
  every 2D format (same as Cytoscape.js JSON, which shares the convention).
- `z` -> NOT the third position component by default. Every real file uses it as a stacking
  order (Cytoscape's `NODE_Z_LOCATION`), and putting 32768 into the depth axis would explode a
  3D layout. Import it as an `f64` node column named `z` (renamed `z#position` if a `v` attribute
  called `z` exists) carrying `origin.extra.cx2: "z"`; the exporter writes it back as the node's
  `z`. An importer option (`zAs: "order" | "position"`) can put it into the position column for a
  producer that really means depth.
- Precision: real files carry full doubles (`123.14439668294953`); the f32 position column keeps
  7 significant digits, so an export re-writes rounded coordinates. That is an exporter loss note,
  not an import issue.

### 5.4 What has no snapshot slot

| CX2 construct                   | Recommended handling                                                                                                                                                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `visualProperties`              | `GraphMeta.extra.cx2.visualProperties` (JSON, verbatim). Turning it into graphty style layers is graphty-element's job (styling must go through style layers there), not graph-io's                                                                    |
| `nodeBypasses` / `edgeBypasses` | a node / edge `json` column `graphty.cx2.bypass` holding each element's `v` object (row-aligned, survives compaction and derived graphs, unlike ids stored in `extra`)                                                                                 |
| `visualEditorProperties`        | `GraphMeta.extra.cx2.visualEditorProperties`, normalized to the unwrapped form, with the wrapper shape recorded for the exporter                                                                                                                       |
| opaque aspects                  | `GraphMeta.extra.cx2.opaque[<name>]` = the concatenated elements, verbatim, so an export can write them back; no issue (the spec makes them legal). A size cap with `W_CX2_OPAQUE_DROPPED` is a reasonable guard for multi-megabyte provenance aspects |
| `metaData`                      | not stored; each `elementCount` is checked against the elements read and a mismatch is `W_COUNT_HINT` (the shared code)                                                                                                                                |

### 5.5 Sniffing and registration

- Extension `.cx2`; MIME `application/json` (NDEx serves CX2 as `application/json`; no
  registered type exists). Do NOT claim `.cx` (CX1).
- Content: the first array element is an object containing `"CXVersion"` (key order varies:
  `{"hasFragments":false,"CXVersion":"2.0"}` is the Java writer's order). CX1 starts with
  `{"numberVerification": ...}` or `{"metaData": ...}` and never has `CXVersion`. The JSON
  dialect sniffer (`graph-io/src/formats/json/dialect.ts`) classifies a top-level array as
  Cytoscape.js only when the first element has an object `data` (or the array is empty), so a
  CX2 head does not collide today; the CX2 sniff should score above the JSON one for
  `[{"CXVersion"` and the empty `[]` stays with the JSON dialect.

### 5.6 Export notes (for the companion exporter in issue #307)

- Write `[{"CXVersion":"2.0","hasFragments":false}, {"metaData": [...]}, {"attributeDeclarations":
[...]}, {"networkAttributes": [...]}, {"nodes": [...]}, {"edges": [...]}, visual aspects from
`extra`, opaque aspects, {"status":[{"error":"","success":true}]}]`.
- Losses to announce in `check()`: undirected or mixed edges (CX2 has no undirected edge:
  `W_MUTUAL_EXPANDED` / an undirected-written-as-directed note), non-integer node ids (CX2 ids are
  longs: a sanitize/remap with `E_INVALID_ID` under the default `sanitizeIds: "error"`), `json`
  and nested `list` columns (no CX2 type: written as strings), `dict` (written as `string`),
  `u8` / `u32` (written as `integer` / `long`), NaN / Infinity in `f64` (written as null),
  the `parent` column (no CX2 slot), and f32 position rounding.

## 7. The independent reader for expectations

**ndex2 3.12.0** (NDEx's Python client, BSD-3-Clause), `ndex2.cx2.CX2Network.create_from_raw_cx2`,
optionally followed by `CX2NetworkXFactory().get_graph(net)` for a networkx `MultiDiGraph`. It
is maintained by the NDEx team that co-authors the spec, it is Python (so it slots into the
existing `tools/oracle.py` driver as `oracle_cx2.py` beside networkx 3.1), and it resolves
aliases, applies defaults, converts declared types and returns nodes, edges, coordinates,
network attributes, bypasses, visual properties and opaque aspects.

How to run it (verified in this worktree with Python 3.10):

```bash
uv venv tmp/samples-cx2/venv -p 3.10
VIRTUAL_ENV=tmp/samples-cx2/venv uv pip install ndex2==3.12.0   # pulls networkx, pandas, numpy, ijson
tmp/samples-cx2/venv/bin/python tmp/samples-cx2/tools/ndex2_oracle.py <file.cx2 ...>
```

In the conformance tooling the same is `pip install ndex2==3.12.0` into the oracle's Python and
an `oracle_cx2.py` whose `compute(path, fixture)` returns `nodes`, `edges`, `directed: true`,
`nodeIds`, `labels` (the `name` attribute), `nodeAttrs` (alias-resolved, default-filled, typed
values) and `edgeChecks` from `CX2Network.get_nodes()` / `get_edges()` /
`get_network_attributes()`, with `x` / `y` / `z` read from the node dicts.

ndex2 is lenient: it validates nothing structural. Where it departs from the specification the
expectation follows the specification and the fixture says why (the same mechanism as
`networkxDisagrees`), in these known places:

- It accepts a missing or failed `status`, a missing or wrong `CXVersion`, a top-level object, an
  empty array, blocks with several keys, blocks after post-metadata and dangling edge endpoints
  (all read as data).
- It aborts on the first duplicate node or edge id, where graph-io's shared rule warns and keeps
  the first.
- It keeps only the last `attributeDeclarations` / `networkAttributes` / `visualProperties`
  block (fragmented declarations are lost).
- It resolves aliases only for declarations that precede the elements.
- It ignores falsy defaults (`if default_value:`).
- It truncates `3.7` to 3 for integer and long columns and reads any non-`"true"` string as false
  for booleans.
- It treats `visualEditorProperties` as an opaque aspect.

For the error cases the expectation comes from the specification, cross-checked against the
strict Java reader (`org.ndexbio.cx2.io.CXReader` in ndex-object-model, which NDEx and Cytoscape
Desktop use): its messages for missing descriptor, missing status, `success: false`, aspects after
post-metadata and malformed blocks are quoted in section 4. Running it needs a JDK and Maven
(`mvn -q test -Dtest=CXReaderTest` in a checkout); it is a cross-check, not a required tool.
Cytoscape Web's `validateCX2` (`npx vitest` in its repository) is a third opinion for referential
errors, with two known defects of its own: it reads network-attribute declarations under the key
`network` instead of `networkAttributes`, and it requires a `metaData` block that the spec makes
optional.
