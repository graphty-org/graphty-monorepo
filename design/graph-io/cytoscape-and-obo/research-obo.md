# OBO flat file format and OBO Graphs JSON: research for graph-io

Research date: 2026-10-02. Scope: what a comprehensive graph-io reader for the OBO flat file format
(versions 1.0, 1.2 and 1.4) and for OBO Graphs JSON (the "obographs" format the Gene Ontology also
publishes) has to handle, how each construct maps onto the graph-format snapshot, which real
files exercise it, and which independent reader the conformance suite should take its
expectations from.

Everything below that says "measured" was run on 2026-10-02 against the files in
`tmp/samples-obo/` (downloads, probes and scripts; `SHA256SUMS` there pins every candidate file).
The probe cases are in `tmp/samples-obo/probes/*.obo`, the scripts in `tmp/samples-obo/scripts/`.

---

## 1. Summary

- OBO is a line-oriented tag-value text format: an untitled header block, then frames ("stanzas")
  headed `[Term]`, `[Typedef]` or `[Instance]`. Every frame starts with `id:`. A graph is formed by
  `is_a:` (subclass) and `relationship: <relation> <target>` clauses, always pointing from the
  frame (child, subject) to the target (parent, object). Relations are declared by `[Typedef]`
  frames. Everything else on a frame (name, definition, synonyms, cross-references, subsets,
  obsoletion) is node metadata.
- There are three specifications, and they disagree. The 1.4 "syntax and semantics" document is
  a BNF plus an OWL mapping and is the only normative one; the 1.2 and 1.4 "guides" are
  informative but they are what most writers and lenient readers follow. The main conflicts:
  unknown tags (the guides: never fatal; the BNF: not in the grammar), synonym scope (optional in
  1.2, mandatory in the 1.4 BNF), `\W` (the guides: a space; the BNF: the letter W), per-xref
  qualifiers inside a list (1.2: allowed; 1.4 BNF: not), and backslash line continuation (1.2:
  allowed; 1.4: deprecated).
- Real files do not say which version they follow. The current GO release (`releases/2026-07-26`)
  writes `format-version: 1.2` while using 1.4-only tags (`property_value`, `creation_date`
  in ISO 8601, `holds_over_chain`). Of 101 test-suite and ontology files surveyed, 36 have no
  `format-version` at all, 51 say 1.2, 14 say 1.4. A reader must therefore accept the union of
  1.2 and 1.4 and never branch on the declared version for anything except reporting.
- The GO publishes three editions. `go-basic` has only is_a, part_of, regulates,
  negatively_regulates and positively_regulates and is guaranteed acyclic with no links across
  its three namespaces; `go` adds has_part, occurs_in, happens_during and ends_during (which can
  create cycles), plus intersection_of, disjoint_from, created_by and creation_date; `go-plus`
  (OWL and JSON only, no OBO) adds the imported ChEBI, CL and Uberon axioms. Measured on the
  2026-07-26 release: go-basic 48,340 terms (10,248 obsolete), 71,496 edges; go 48,340 terms,
  73,634 edges.
- OBO Graphs JSON is a different file of the same ontology (`go-basic.json`, `go.json`): a
  `{"graphs": [{"nodes": [...], "edges": [{"sub", "pred", "obj"}]}]}` document produced by
  converting the ontology to OWL first. It IS a JSON graph dialect graph-io should read, but it
  collides with graph-io's JSON sniffing today: `sniffJsonDialect()` returns `"jgf"` for any
  top-level `graphs` array (`graph-io/src/formats/json/dialect.ts:143`), so an obographs file is
  misread as JGF. The discriminator is edges keyed `sub` / `pred` / `obj` (the README still says
  `subj`; the JSON Schema, the reference implementation and every GO file say `sub`).
- Independent reader for the expectations: **fastobo-py 0.14.1** (Rust core fastobo 0.15.5,
  MIT, `pip install fastobo==0.14.1`), whose `fastobo.load()` is a strict OBO 1.4 parser and
  whose `fastobo.load_graph()` reads OBO Graphs JSON; mapped to nodes and edges by a small
  `oracle_obo.py`. **ROBOT 1.9.11** (owlapi's Java OBO parser, the reference implementation the
  GO itself uses) is the second opinion for the lenient cases fastobo rejects or panics on. Both
  are detailed in section 9.

### 4.5 Typedef frame clauses

All Term tags above, plus: `domain`, `range` (0..1 in 1.4), `inverse_of`, `transitive_over`,
`holds_over_chain <r1> <r2>`, `equivalent_to_chain <r1> <r2>`, `disjoint_over`, booleans
`is_cyclic`, `is_reflexive`, `is_symmetric`, `is_anti_symmetric`, `is_asymmetric`,
`is_transitive`, `is_functional`, `is_inverse_functional`, `is_metadata_tag`, `is_class_level`,
`expand_assertion_to` / `expand_expression_to "template" [xrefs]`, and `is_a <relation>` (sub-
property). `relationship` in a Typedef relates two relations. 1.2 forbids union_of,
intersection_of and disjoint_from here; 1.4 allows them. Measured: RO has 711 Typedefs (and 54
Terms), GO 11 (go) / 5 (go-basic), goslim 11.

### 4.6 Instance frame clauses

`id`, `name`, `namespace`, `alt_id`, `def`, `comment`, `subset`, `synonym`, `xref`,
`instance_of` (0..1), `property_value <relation> <ID | "literal" xsd:type>`, `relationship
<relation> <ID>`, `created_by`, `creation_date`, `is_obsolete`, `replaced_by`, `consider`,
`is_anonymous`. No surveyed real file has an Instance frame; the conformance fixture must be
generated (the guide's own `john` / `heather` example). fastobo 0.14.1 PANICS (Rust
`unreachable!`, surfaced as `pyo3_runtime.PanicException`) on `relationship:` inside an Instance
frame; ROBOT reads it.

### 4.7 Unknown frames

`[Annotation]`, `[Foo]`: the 1.0-1.4 guides say unrecognized frames "must survive
round-tripping"; fastobo, pronto, obonet and ROBOT all reject the file (probe
`unknown_stanza`). graph-io should skip the frame with a warning (it is not a node).

### 4.8 Document structure rules (1.4 section 4)

- Frames with the same id and the same type are MERGED: the union of their clauses, identical
  tag-value clauses counted once. fastobo returns both frames; ROBOT merges (probe
  `duplicate_frame_merge`: 2 classes, 1 edge). fastobo-validator `--duplicates` reports it.
- The same id for two frame types (a Term and a Typedef) is structurally invalid; ROBOT reads it
  (0 classes), pronto throws, fastobo-validator reports it.
- Cardinality constraints (table above) hold after merging; two `name` clauses are a parse error
  per the guide; fastobo and ROBOT read the file, fastobo-validator reports it.
- Namespace defaulting: a frame without `namespace` gets `default-namespace`, else a
  parser-chosen value.
- Header clauses after the first frame are not header clauses (fastobo rejects as an unknown
  Term clause; ROBOT accepts; probe `header_after_frame`).

### 4.9 OBO Basic and the GO editions

OBO Basic (1.4 section 6.2) is the sublanguage legacy graph tools assume: a DAG over is_a and
relationship, unidirectional (no part_of together with has_part), no dangling clauses, fully
labeled, no equivalence axioms, singly labeled edges (at most one relation between two terms),
no qualifier blocks, no disjointness, no owl-axioms, no imports. go-basic is OBO Basic; go is
not (has_part makes cycles; measured 2 term pairs with two different relations in go.obo, 0 in
go-basic; goslim_generic, built from go, has 2).

## 8. OBO Graphs JSON

### 8.1 Shape (schema, measured on GO and the obographs examples)

```
{ "@context"?: ..., "meta"?: Meta,
  "graphs": [ { "id": IRI, "lbl"?: string, "meta"?: Meta,
      "nodes": [ { "id": IRI, "lbl"?: string, "type"?: "CLASS" | "INDIVIDUAL" | "PROPERTY",
                   "propertyType"?: "ANNOTATION" | "OBJECT" | "DATA", "meta"?: Meta } ],
      "edges": [ { "sub": IRI, "pred": "is_a" | "subPropertyOf" | "inverseOf" | "type" | IRI, "obj": IRI, "meta"?: Meta } ],
      "equivalentNodesSets"?: [ { "representativeNodeId", "nodeIds": [], "meta" } ],
      "logicalDefinitionAxioms"?: [ { "definedClassId", "genusIds": [], "restrictions": [ { "propertyId", "fillerId" } ], "meta" } ],
      "domainRangeAxioms"?: [ { "predicateId", "domainClassIds", "rangeClassIds", "allValuesFromEdges": [edge] } ],
      "propertyChainAxioms"?: [ { "predicateId", "chainPredicateIds": [] } ] } ] }
Meta = { definition?: {val, xrefs}, comments?: [], subsets?: [], xrefs?: [{val}], synonyms?: [{pred: hasExactSynonym|hasBroadSynonym|hasNarrowSynonym|hasRelatedSynonym, val, synonymType?, xrefs}], basicPropertyValues?: [{pred, val}], version?, deprecated?: bool }
```

- Ids are full IRIs in GO's files (`http://purl.obolibrary.org/obo/GO_0000228`), CURIEs in the
  README examples; relation ids are IRIs (`http://purl.obolibrary.org/obo/BFO_0000050`), never
  the OBO shorthand.
- The README's edge key `subj` is outdated; the schema, the Java model and every file say
  `sub`. A reader should accept both (`subj` with `W_OBOGRAPH_LEGACY_KEY`).
- A document holds several graphs (`importAll()` per graph-io's rule; `import()` reads the
  first with `W_MULTIPLE_GRAPHS`).
- Nodes can lack `type` (obographs `nucleus.json`: subset and annotation-property IRIs) and
  `lbl` (go-basic.json: 3,683 nodes without a label, 3,646 of them the deprecated stand-ins the
  OWL conversion makes for every `alt_id`).
- Edge `meta` carries axiom annotations (`equivNodeSetTest.json`: comments, source).
- Release history: v0.1.0 (2017), v0.2.x (2020), v0.3.0 (2021), v0.3.1 (2023-11, `propertyType`
  added and unlabeled declared nodes kept), v0.3.2 (2025-08). Older files lack `propertyType`
  and may omit unlabeled nodes.

Measured pairs (OBO and obographs of the same release agree on edges): goslim_generic.obo 140
terms and 64 edges vs goslim_generic.json 211 nodes (140 CLASS + 71 PROPERTY) and 68 edges (64 +
3 subPropertyOf + 1 inverseOf); go-basic.obo 48,340 terms and 71,496 edges vs go-basic.json
52,048 nodes (48,340 terms + 3,646 alt_id stand-ins + 62 properties) and 71,498 edges (71,496 + 2
subPropertyOf).

### 8.2 Should graph-io read it, and how

Yes, as a JSON dialect (`dialect: "obographs"`): it is how the GO and every OBO Foundry ontology
publishes a ready-made graph, it is plain nodes and edges, and graphty-element users will meet
it beside the .obo file. Proposed mapping: every node -> node (id as given, `lbl` -> label role,
`type`, `propertyType` dict columns, `meta` -> `deprecated` bool, `definition` string, `synonyms`
json, `xrefs` / `subsets` / `comments` lists, `basicPropertyValues` json); every edge -> directed
edge with `pred` in a `relation` dict column and `meta` json; edge endpoints missing from `nodes`
-> placeholder nodes with `W_OBOGRAPH_DANGLING` (none measured in GO, but the schema does not
forbid it); the axiom arrays and graph `meta` -> `meta.extra.obographs`.

Sniffing change required: in `sniffJsonDialect()` the `graphs[]` test must look at the first
edge (or node) of the first graph: `sub` / `subj` + `obj` (or nodes with `lbl` / `type` in
CLASS|INDIVIDUAL|PROPERTY) -> `obographs`; `source` / `target` (or a nodes object map) -> `jgf`.
The head-scan path for truncated heads needs the same keys. Without it every obographs file is
silently read as JGF.

## 9. The independent reader for the conformance expectations

**Primary: fastobo-py 0.14.1** (MIT; Rust core fastobo 0.15.5). Reasons: a complete
implementation of the 1.4 BNF by a co-author of the specification; strict, so a file it reads
has an unambiguous parse; fast (go.obo, 48,351 frames, in 0.3 s); pip-installable like the
existing Python oracles; it also reads OBO Graphs JSON (`fastobo.load_graph`, which read
goslim_generic.json as 211 frames and abox.json as 22). Limits found: it rejects unknown tags,
1.2 synonyms without scope, unquoted qualifiers and per-xref qualifiers; it panics on comment
lines and Instance relationships; it keeps the space before a `!` comment. Expectations for those
cases come from ROBOT or from the spec text (`"oracle": "spec"`, citing the guide's
parser-requirements section).

**Second opinion: ROBOT 1.9.11** (BSD-3; owlapi's OBO parser, the 1.4 reference implementation;
needs Java 11+). `robot convert --input x.obo --output x.json` gives the OWL-mediated node and
edge sets. Use it for acceptance (does the reference parser read the file) and for edge counts on
the basic graph; do not use its graph as the expectation verbatim, because the OWL detour merges
duplicate axioms, drops qualified relationships (cardinality, all_only, gci) from `edges`, adds
alt_id stand-in nodes and Typedef nodes, and rewrites relation ids to IRIs.

Mapping the oracle applies (prototype: `tmp/samples-obo/scripts/oracle_obo_proto.py`): nodes =
Term and Instance frames merged by id, plus one placeholder per undeclared is_a / relationship
target; edges = is_a and relationship clauses, child -> target, identical clauses deduplicated
per merged frame; Typedefs = metadata; obsolete kept. Its counts are the "Expected" column in
section 10.

How to run (to become `graph-io/test/conformance/tools/oracle_obo.py`, called by `oracle.py obo`):

```bash
python3 -m venv tmp/obo-oracle && tmp/obo-oracle/bin/pip install fastobo==0.14.1
tmp/obo-oracle/bin/python tmp/samples-obo/scripts/oracle_obo_proto.py <file.obo> ...
# second opinion (portable JRE + robot.jar, both under tmp/samples-obo/tools/ here)
tools/jdk-17*/bin/java -jar tools/robot.jar convert --input <file.obo> --output <file.json>
# validation findings for a fixture's notes
tools/fastobo-validator --all <file.obo>
```

obonet 1.3.0 is useful only as a networkx-consistency check (it is what `networkx` users get);
pronto is not an oracle (it follows imports over the network by default and crashes on dangling
targets).

## 11. Decisions taken here (all reversible)

- Typedefs are metadata, not nodes (option to make them nodes).
- Obsolete terms kept with an `obsolete` column (option to drop).
- Dangling targets become placeholder nodes (the guide's recommended READ; option to drop).
- Only is_a and relationship are edges by default (OBO Basic and obographs agree); the logical
  axioms are columns, with an option to emit them as edges.
- Lenient reading of 1.0 / 1.2 constructs with warnings, never a fatal error for anything
  owlapi reads; fatal only for undecodable bytes and an empty input.
- Imports are never followed.
- obographs is a JSON dialect of the existing JSON importer, not a format of its own.
