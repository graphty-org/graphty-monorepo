# Style import: format research and prior art

Research behind `style-import-design.md`, which designs how graphty imports the colors, sizes,
shapes, labels and line styles stored in graph files. This document answers three questions:

1. How does each graph file format that graph-io reads store styles, and what does graph-io keep
   or drop today?
2. Is it true, as the starting hypothesis said, that formats store styles per node and per edge
   while graphty-element styles groups of elements through layers?
3. What prior art (academic work, algorithms, tools) helps turn per-element values back into a few
   group rules?

It is organized as one part per family of formats, then the prior art, then what graphty-element's
layer model can and cannot express. Each part was written as a separate study and can be read on
its own. The results of the prototype that tests the design are in `style-import-results.md`.

About the files and scripts named below: the measurements were made with research scripts and
downloaded files kept outside the repository, because several of the files carry no license or one
that forbids redistribution. File names such as `wild/gexf/...` name those downloads; the
appendix at the end lists each one with its URL, license and retrieval date (2026-10-11), so any
measurement can be repeated from the sources.

## How GEXF files carry styles

Research for importing the styles in graph files into graphty. This note covers GEXF, the XML
format of Gephi, with its "viz" visualization module. It answers four questions: what style
properties GEXF can express, how they are attached to nodes and edges, what graph-io reads and
drops today, and whether the owner's hypothesis holds that formats store styles per node and per
edge rather than per group.

Short answer: GEXF stores every style value on the element it applies to. It has no classes, no
selectors, no defaults for viz values, no inheritance and no style mappings. But the values in real
files are almost never arbitrary: in the files surveyed they are, in most cases, the output of a
data mapping the writing tool ran (Gephi's "partition" and "ranking"), and the mapping can be
recovered exactly from the file's own attributes and degrees. Where it cannot (random colors,
mappings over columns the file did not keep), a per-element style is still small to express: one
layer per style property that reads the imported value straight from the element's data.

Hypothesis verdict: storage is per node and per edge, always. Meaning is mostly group- or
data-level: of the 27 wild files with more than one node color, 17 are an exact function of one
attribute or of degree (5 of the other 10 are 2- or 3-node syntax samples or hand overrides); of
the 24 files with varying node sizes, 16 are an exact function of degree or one numeric attribute
(3 of the other 8 are 2-node samples). The worst real case (homestuck-viko.gexf, 374 nodes) has 281
distinct node colors and no attribute that explains them; grouping by distinct value there would
need about 295 layers, while one data-bound layer per property needs 3.

### 2. What GEXF can express

#### 2.1 The viz module

Styles live in a separate XML namespace, "viz", whose elements are children of `<node>` and
`<edge>`. The namespace URI changed with each version, and real files use all of them:
`http://www.gexf.net/1.1draft/viz`, `http://www.gexf.net/1.2draft/viz`, `http://gexf.net/1.3/viz`,
`http://www.gexf.net/1.3draft/viz` (the wiki's spelling), GEXF 1.0's `http://www.gephi.org/gexf/viz`,
mismatched pairs (a 1.2draft document declaring the 1.1draft viz namespace, as in
ogdf/color.gexf) and undeclared `viz:` prefixes in hand-written files.

| Element     | On         | Attributes                                                              | Schema constraints                                                                                   |
| ----------- | ---------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `color`     | node, edge | `r`, `g`, `b` (integer 0..255), `a` (float 0..1, from 1.2), `hex` (1.3) | 1.1 and 1.2: `r g b` required. 1.3: every attribute optional, `hex` is an unconstrained `xs:token`   |
| `size`      | node       | `value`                                                                 | float >= 0. "A scale. Set to 1.0 by default ... an object of size 2.0 is twice bigger as one of 1.0" |
| `thickness` | edge       | `value`                                                                 | float >= 0, a scale, default 1.0                                                                     |
| `shape`     | node       | `value`, `uri`                                                          | `disc` (default), `square`, `triangle`, `diamond`, `image`; `uri` locates the image                  |
| `shape`     | edge       | `value`                                                                 | `solid` (default), `dotted`, `dashed`, `double`                                                      |
| `position`  | node       | `x`, `y`, `z`                                                           | floats; `z` required before 1.3                                                                      |

The spec text for colors: "Colors are either defined by the RGBA color model or by an html-like hex
syntax ... hex value with or without the initial # symbol. In both cases an optional alpha value a
as a float from 0.0 to 1.0 can be added." Its own example, `hex="FF38AG"`, is not valid hex.

Units: none. Size and thickness are unitless relative scales; colors are sRGB bytes; alpha is a
0..1 float. Gephi writes its internal sizes as they are (10 to 100 is typical), so a size is only
meaningful relative to the other sizes in the same file.

#### 2.2 How a style value is attached

Only one mechanism: a viz element inside the element it styles. Specifically, GEXF has:

- no defaults for viz values: the `<default>` element exists only for data attributes
  (`<attributes><attribute><default>`), and the spec defaults (size 1.0, disc, solid) are reader
  conventions, not something a file can set;
- no classes, no selectors and no style sheet;
- no data-to-style mapping: a file records the result of a Gephi partition or ranking, not the
  partition or ranking itself (Gephi keeps those in its `.gephi` project file);
- no inheritance through the hierarchy: nested `<nodes>` and `pid` build parent nodes, and each
  parent carries its own viz like any node; none of the hierarchy fixtures carries viz;
- no graph-level styles: nothing for the background, labels in general, or edge defaults;
- no label styling: only the label text, as the `label` XML attribute;
- no arrow styling: arrows follow from the edge direction (`defaultedgetype`, per-edge `type`).

Time-varying styles exist only in 1.2: a viz element may carry `start` / `end` (or the open
variants), may be repeated with different bounds, or may hold a nested `<viz:spells>`. 1.3 removed
the time attributes from the viz schema. No fixture and no wild file uses any of it.

#### 2.3 Conventions outside the spec

Because GEXF has no defaults or label styles, some tools store them as ordinary data attributes:

- qvge (Qt Visual Graph Editor) declares node attributes `color`, `size`, `shape`, `label.color`,
  `stroke.color`, `stroke.size`, `stroke.style` with `<default>` values (`#55aaff`, 11, `disc`,
  ...) and writes viz elements only on the 4 of 64 nodes that differ from the defaults. That is a
  "defaults plus bypass" model encoded in the data, and the only class-level styling found in GEXF.
- CorText writes `color`, `size`, `shape`, `r`, `g`, `b` as data attributes beside the viz.
- graphology and sigma.js treat `color`, `size`, `x`, `y`, `label` as plain node attributes and
  write them to viz on export.

These are tool dialects; recognizing them would be a heuristic, not GEXF.

### 4. What graph-io parses today

The importer (`graph-io/src/formats/gexf/importer.ts`) reads the viz namespace in one streaming
pass into role columns with `origin.namespace "viz"`:

- node: `color` (f32 x4, rgba in 0..1, role color), `size` (f32, role size), `shape` (dict
  string, role shape), `shape.uri` (string), `position` (f32 x3, role position);
- edge: `color`, `thickness` (f32, role thickness), `shape`;
- the `label` XML attribute into the `label` role column on both.

Option `viz: false` skips the whole module with one W_GEXF_VIZ_SKIPPED warning. A value that does
not parse becomes W_GEXF_VIZ_VALUE and the element keeps no value; a viz element where the schema
allows none (`viz:thickness` on a node, `viz:size` or `viz:position` on an edge) is reported once
as W_UNKNOWN_ELEMENT. Shape values are stored verbatim, so values outside the enumeration never
fail. Every rule above was checked by importing all 147 files, plus two authored probe files
(`gexf/probes/`), from the current source with tsx.

No file threw because of a style. The import results, all style-related differences between the
viz elements in the file and the imported columns:

| File                                  | Lost                | Why                                                                                                                       |
| ------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| graphology/v1_3_writer.gexf (fixture) | 1 of 1 node colors  | `hex="#fff"` (3 digits)                                                                                                   |
| authored/rgba-hex-1.3.gexf (fixture)  | 1 of 2 node colors  | `#FF000080` (8 digits); the other node, with `hex` and `r g b`, gets the rgb value where Gephi and graphology use the hex |
| d3cryptor-g.gexf (wild)               | 2 of 3 node colors  | `<viz:color r="255"/>` and `<viz:color b="255"/>` (missing channels)                                                      |
| aoc-2023-25.gexf (wild)               | 16 of 16 node sizes | `value="NaN"`; also a non-spec `viz:position` on every edge                                                               |

Gaps found by the probes (`gexf/probes/probe-output.txt`), none of which throws:

1. Color forms dropped: `#rgb`, `#RRGGBBAA`, missing channels (valid in 1.3), CSS names.
2. `hex` next to `r g b`: graph-io prefers `r g b`, unlike Gephi and graphology.
3. No range checks: channels above 255, alpha above 1, negative size and thickness, and size
   `INF` are stored as they are. graphty's node size must be finite and non-negative, so these
   would surface downstream instead of as an import warning.
4. A repeated viz element in a static graph keeps the last value without a warning.
5. A nested `<viz:spells>` inside a viz element is skipped without any warning (only `start` /
   `end` attributes on the viz element itself raise W_GEXF_VIZ_DYNAMIC_DROPPED).
6. The `image` shape's `uri` is read, but graphty-element has no node image channel to receive it.

Not style, but found while checking that every file imports, and directly relevant to "every
valid input must import without error": the two Gephi CPAN datasets (GEXF 1.0) fail the whole
import with E_IMPORT, because GEXF 1.0 spells edge types `dir` and every edge counts against the
error limit of 100; and the Gephi diseasome dataset fails the same way on 1,419 `pid="0"` values
naming no node (the manifest already lists this as a known failure). The built `graph-io/dist`
on this machine is older than the source and fails more files; the results above are from the
source.

### 6. Testing the hypothesis: per element, or per group?

Storage is per element in every file, by construction. The question that matters for the layer
count is whether the per-element values hide a group or a data mapping. The survey script
(`gexf/analyze_gexf.py`) tests, for each file and property:

- partition: the style value is a function of one data attribute (every node with the same value
  of that attribute has the same style), with fewer attribute values than nodes;
- ranking: the style value is a linear function of a number (degree, in- or out-degree, weighted
  degree, or a numeric attribute), or a monotone function of it; for colors, each channel is
  monotone along the number (a Gephi gradient), or the color is a function of the number with few
  turns per channel (a 3-stop gradient, `gexf/probe_gradient.py`);
- edge colors against the endpoint colors (Gephi's source, target and mixed edge colors).

Gephi's own generator explains the shapes of these mappings. Ranking computes
`size = t * (max - min) + min` where `t` is the normalized value passed through an interpolator
(LINEAR, LOG2 = log2(1 + x), or a Bezier spline the user draws); ranking colors are a linear
gradient through 2 or more stops at chosen positions (default 3 stops, #EDF8FB, #66C2A4,
##006D2C). Partition assigns one palette color per category. The "monotone" sizes in the 2009
Gephi datasets fit neither LINEAR nor LOG2 (`gexf/probe_log2.py`: 8 to 25 percent maximum error),
which matches a hand-drawn spline: a monotone function of degree, recoverable only as a lookup.

#### 6.2 Fixtures

- The Gephi and graphology real datasets behave like the wild files (diseasome: 22 colors,
  partition on `disclass`; graphology les_miserables: color and size both functions of degree).
- The 15 networkx-generated fixtures with viz are the adversarial case: random colors and sizes,
  one distinct value per node (barabasi-albert: 15 nodes, 15 colors, 15 sizes). Nothing explains
  them, by construction.
- The rest are 1- or 2-node samples of syntax (hex, alpha, shapes, edge viz).

#### 6.3 Verdict

- Per node / per edge storage: true for every GEXF file, because the format offers nothing else.
- Per node / per edge meaning: mostly false. In the wild set, 17 of 27 files with varying node
  colors and 16 of 24 with varying node sizes are an exact function of one attribute or of degree:
  group-level (partition) or data-mapped (ranking) styling, flattened by the writer.
- Genuinely per-element styles exist: random or generator-assigned colors (networkx fixtures,
  homestuck-viko, Spark-TDA), and mappings over columns the file did not keep (sigma-arctic,
  french-ipr, the airlines sample). Grouping those by distinct value produces hundreds of layers
  for hundreds of nodes, the failure the owner described.
- Edge styles in GEXF are rare and, where present, constant in every wild file. Gephi never writes
  thickness (its edge thickness is the weight) and writes edge colors only for edges given their
  own color, so "no edge color" means "the reader's default rule" (Gephi draws by source, target or
  mixed node color, chosen in its preview settings, not in the file).

### 7. What this means for the design

These are observations for the design work that follows, not the design.

1. One data-bound layer per style property reproduces any GEXF file exactly with a bound
   independent of graph size. graph-io already puts each viz value in a per-element column, and
   graphty-element's binding grammar has a `passthrough` scale ("a column that already holds
   channel values -- a colour per node, a shape per node -- is passed through untouched",
   `graphty-element/src/session/styles/scales.ts`). A GEXF file has at most 6 viz properties (node
   color, size, shape; edge color, thickness, line style), so the bound is 6 layers plus what
   alpha needs. graph-io stores color as an rgba number vector while passthrough accepts a string
   or a number, so either side needs a color text form or a vector-aware path; that is a design
   question for the shared style format.
2. Recovering the generating mapping is a quality upgrade, not a requirement: it is exact when the
   tests in section 6 succeed, and gives an editable layer ("color by Modularity Class", "size by
   degree, linear from 10 to 50") that the reader can change. The binding grammar already has
   `ordinal` with a `map` (partition), `linear` with a domain and range (ranking), and palettes;
   a multi-stop gradient with custom stop colors and a Gephi spline (an arbitrary monotone
   function) would need a lookup `map` or the passthrough.
3. Value mapping decisions the design must make and report:
    - size and thickness are relative scales, so exact reproduction is up to one global factor per
      property; the factor should be stated in the import report;
    - alpha maps to opacity;
    - 2D shapes onto graphty's 3D shapes (`disc`, `square`, `triangle`, `diamond` have no exact
      equivalents), `image` (graphty-element has no node image channel), `double` (no line type),
      and non-enumeration values (`circle`, `hexagon`, ...) are approximations or drops that must
      be reported per value, with counts;
    - `dotted` and `dashed` map to graphty's `dot` and `dash` line types;
    - an absent edge color must stay absent (the reader's default rule), not become a color.
4. graph-io color parsing should accept every form a valid or common file carries before styles
   are built on it: `#rgb`, `#rrggbbaa`, missing channels as 0 in 1.3, `hex` preferred over
   `r g b` (matching Gephi and graphology), CSS names, and range-checked channels, alpha, size and
   thickness with a warning on every value it changes.
5. The two structural import failures (GEXF 1.0 `type="dir"`, and `pid` naming no node) break the
   "every valid input imports" requirement on official Gephi datasets, independent of styles.

## How GraphML files carry styles

GraphML itself has no style vocabulary. Every color, shape, size or line style in a GraphML
file comes from a convention layered on top of it, and there are six conventions in real use:
yEd's graphics extension, visone's wrapper around it, the newer yFiles 3 / yEd Live format,
Gephi's `r`/`g`/`b`/`size` keys, a handful of other plain-key conventions (SocNetV, Chilay, the
GraphML primer's own example), and the GraphML+SVG extension. This note describes each one: what
it can express, how a style is attached to elements, its value syntax, what graph-io keeps and
drops today, and how often real files use each mechanism. It ends with a verdict, per
convention, on whether styling is per node and per edge, by group, mapped from data, or a mix.

Everything measured here was produced by research scripts over the real files in `wild/graphml/`,
whose sources and licenses are listed in the appendix.

Hypothesis verdict: the owner's hypothesis holds for storage in every GraphML convention that
carries style: styles are written per node and per edge (only key defaults and yFiles 3 shared
objects are written once for many elements). It does NOT hold for the underlying structure:
the per-element values almost always encode a small number of groups.

- yEd: 1,424 nodes in 50 real files carry 360 distinct node styles (size excluded), at most 23
  in any one file; 1,124 edges carry 142 distinct edge styles, at most 18 per file. The largest
  diagram, 263 nodes, has 12 node styles; a 254-edge diagram has 1 edge style.
- yFiles 3: 620 nodes carry 94 distinct styles (at most 25 per file), 653 edges carry 61.
- Gephi and other plain-key files: 3,472 styled nodes carry 145 distinct colors and shapes (at
  most 21 per file). In 16 of the 17 files with more than one node color, the color is a
  function of one data attribute (`Modularity Class`, `Type`, `continent`, ...). In 10 of the 12
  Gephi files whose `size` has more than two values, size is an exact linear interpolation of one
  numeric attribute or of the node degree (largest residual 6e-6, which is float32 rounding).
- Sizes in yEd (`y:Geometry` width and height) are the exception: they are per element (yEd fits
  each box to its label), so they have no group structure at all.

So GraphML styling is per element in storage, group-shaped in content, and in Gephi files
data-mapped. Exact equality grouping recovers the groups for yEd, visone and yFiles 3; inverting
a partition (categorical) or a linear ranking (continuous) recovers Gephi's rules exactly.

### GraphML core

A `<key>` declares an attribute (`id`, `for`, `attr.name`, `attr.type`); a `<data key="...">`
inside a node, edge or graph gives that element its value. `for` is one of `all`, `graphml`,
`graph`, `node`, `edge`, `hyperedge`, `port`, `endpoint` (graphml-structure.xsd). `attr.type` is
`boolean`, `int`, `long`, `float`, `double` or `string`.

A key may hold one `<default>`. The primer: "There can be graph elements for which a
GraphML-Attribute is defined but no value is declared by a corresponding data element. If a
default value is defined for this GraphML-Attribute, then this default value is applied to the
graph element." This is the only group-level mechanism in GraphML itself: one value for every
element of a kind, overridden per element.

GraphML defines no style vocabulary. The primer's own attribute example is a node key named
`color` with `<default>yellow</default>` and per-node values `green`, `blue`, `red`; that file is
copied into six of our fixtures (primer, tulip, ogdf, graphology twice, igraph).

Structured content inside `<data>` is the official extension mechanism (primer section 4.2,
"Adding Complex Types"); its example puts SVG fragments in `<data>` and a default SVG in the
key's `<default>`. A key without `attr.type` that holds elements is therefore valid GraphML.

### yEd and yFiles for Java

#### Mechanism

A key with `yfiles.type="nodegraphics"` (or `edgegraphics`, `portgraphics`, `resources`) holds,
per element, one realizer element in the `y:` namespace. Every realizer is complete: yEd writes
every fill, border, label and geometry attribute on every element, so there is no default, no
class and no inheritance. In 1,424 nodes and 1,124 edges of real yEd files, no realizer lacked
its Fill, BorderStyle, LineStyle or Arrows child; only hand-written files (our `yed-classic`
fixture) omit them, and the schema does not say what an omitted one means.

yEd's Properties Mapper does create styles from data (map an attribute to a fill color, a
size, a shape), but its rules are saved to separate `.cnfx` files, not to the GraphML. The file
holds only the result, per element.

Group nodes (`y:ProxyAutoBoundsNode`) hold two realizers, an open and a closed `y:GroupNode`,
and `y:Realizers active="0|1"` picks the one shown. Nested `<graph>` elements give containment.

The only sharing is `<data key="resources"><y:Resources><y:Resource id="1">...` holding SVG
documents and images, referenced by `refid` from `y:SVGContent` and `y:Image`. This key is
declared `for="graphml"`.

#### Value syntax

- Colors are `#RRGGBB` or `#RRGGBBAA`, upper-case hex (schema pattern
  `#(([A-F]|[0-9]){2}){3,4}`). The fourth byte is ALPHA LAST: yEd's default group fill is
  `#CAECFF84`, a light blue at alpha 0x84, which only reads right as RRGGBBAA. 6 of the 54 files
  use 8-digit colors.
- "No fill" is written two ways: `hasColor="false"` (148 fills and 340 borders in real files) or
  `transparent="true"` (one fill, which also kept its `color`). Neither leaves the color absent
  in a way a reader can ignore: a reader that keeps `color` and ignores the flag paints a fill
  that yEd does not draw.
- Numbers are `xs:double` text; font size is an unsigned byte (points).
- Enumerations are wider in real files than in the published schema (shapes, arrows above), so
  every enumeration must be treated as open.

### visone

visone writes yEd realizers wrapped in its own elements: `visone:shapeNode > y:ShapeNode`,
`visone:bezierEdge > y:BezierEdge` plus `visone:edgeRealizerData > visone:line
style="continuous" width="1.0"`. Its root namespace is `http://graphml.graphdrawing.org/xmlns/graphml`
(not the GraphML namespace) and its keys use a non-standard `attr.default` attribute. Legend
templates (`Network_Node_Templates`, `Network_Edge_Templates`) are whole GraphML documents
escaped into a graph attribute; they are visone's own group-level styles, but they describe the
legend, not which elements use them. All four visone files have one node style and one edge
style.

### yFiles 3: yFiles for HTML, yEd Live

#### Mechanism

Keys are identified by `y:attr.uri`, not by `yfiles.type`:
`.../yfiles-common/2.0/NodeStyle`, `EdgeStyle`, `NodeLabels`, `EdgeLabels`, `NodeGeometry`,
`EdgeGeometry`, `PortStyle`, `UserTags`, `SharedData`, plus folding state (`Expanded`) and
`zOrder`. Values are XAML-like object graphs (namespace
`http://www.yworks.com/xml/yfiles-for-html/2.0/xaml` or `/3.0/xaml`, prefix `yjs`):
`yjs:ShapeNodeStyle fill="..." stroke="..." shape="ELLIPSE"`, `yjs:PolylineEdgeStyle` with
`stroke`, `sourceArrow`, `targetArrow`, `yjs:DefaultLabelStyle textFill textSize font`,
`yjs:Stroke fill thickness dashStyle lineCap`, `yjs:Arrow type`, gradients, and any third-party
style class (`uml:UMLNodeStyle`, `demostyle:FlowchartNodeStyle`, `GraphvizNodeStyle:GraphvizNodeStyle`,
`bpmn:*`, `icon-style:*`).

Sharing is explicit. Any object can be written once in `<data key="SharedData"><y:SharedData>`
with an `x:Key`, and referenced from any element either as an element
(`<y:GraphMLReference ResourceKey="1"/>`) or inside an attribute (`stroke="{y:GraphMLReference 5}"`).
`{x:Static y:VoidPortStyle.Instance}` names singletons. A key `<default>` may hold an object too.
Shared objects are groups by identity: two shared keys can hold equal objects (in one file the
37 edges reference 36 different shared keys that resolve to 2 distinct edge styles), so grouping
must compare resolved values, not keys.

Per-element content lives inside some style objects (a UML class's attributes and operations in
`UMLNodeStyle.model`, label text in `Label.Text`, label placement in `Label.LayoutParameter`);
these are content and placement, not style.

#### Value syntax

Colors in real files (fill, stroke, color, textFill, backgroundFill attributes):
`#AARRGGBB` 1,055 times, `#RRGGBB` 602, named constants 1,032 (`BLACK`, `WHITE`, `RED`, `SILVER`,
`WHITE_SMOKE`, `LIME`, `TRANSPARENT`, and mixed-case `Black`, `White`), shared references 562.
The 8-digit form is ALPHA FIRST (`#0039D000` is fully transparent, `#FF299600` is opaque
green), the opposite of yEd's `#RRGGBBAA`; a reader must decide by dialect, never by the
string. Enumerations are upper-case (`ELLIPSE`, `ROUND_RECTANGLE`, arrow `NONE`, `TRIANGLE`,
`SIMPLE`, `DIAMOND`, `CIRCLE`), except inside third-party styles (Graphviz shapes `ellipse`,
`box`). A `stroke` may be a bare color (thickness 1) or a `yjs:Stroke` object.

### Gephi

Gephi's GraphML exporter writes node keys `label`, `r`, `g`, `b` (int), `x`, `y` (float), `z`
when the layout is 3D, `size` (float) and edge keys `Edge Label`, `weight`; each node carries all of them. It writes no
edge color (the `r`/`g`/`b` keys are declared `for="node"`). Its importer maps, by key id or
title: `label`/`nodelabel`, `x`/`y`/`z` (and `xpos`...), `size`, `r`, `g`, `b`, `color` for
nodes and `label`/`edgelabel`, `weight`/`Edge Weight`, `r`, `g`, `b`, `color` for edges.
`color` text goes through `ImportUtils.parseColor`: a `java.awt.Color` field name, a name from
Gephi's color table, or `Color.decode` (`#RRGGBB`, `0xRRGGBB`, decimal).

The values are what Gephi's Appearance panel computed: a partition (one color per category of
an attribute) and a ranking (a value interpolated between a minimum and a maximum by a numeric
attribute). Measured on the 21 Gephi-style exports (14 with more than one color):

- Color is a function of one attribute in 13 of the 14: `Modularity Class` (9, 8, 14, 6, 6, 5,
  9 classes), `Type` (4), `sex` (2), `continent` (6), `Grado` (20), `scene` (28 values onto 21
  colors), and in one file `Degree` (9 values onto 9 colors: either a partition by degree or a
  color ranking, which the file cannot tell apart). The 14th (17 nodes, 3 colors) follows no
  stored attribute.
- In 10 of the 12 files whose `size` has more than two values, size is an exact min-max linear
  interpolation of one attribute: degree (LesMiserables, 4 to 100 over degree 1 to 36),
  `Betweenness Centrality`, `PageRank`, `Authority`, `Degree`. The largest residual against
  `minSize + (v - vmin) / (vmax - vmin) * (maxSize - minSize)` is 6e-6. The other two files'
  sizes follow no stored attribute (sizes set by hand or from a column Gephi did not export).

### Cytoscape

Cytoscape's GraphML writer (`graphml-impl/.../write/graphml/GraphMLWriter.java`) writes the
node and edge table columns (`name`, `shared name`, `selected`, `interaction`, ...) and nothing
from the view; its reader builds a view with the default layout. None of the 10 real Cytoscape
GraphML exports carries a style. One file named for Cytoscape (WikiNetworks) has hand-named
columns `Color`, `Border Width`, `Width`, `LineStyle`: data that looks like style, written by
another tool.

### Other plain-key conventions

- SocNetV: node keys `size`, `color`, `shape`, `label.color`, `label.size`, edge `color`, each
  with a `<default>` (`10`, `red`, `circle`, `#8d8d8d`, `8`, `#666666`) and per-node overrides.
  Key defaults are the base style; overrides are the exceptions.
- Chilay / iVis (Bilkent): node `color` as a space-separated triple (`"32 32 200"`), `shape`
  (`Rectangle`), `width`, `height`; edge `color`, `style` (`Solid`), `arrow` (`None`), `width`.
  Color is a function of `clusterID` (8 values).
- The primer `color` key: CSS-like names with a default (`yellow`), in six fixtures.
- networkx, igraph, graph-tool, TinkerPop, Neo4j APOC: no style convention; attributes only.
  networkx's reader treats any `<data>` with child elements as a yFiles extension and reads the
  label, geometry and shape (`GenericNode@configuration` or `Shape@type`) from ShapeNode,
  GenericNode, SVGNode and ImageNode, and the edge label from every yEd edge realizer.

Plain-key value forms seen: named colors (`yellow`, `Red`), `#rrggbb`, three integer keys
`r`/`g`/`b`, a space-separated triple, numeric sizes, capitalized shape and line names. Key names
are not standardized (`color`, `Color`, `colour`, `label.color`), so a style key is recognized
by convention, never by schema. Names alone mislead: `line` in a London Underground file is the
tube line, not a line style.

### GraphML+SVG

The primer's `svg.graphml` puts an `svg:svg` fragment in each node's and edge's `<data>` and a
default fragment in the node key's `<default>`. No real file in the sample uses it; yEd's SVGNode
is the practical equivalent.

### What graph-io keeps and drops today

What it keeps:

- Every typed key becomes a column, with its `<default>` as the column default; `label` keys
  get the label role. Plain style keys (`color`, `r`, `g`, `b`, `size`, `shape`) are imported as
  ordinary data columns; nothing treats them as style.
- A `yfiles.type` key's content is kept as a JSON tree column (origin namespace `yfiles`) and
  reported once as a loss (`W_GRAPHML_YFILES_JSON`).
- From a top-level `y:ShapeNode` it also writes typed columns `yfiles.position`, `.width`,
  `.height`, `.color`, `.borderColor`, `.borderWidth`, `.label`, `.shape`; from a top-level
  `y:PolyLineEdge`, `yfiles.color`, `.width`, `.directed`, `.targetArrow`, `.sourceArrow`.
  6-digit colors are upper-cased, 3-digit expanded, anything else kept as written.

Coverage of those typed columns on real files: 942 of 1,424 yEd nodes (66 percent) and 901 of
1,124 yEd edges (80 percent); 0 of 52 visone nodes and 33 edges (the wrapper hides the
realizer); 0 yFiles 3 elements.

What it drops or gets wrong (each confirmed by importing the real files with graph-io's source):

1. yFiles 3 files fail. Their keys have `y:attr.uri` and no `yfiles.type`, so they are read as
   untyped string keys, and every `<data>` holding a style, label list or geometry is reported as
   an error (`E_GRAPHML_DATA_NESTED`). 10 of the 16 real yFiles 3 files exceed the error limit of
   100 and the import throws `E_IMPORT`; the other 6 import with errors and lose every style,
   label and position. The two conformance fixtures of this dialect (`igraph/yfiles.graphml`,
   `igraph/graphml-yed.xml`) pass only because they are small. This breaks the requirement that
   every valid input imports without error.
2. Structured `<data>` under any key without `yfiles.type` is an error, including the primer's
   own SVG example (`primer/svg.graphml`: 2 errors, 1 warning). Primer section 4.2 makes it valid.
3. `for="graphml"` is reported as an error (`E_GRAPHML_KEY_FOR_INVALID`) in 53 of 54 yEd files;
   graphml-structure.xsd allows it. The resources it holds (SVG and image content) are dropped
   with a warning, so SVGNode and ImageNode lose their pictures.
4. Every node realizer other than ShapeNode is not mapped: GenericNode, SVGNode, ImageNode,
   UMLClassNode, GroupNode. They have the same Fill, BorderStyle, NodeLabel and Geometry children,
   but graph-io writes no typed column, so those 482 real nodes lose even their label text.
   networkx reads all four.
5. Every edge realizer other than PolyLineEdge is not mapped (Bezier, QuadCurve, Arc, Spline,
   Generic: 223 real edges).
6. `hasColor="false"` and `transparent="true"` are ignored. A fill with `hasColor="false"` gives
   no `yfiles.color`, so graphty paints its default fill where yEd paints none; a fill with
   `transparent="true"` and a color gives that color where yEd paints none.
7. Not mapped at all: edge labels, label font family, size, style and color, label visibility,
   several labels per element (only the first node label is kept), line and border type
   (dashed, dotted), gradient `color2`, drop shadow, group-node open/closed state.
8. 8-digit colors are kept as written; nothing records that yEd's are RRGGBBAA. A consumer that
   reads them as CSS gets the right answer by luck; one that treats them as yFiles 3 ARGB does not.
9. visone's wrapper hides the realizer (item 4's mapping looks only at the top level), and its
   `attr.default` is reported as an unknown attribute and ignored.

### Hypothesis per convention

| Convention            | Per node / per edge in storage?               | Underlying structure                                                                         | Evidence                                                                                          |
| --------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| GraphML core          | yes, plus key defaults                        | default plus exceptions                                                                      | primer, SocNetV                                                                                   |
| yEd / yFiles for Java | yes, always complete per element              | small number of exact-equality groups for every style property except size; size per element | 360 node styles in 1,424 nodes (at most 23 per file); 142 edge styles in 1,124 edges (at most 18) |
| visone                | yes                                           | one group per file                                                                           | 4 of 4 files                                                                                      |
| yFiles 3              | mixed: inline per element or shared reference | explicit shared groups, plus equal inline duplicates                                         | 94 node styles in 620 nodes, 61 edge styles in 653 edges                                          |
| Gephi                 | yes                                           | data-mapped: categorical on one attribute (color), linear range on one attribute (size)      | color 13 of 14 files, size 10 of 12                                                               |
| Other plain keys      | yes, plus defaults                            | default plus data-mapped categories                                                          | SocNetV, Chilay (clusterID), 16 of 17 plain files overall                                         |
| Cytoscape GraphML     | no style                                      | n/a                                                                                          | 10 of 10 files                                                                                    |
| GraphML+SVG           | yes, plus default                             | not seen in real files                                                                       | primer only                                                                                       |

Layer counts these structures imply (upper bounds, measured with every yEd style attribute
including label placement, so properties graphty cannot draw inflate them):

- One layer per distinct style combination: at most 23 node layers and 18 edge layers per real
  file; the ratio of layers to elements is 0.25 for yEd nodes and 0.13 for yEd edges, and falls
  as files grow (263 nodes, 12 styles; 254 edges, 1 style). Small diagrams are the worst case:
  an 8-node flowchart can have 7 styles.
- One layer per property value (a base layer plus one per other value): at most 33 node layers
  per yEd file.
- Gephi: one categorical color layer and one ranged size layer reproduce every file exactly;
  falling back to one layer per distinct color, the maximum is 21.
- Size (yEd geometry) and anything else with no group structure cannot be grouped; it needs one
  layer that reads a per-element value from a data column.

### Implications for the design (not decisions)

- Every GraphML style mechanism above must import without an error. That needs: `for="graphml"`
  accepted; structured `<data>` under an untyped key kept as a tree (never an error); yFiles 3
  keys recognized by `y:attr.uri` and kept as trees with their `SharedData`; enumerations
  treated as open, with an unknown value reported as a loss note.
- Color parsing depends on the dialect: yEd RRGGBBAA, yFiles 3 AARRGGBB plus named constants,
  Gephi Java names and `Color.decode`, Chilay triples, CSS-like names elsewhere.
- yEd and visone extraction can be uniform across realizers: Fill, BorderStyle, NodeLabel,
  Geometry, LineStyle, Arrows and EdgeLabel have the same shape in every realizer, with a
  realizer-specific shape source (`Shape@type`, GenericNode `configuration`, SVG resource).
- Group recovery by exact value equality is enough for yEd, visone and yFiles 3. Gephi and
  plain-key files reward a second step: find the data attribute that determines the color
  (functional dependency) and a numeric attribute the size is linear in, and emit a data mapping
  instead of one layer per value.
- Per-element values with no group structure (yEd sizes, positions, label text) belong in data
  columns, bound by one layer, never one layer per element.

## Styles in XGMML, CX, CX2 and Cytoscape session files: research

How the four Cytoscape-family formats that graph-io reads carry node, edge, label and network
styles; what graph-io keeps of them today; how often each mechanism occurs in the conformance
fixtures and in real files; and whether styling in each format is per element, group level,
mapped from data, or a mix.

Everything numeric below was measured by research scripts over the conformance
fixtures (`graph-io/test/conformance/fixtures/{xgmml,cx,cx2,cys}`) and over 34 real files
downloaded on 2026-10-11 (`wild/{ndex,xgmml,cys}`, listed in the appendix). Statements about Cytoscape's behavior come from its reader and writer source, cited
by URL.

The owner's hypothesis holds for XGMML, and for the per-element bypass layer of the other three.
It does not hold for CX, CX2 and sessions as a whole: they store Cytoscape's own style model
(defaults plus mappings keyed by an attribute), which is already group level. In those formats
the per-element part (bypasses) is small and, where it is large, it is one of three cases measured
in section 6: manual geometry (label offsets, bends, z order), pathway-diagram sizes that are
per-element by nature, or one constant value applied to many elements.

A second finding matters for the layer bound: every per-element value, whatever it is, can be
reproduced EXACTLY by one layer per property that binds the property to a per-element value
column (graph-io already writes CX and CX2 bypasses as such columns). That bounds the layers for
per-element styles at the number of style properties, independent of graph size. Mining groups
(section 6.2) then only has to win readability, not exactness.

### 2. The shared model: Cytoscape's visual style

All four formats serialize the same model, Cytoscape's visual lexicon and visual styles. Knowing
it once covers most of each format.

- **Visual properties** are named by id (`NODE_FILL_COLOR`, `EDGE_WIDTH`, `NETWORK_BACKGROUND_PAINT`)
  in a tree: `NODE_PAINT` is the parent of `NODE_FILL_COLOR`, `NODE_BORDER_PAINT`,
  `NODE_LABEL_COLOR` and `NODE_SELECTED_PAINT`; `NODE_SIZE` is the parent of `NODE_WIDTH`,
  `NODE_HEIGHT`, `NODE_DEPTH`; `EDGE_PAINT` of the edge colors
  (https://github.com/cytoscape/cytoscape-api/blob/develop/presentation-api/src/main/java/org/cytoscape/view/presentation/property/BasicVisualLexicon.java,
  `addVisualProperty` calls; the Ding renderer adds more in
  https://github.com/cytoscape/cytoscape-impl/blob/develop/ding-impl/ding-presentation-impl/src/main/java/org/cytoscape/ding/DVisualLexicon.java).
  A value set on a parent applies to children that have none of their own.
- **A style** is, per property: a default, at most one mapping, and style-wide dependencies.
  Mappings are PASSTHROUGH (the attribute's value, parsed as the property's type), DISCRETE (a
  lookup table keyed by the attribute value's string form; no match means the default) and
  CONTINUOUS (sorted breakpoints with lesser / equal / greater values; numbers interpolate linearly,
  colors interpolate in RGB, other types step; below the first point the `lesser` value, above the
  last the `greater` value, which may differ from the endpoint's value).
- **Dependencies** change what a property resolves to: `nodeSizeLocked` (NODE_SIZE drives width
  and height and the NODE_WIDTH / NODE_HEIGHT mappings are ignored), `arrowColorMatchesEdge`
  (arrow colors follow the edge stroke color), `nodeCustomGraphicsSizeSync`. In the session style
  files surveyed, `nodeSizeLocked` is true in 162 styles and false in 98; `arrowColorMatchesEdge`
  true in 50, false in 210.
- **A bypass** (Cytoscape "locked" value) sets one property on one element and overrides the
  mapping and the default. Resolution order: bypass, then mapping, then default, then the lexicon
  default.
- **Selection state** has its own properties (`NODE_SELECTED_PAINT`, `EDGE_STROKE_SELECTED_PAINT`,
  `NODE_SELECTED`, `EDGE_SELECTED`): an interaction style and state, not an appearance of the data.
- **Network properties** (`NETWORK_BACKGROUND_PAINT`, center, scale, title) are graph level.
- There are no classes and no selectors. A "group" of elements in a Cytoscape style is always
  defined by an attribute value (a discrete key, a continuous range). Cytoscape groups (compound
  nodes) and nested networks do not pass styles to their members; a group node has its own style
  like any node.

### 3. XGMML

#### 3.1 Properties and attachment

- **Draft (1.0) attributes on `<graphics>`**: `type` (shape), `fill`, `outline`, `w`, `h`, `d`,
  `width` (line width), `x y z`, `image`, `font`, `arrow`, `capstyle`, `joinstyle`, `smooth`,
  `stipple`, `visible`, `<center>`, `<Line><point>` (edge polyline). Per element only.
- **Cytoscape 3 export** (`GenericXGMMLWriter.writeGraphics`,
  https://github.com/cytoscape/cytoscape-impl/blob/develop/io-impl/impl/src/main/java/org/cytoscape/io/internal/write/xgmml/GenericXGMMLWriter.java):
  for every node, edge and the network, the writer walks every leaf visual property of the
  lexicon, takes `view.getVisualProperty(vp)` (the value the style, mappings and bypasses
  resolved to) and writes it: as an XGMML attribute where one exists (`fill`, `outline`, `w`, `h`,
  `type`, `width`), otherwise as a nested `<att name="NODE_LABEL_FONT_FACE" value="Dialog,plain,12"
type="string"/>`. The style itself (name, defaults, mappings) is not written.
- **Cytoscape reads it back as bypasses**: `GenericXGMMLReader.setVisualProperties` and
  `isLockedVisualProperty` set every graphics value as a locked (bypass) value except a node's
  `x`, `y`, `z` and the network center and zoom
  (https://github.com/cytoscape/cytoscape-impl/blob/develop/io-impl/impl/src/main/java/org/cytoscape/io/internal/read/xgmml/GenericXGMMLReader.java).
  Attribute aliases (`fill` is NODE_FILL_COLOR on a node and EDGE_STROKE_UNSELECTED_PAINT on an
  edge, `width` is NODE_BORDER_WIDTH on a node and EDGE_WIDTH on an edge, `type` is NODE_SHAPE,
  2.x names `nodeFillColor`, `edgeLineStyle`, `nodeHight` [sic]) are the `addIdentifierMapping`
  calls in BasicVisualLexicon. Three edge-label aliases are registered on the NODE class by
  mistake (`edgeLabelBackgroundShape`, `edgeLabelBackgroundColor`,
  `edgeLabelBackgroundTransparency`, lines 899 to 901), so Cytoscape itself never applies them to
  edges.
- **Cytoscape 2.x**: `cy:` attributes on `<graphics>` (`cy:nodeTransparency` 0.0 to 1.0, converted
  to 0..255 on read; `cy:nodeLabelFont` `Name-style-size`; `cy:sourceArrow` integers 0 to 17,
  converted by the `legacyArrowShapes` table to shapes, losing the WHITE/BLACK color part); 2.x
  documentVersion 1.0 wraps them in `<att name="cytoscapeNodeGraphicsAttributes">`.
- **Bypasses in 3.x**: `<att name="lockedVisualProperties" type="list">` inside `<graphics>`.
  Seen only in authored fixtures and session view files, never in the 15 real exports.
- **Styles hidden as data**: an R-generated 2.x file (fixture `ngscheckmate/test.out.xgmml`)
  writes the same style three times per node: `node.fillColor="255,0,0"` data atts,
  `vizmap:NGSCheckMate_graph NODE_FILL_COLOR="java.awt.Color[r=255,g=0,b=0]"` data atts, and
  `<graphics fill="#ff0000" type="ROUNDED_RECTANGLE">`, plus graph atts `backgroundColor`,
  `NODE_SIZE_LOCKED`. Only the `<graphics>` copy is authoritative for Cytoscape 3.
- **Graph level**: `<graphics>` on the root graph with `NETWORK_*` atts (3.x) or graph atts
  `backgroundColor`, `GRAPH_VIEW_ZOOM` (2.x).
- **Nested graphs and groups** do not inherit or pass styles.

#### 3.2 Value syntax

All values are strings. Colors `#RRGGBB` (upper or lower case; 48310 upper and 27254 lower case
color values counted, no `#RGB`, `rgb()` or names in any file, although Cytoscape's parser accepts
`r,g,b`, `rgb(...)`, decimal and CSS names), plus `r,g,b` and `java.awt.Color[r=..,g=..,b=..]` in
2.x data atts. Opacity is a separate `*_TRANSPARENCY` integer 0..255 (draft and 2.x: 0.0..1.0).
Fonts `Name,style,size` (`Dialog,plain,12`, `SansSerif.bold,bold,12`), the 2.x `Name-style-size`,
and a bare family (`Arial Black`, 13 values). Shapes upper case (`ELLIPSE`, `ROUND_RECTANGLE`),
but draft and 2.x files also write `rectangle`, `ROUNDED_RECTANGLE`, `oval`, `rhombus`, `circle`,
`box`, `roundrect`. Label positions `C,C,c,0.00,0.00`. Edge bends `cos,sin,ratio|...` (3.x) or
`x,y` handles (2.x), empty for straight. Custom graphics are Java class strings
(`org.cytoscape.cg.model.NullCustomGraphics,0,[ Remove Graphics ],`, `org.cytoscape.PieChart:{json}`,
`org.cytoscape.RadialGradient:{json}`), and 221 `NODE_CUSTOMPAINT_n` values are Java `toString`
output (`DefaultVisualizableVisualProperty(id=NODE_CUSTOMPAINT_1, ...)`) that is not a value at all.
2.x float noise: galFiltered.xgmml has `h="40.00048828125"` and `h="40.000732421875"` beside 329
nodes at `40.0`.

#### 3.3 What graph-io does today

The importer keeps `<graphics>` verbatim and interprets only positions: `x`, `y`, `z` (or
`<center>`) go to the position column (y flipped up); everything else, including nested Cytoscape
3 atts, `lockedVisualProperties` (as a nested object) and `<Line>` points, goes into one `json`
column `graphics` on the node, edge and graph tables (`graph-io/src/formats/xgmml/importer.ts`
header, `document.ts` `beginGraphics` / `graphicsAtt` / `attJson`, `emit.ts` `JsonColumn`). It
reports no style loss (nothing is lost, nothing is applied). `node.*` and `vizmap:*` style atts
are ordinary data columns.

### 4. CX (version 1)

#### 4.1 Properties and attachment

Aspect `cyVisualProperties` (old name `visualProperties`), spec
https://cytoscape.org/cx/specification/cytoscape-exchange-format-specification-(version-1)/ (dated
2022-01-11). Each element has `properties_of` (`network`, `nodes:default`, `edges:default`,
`nodes`, `edges`), `applies_to` (a view id for the first three, a node or edge id for the last
two), `view`, `properties` (property id to string), `dependencies` (string to string) and
`mappings` (property id to `{type, definition}`).

- `nodes:default` / `edges:default`: defaults (46 to 67 node, 21 to 33 edge properties in real
  files) plus mappings plus dependencies. Group and data level.
- `nodes` / `edges`: per-element bypasses.
- One set per view: a collection file with several views (`5views1network.cx`: 5 views, 348 node
  and 224 edge bypass entries for 81 nodes and 56 edges) carries several complete styles.
- Property ids and value strings are Cytoscape's lexicon (section 2), so CX shares XGMML's value
  syntax.
- Mapping definitions are one string: `COL=<column>,T=<type>` then `K=i=<key>,V=i=<value>`
  (discrete) or `L=i=,E=i=,G=i=,OV=i=` (continuous: lesser, equal, greater, breakpoint). A literal
  comma inside a key or value is doubled. Real examples:
  `COL=kind,T=string,K=0=a,,b,V=0=#FF0000` (authored),
  `V=0=S,,NW,,c,,0.00,,0.00` (a label position as a discrete value, NetPath map), and
  `COL=gene count,T=double,L=0=1,E=0=7,G=0=7,OV=0=7.0,L=1=30,E=1=30,G=1=1,OV=1=228.0` (font size:
  1 below 7 genes, 7 to 30 interpolated, and back to 1 above 228: the off-range values jump).
  5 of 236 definitions surveyed use the doubled comma.

#### 4.2 What graph-io does today

`readVisualProperties` (`graph-io/src/formats/cx/importer.ts`): for the graph's first view, each
`nodes` / `edges` bypass property becomes a nullable string column named after the property
(origin namespace `cx.bypass`), and `network` properties become string graph values. Defaults,
mappings, dependencies and table styles are kept verbatim in `meta.extra.cx` and reported with
one `W_STYLES_NOT_IMPORTED` warning that counts them. Bypasses of other views stay in
`meta.extra.cx`.

### 5. CX2

#### 5.1 Properties and attachment

Spec https://cytoscape.org/cx/cx2/specification/cytoscape-exchange-format-specification-(version-2)/
(dated 2025-07-22) and the property reference https://cytoscape.org/cx/cx2/cx2-visual-styles/.

- `visualProperties` (one element): `default.network`, `default.node`, `default.edge` (property
  to value), `nodeMapping` and `edgeMapping` (property to `{type, definition}`). PASSTHROUGH
  `{attribute, type?}`; DISCRETE `{attribute, type?, map: [{v, vp}]}` with `v` typed as the
  attribute (490 string, 141 integer, 3 boolean keys seen); CONTINUOUS `{attribute, type?, map:
[{min, includeMin, max, includeMax, minVPValue, maxVPValue}]}` where the first and last
  intervals are open (`min` or `max` absent: 46 such intervals seen). `type` is needed only when
  `attributeDeclarations` does not declare the attribute. The spec restricts `visualProperties`
  to "Cytoscape Portable Graphic Styles"; non-portable ones belong in an opaque
  `cyVisualProperties` aspect (seen in no file).
- `nodeBypasses` / `edgeBypasses`: `{id, v: {property: value}}`, precedence bypass over mapping
  over default.
- `visualEditorProperties`: `{properties: {nodeSizeLocked, arrowColorMatchesEdge,
nodeCustomGraphicsSizeSync, NETWORK_CENTER_X_LOCATION, ...}}` (the spec shows the keys without
  the `properties` wrapper; every real file has it).
- Portable names differ from the lexicon. NDEx's converter
  (https://github.com/ndexbio/ndex-object-model/blob/master/src/main/java/org/ndexbio/cx2/converter/CXToCX2VisualPropertyConverter.java)
  renames `NODE_FILL_COLOR` to `NODE_BACKGROUND_COLOR`, `NODE_TRANSPARENCY` (0..255) to
  `NODE_BACKGROUND_OPACITY` (0..1, divided by 255), `NODE_BORDER_PAINT` / `STROKE` /
  `TRANSPARENCY` to `NODE_BORDER_COLOR` / `STYLE` / `OPACITY`, `NODE_LABEL_WIDTH` to
  `NODE_LABEL_MAX_WIDTH`, `NODE_VISIBLE` to `NODE_VISIBILITY` (`element` / `none`),
  `EDGE_STROKE_UNSELECTED_PAINT` to `EDGE_LINE_COLOR`, `EDGE_LINE_TYPE` to `EDGE_LINE_STYLE`,
  `EDGE_TRANSPARENCY` to `EDGE_OPACITY`, the unselected arrow paints to `EDGE_*_ARROW_COLOR`,
  `EDGE_BEND` to `EDGE_CONTROL_POINTS`; it folds `nodeSizeLocked` (NODE_SIZE copied to width and
  height) and `arrowColorMatchesEdge` (EDGE_UNSELECTED_PAINT copied to the three edge colors) into
  the values.
- Composite values are JSON objects: `NODE_LABEL_FONT_FACE {FONT_FAMILY, FONT_STYLE, FONT_WEIGHT,
FONT_NAME?}`, `NODE_LABEL_POSITION {HORIZONTAL_ALIGN, HORIZONTAL_ANCHOR, VERTICAL_ALIGN,
VERTICAL_ANCHOR, MARGIN_X, MARGIN_Y, JUSTIFICATION}`, `NODE_IMAGE_<n>_SIZE {HEIGHT, WIDTH}`,
  `EDGE_CONTROL_POINTS [{cos, sin, ratio}]`, custom graphics `{type, name, properties}`.

#### 5.2 Value syntax: the spec's enumerations are not what files hold

The converter lower-cases any value it has no rule for, so real CX2 holds values outside the
published enumerations: line styles `equal_dash` (20), `parallel_lines`; arrows `cross_open_delta`,
`open_delta`, `open_circle`; WikiPathways shapes `nucleus`, `brace`, `mitochondria`,
`golgi apparatus`, `endoplasmic reticulum`, `sarcoplasmic reticulum`, `arc` (in discrete map
values). `COMPOUND_NODE_SHAPE` keeps upper case (`ROUND_RECTANGLE`, all 19 values) and so does
`NODE_LABEL_BACKGROUND_SHAPE` in 2 of 6. Some booleans and numbers are strings (`"EDGE_SELECTED":
"false"`, `"COMPOUND_NODE_PADDING": "10.0"`). Colors are `#RRGGBB` in either case.

#### 5.3 What graph-io does today

`readBypasses` (`graph-io/src/formats/cx2/importer.ts`): one column per bypass property (origin
namespace `cx2.bypass`), typed f64, bool, string or json by its values (a font or label position
object makes a json column). `visualProperties`, `visualEditorProperties` and the table-style
aspects are kept verbatim in `meta.extra.cx2.opaque` with one `W_STYLES_NOT_IMPORTED` warning.

### 6. Cytoscape session (.cys)

#### 6.1 Properties and attachment

Background: `design/graph-io/cytoscape-and-obo/research-session-and-style.md` section 4 (the
vizmap document structure, every property and value form). What matters here:

- `session_vizmap.xml` holds EVERY style of the session (17 to 37 in each real session; 374 in
  the 57 sessions read), not only the ones in use. Each view XGMML names its style in
  `cy:visualStyle`; of the 374 styles, 60 are used by a view. A session with several views can use several styles (fixture `subnetworks.cys`:
  4 views, 4 styles).
- Per style: `<network>`, `<node>`, `<edge>` sections with `<dependency>` and
  `<visualProperty name default>` plus at most one `passthroughMapping`, `discreteMapping` or
  `continuousMapping`. Table-column styles (3.9+, 12 seen) style the table panel, not the graph.
- View XGMML (`views/*.xgmml`): `<graphics x y z>` (unlocked values: positions) and
  `lockedVisualProperties` (bypasses). Cytoscape sets the unlocked ones as plain values that the
  style then replaces, and the locked ones as bypasses
  (https://github.com/cytoscape/cytoscape-impl/blob/develop/io-impl/impl/src/main/java/org/cytoscape/io/internal/read/xgmml/SessionXGMMLNetworkViewReader.java).
- 2.x sessions: `session_vizmap.props` (Java properties calculators) and network XGMML files whose
  `<graphics>` hold the resolved values, as in an XGMML export. Cytoscape IGNORES those standard
  graphics attributes when reading a session (`ReadDataManager.ignoreGraphicsAttribute`, "When
  reading XGMML as part of a CYS file, these graphics attributes should not be parsed",
  https://github.com/cytoscape/cytoscape-impl/blob/develop/io-impl/impl/src/main/java/org/cytoscape/io/internal/read/xgmml/handler/ReadDataManager.java);
  the style comes from `vizmap.props`.

#### 6.2 What graph-io does today

The importer reads the first view's positions and `graphics` json (from the view file, merged
onto the network's records) and records the view's style name; it detects
`session_vizmap.xml` / `.props` entries but does not read them (`W_STYLES_NOT_IMPORTED` names the
entries; `graph-io/src/formats/cys/importer.ts`, `session.ts`).

### 7. Measurements: is per-element styling reducible to groups?

#### 7.1 Method

`survey_cytoscape.py` reads every file with the Python standard library only (its own readers,
independent of graph-io), collects each element's data attributes and its per-element style
values (XGMML `<graphics>`; CX, CX2 and session bypasses), and for every style property that
varies across elements asks:

1. **Passthrough**: is there a data column whose value equals the style value on every element?
2. **Discrete**: is the style value a function of one data column (a column that is unique per
   element does not count)? The key count is the size of the lookup table.
3. **Continuous**: is the style value (a color as an RGB vector or a number) a piecewise-linear
   function of one numeric column? The fit is greedy with a tolerance of one unit per color
   channel or per integer step (Cytoscape rounds or truncates interpolated values) or 0.1 percent
   of the range for real numbers; elements without the column may share one value (the default).
   More than 12 segments is rejected as not a mapping anyone drew.
4. Otherwise the property is **unexplained**.

Geometry and state (`x y z`, `NODE_X/Y/Z_LOCATION`, `EDGE_BEND`, `EDGE_CONTROL_POINTS`,
`NODE_SELECTED`, `EDGE_SELECTED`) are counted apart: they vary per element by nature and are not
group styles.

Four layer counts are reported per file and element kind:

- **tuple**: one layer per explained property, plus one layer per distinct COMBINATION of the
  unexplained properties' values (elements styled alike share a layer);
- **perProp**: as tuple, but unexplained properties grouped one property at a time;
- **column**: one layer per varying property, each bound to a per-element value column (exact by
  construction);
- and the distinct-tuple count of ALL style values, which is what naive grouping by identical
  style would produce.

#### 7.3 What the numbers say

- Where a format writes resolved values per element (XGMML), the values come from a handful of
  group rules, and the rules are recoverable: passthrough, discrete and piecewise-linear fits on
  single columns explained every varying property of every real export of more than 7 elements.
- Where a format writes rules (CX, CX2, sessions), use the rules. The rules plus bypasses are a
  complete description; mining is needed only for bypasses.
- Where per-element values are genuinely per element (manual label offsets, diagram sizes,
  pathway anchors, hand edits), grouping by identical value can still need tens of layers (50 for
  50 label offsets, 42 for an 81-node hand-styled diagram). Binding the property to a per-element
  value column keeps it at one layer per property and is exact, so the layer count is bounded by
  the number of style properties (at most about 20 node and 15 edge properties graphty could
  draw), not by graph size.

### 8. Hazards a style importer must survive (seen in real files)

Every item below occurs in a fixture or a real file; none may throw.

1. Values outside every published enumeration (CX2 `equal_dash`, `nucleus`, `brace`,
   `cross_open_delta`), mixed case (`ROUND_RECTANGLE` in CX2, `rectangle` in XGMML), legacy names
   (`ROUNDED_RECTANGLE`, `roundrect`, `oval`, `rhombus`, `box`).
2. Non-values: Java `toString` text in `NODE_CUSTOMPAINT_n` (221), `java.awt.Color[r=..]` in data
   atts, empty strings for "straight" bends and empty tooltips.
3. Strings where JSON types are expected (`"false"`, `"10.0"`) and JSON objects where strings are
   expected (fonts, label positions as objects in CX2, as `C,C,c,0.00,0.00` strings in CX).
4. Several color forms: `#RRGGBB` both cases, `r,g,b`, and the forms Cytoscape's parser accepts
   but no surveyed file used (`rgb()`, decimal, CSS names).
5. Two opacity scales: 0..255 (`*_TRANSPARENCY`, lexicon) and 0..1 (CX2 `*_OPACITY`, draft and 2.x
   `nodeTransparency`).
6. Float noise in resolved values (`40.00048828125` for 40.0): compare with a tolerance and snap
   before grouping.
7. Continuous mappings whose off-range values jump (`G=1=1` after a breakpoint at 228), equal
   breakpoints, single points, open-ended CX2 intervals, empty mappings.
8. Mappings naming an attribute no element has, or one stored under an alias (`name` as `n`).
9. Discrete keys typed differently from the column (CX2 integer keys; vizmap keys are Java
   `toString` forms, so `1.0` does not match `1`).
10. CX1 definition strings with doubled commas inside keys and values.
11. Dependencies that change resolution (`nodeSizeLocked`, `arrowColorMatchesEdge`) and parent
    properties in the lexicon tree (`NODE_PAINT` for `NODE_FILL_COLOR`).
12. Several views, each with its own style and bypasses (CX collections, sessions); unused styles
    (most of a session's styles); styles for elements of another view.
13. The same style written in several places in one file (2.x R output: data atts, vizmap atts and
    graphics), only one of which Cytoscape honors.
14. Properties that are geometry or state, not appearance (z order, bends, label offsets,
    `NODE_SELECTED`, visibility used to hide elements).
15. Cytoscape-only rendering (custom graphics, charts, gradients, label backgrounds, compound
    padding, edge stacking, selection paints): report as not drawn, never fail on.

## How DOT, GML, Pajek and JSON graph files carry styles

Research for importing the styles of graph files into graphty. This note covers four format
families: DOT (Graphviz), GML, Pajek NET / PAJ, and the JSON dialects graph-io reads (NetworkX
node-link, d3, Cytoscape.js, graphology / sigma / Gephi JSON, vis.js, JSON Graph Format). For each
it lists what style properties the format can express, how a style is attached to a node or edge,
the value syntax, what graph-io keeps and drops today, and how often real files use each
mechanism. It then tests the hypothesis that these formats style nodes and edges one element at a
time, and closes with what the findings mean for turning file styles into a small number of
graphty-element style layers.

Evidence comes from three places: the official specifications and manuals, the graph-io
conformance fixtures (196 DOT, 108 GML, 114 Pajek, 109 JSON files), and 54 real files downloaded
from public repositories (15 DOT, 13 GML, 15 Pajek, 11 JSON data files plus 7 Cytoscape
stylesheets). Every count below was produced by research scripts. DOT values were resolved by Graphviz 2.43 itself
(`gvpr`), so they are the values Graphviz draws, not a guess at its inheritance rules.

**The hypothesis holds for the files as written, but not for the information in them.** In every
format, real files overwhelmingly carry styles one element at a time. But:

1. **The number of distinct values is almost always small.** Of 50 DOT element sets with 40 or
   more elements, 36 have at most 10 distinct style combinations; 6 have more combinations than half
   their elements. GML files written by tools repeat the same `graphics` record on every element
   (one distinct combination in 8 of 22 element sets).
2. **Many per-element styles are data mappings that were baked in.** In Gephi exports the color is
   exactly a function of one node attribute (`ModularityClass`, `Country`) and the size is exactly a
   function of `Degree` or a centrality; in a Gephi JSON export every one of 9,228 edge colors is
   the mean of its two endpoint colors. These can be recovered exactly as one rule each.
3. **Some formats do carry group-level styles, and graph-io flattens them away today**: DOT
   defaults and clusters, Pajek partitions, Cytoscape.js stylesheets, vis groups.
4. **A few files are truly per element** (a style value computed from data that is not in the file):
   878 distinct edge pen widths for 878 edges in a NEAT network drawing, 123 for 125 in a weighted
   DOT file. These need a binding that reads the value straight from the element's own column, never
   one layer per value.

So a layer count that does not grow with the graph is achievable for every file seen: at most one
layer per style property per element kind (literal or passthrough binding), plus one per real
group or data mapping found. The widest real file (a yEd GML export) has 14 node and 11 edge style
properties.

#### How a style is attached

- **Per element**: `a [color=red]`, `a -> b [penwidth=2]`.
- **Defaults**: `node [..]`, `edge [..]`, `graph [..]` and `ID = ID` statements. The language
  reference (https://graphviz.org/doc/info/lang.html) says an object of the right kind defined
  afterwards inherits the value; objects created before a default is set get an empty string for
  it. Verified with Graphviz: in `a; node [color=red]; b` only `b` is red.
- **Subgraph scope**: a subgraph starts with its parent's defaults at the point it opens, and its
  own `node [..]` statements apply only to nodes CREATED inside it. A node created earlier and
  mentioned again inside the subgraph keeps its old values (verified with gvpr).
- **Clusters**: a subgraph named `cluster*` (or with `cluster=true`) is drawn as a box; its
  `graph`-level attributes (`label`, `color`, `style=filled`, `fillcolor`...) style the box, and its
  `node [..]` defaults style its members. A cluster is the one real group DOT has.
- **Color schemes**: `colorscheme=spectral7` plus `fillcolor=4` picks the 4th color of a Brewer
  palette; `/blues9/3` names a scheme inline. A palette index is meaningless without its scheme.
- **Edge-level inheritance from graph attributes**: none beyond defaults.

#### Value syntax

- Colors (https://graphviz.org/docs/attr-types/color/): `#RRGGBB`, `#RGB`, `#RRGGBBAA`, HSV(A)
  as three or four numbers in 0..1 separated by spaces or commas, a name in the current scheme
  (X11 by default), `/scheme/name`, `transparent`, and color lists `red:blue` or `red;0.3:blue` for
  gradients, striped or wedged fills and parallel multi-colored edges. **X11 names are not CSS
  names**: Graphviz draws X11 `gray` as #C0C0C0, `green` as #00FF00 and `maroon` as #B03060, while
  CSS has #808080, #008000 and #800000 (checked with `dot -Txdot`). Resolving a DOT color through a
  CSS parser is wrong for these names. (Graphviz's own SVG output writes the bare name, so a browser
  then shows the CSS color: Graphviz is inconsistent with itself here.)
- `style` is a comma list of items, some with arguments (`setlinewidth(2)`, deprecated). Unknown
  items are passed to the output driver, so files contain items Graphviz itself ignores.
- arrowType is a grammar, not an enumeration: up to four arrows concatenated, each an optional
  `o` (open) and `l` / `r` (half) modifier on a primitive (box, crow, curve, icurve, diamond, dot,
  inv, none, normal, tee, vee), plus legacy names (ediamond, open, halfopen, empty, invempty);
  `normalnoneodiamond` occurs in the fixtures
  (https://graphviz.org/docs/attr-types/arrowType/).
- Units: `width` / `height` in inches, `penwidth` and `fontsize` in points, `arrowsize` a factor.

#### What graph-io does today

`graph-io/src/formats/dot/importer.ts` applies node and edge defaults as Graphviz does and writes
every element's effective attributes as plain columns (one column per attribute name; `label` with
the label role, `pos` as the position). A comparison of graph-io's per-element values with
Graphviz's resolved values over every importable fixture and real file: 38,179 element-attribute
values, 166 differences, all of them HTML-label spelling (graph-io keeps the `<...>` delimiters so
an HTML label stays distinguishable), parallel-edge pairing in the comparison script, and two
cluster-name merges. So the flattened columns are a faithful per-element input.

What is lost: which values came from a default or a cluster, i.e. the group structure the author
wrote. Cluster attributes land on the cluster's container node (`graphty.cluster`), members get
`graphty.parent`. Attributes of a non-cluster subgraph are dropped with
W_DOT_SUBGRAPH_ATTRIBUTES_DROPPED (they are only defaults for nodes created inside, which graph-io
does apply, so only `rank=same` and similar layout hints are really lost). No column gets a viz role
(`color`, `size`, `shape`, `thickness` roles exist in graph-format but the DOT importer does not
assign them), and the exporter declares `viz: false`.

Only per element. The spec has no default values for graphics beyond "0, 0.0, empty string, empty

has a `graphics` record on the graph. A key starting with a capital letter is "unsafe" (to be
dropped when the graph changes), so `LabelGraphics` and `Line` are formally unsafe.

#### Value syntax

Colors are `"#RRGGBB"` strings in every file seen (yEd also writes `#RRGGBBAA` in newer versions).
Shapes are free strings whose vocabulary depends on the writer (`oval` and `ellipse` both appear).

integers (`target_arrow 3` means an edge-colored delta). Writers break the grammar: Gephi writes
`Creator Gephi` unquoted, OGDF escapes quotes inside strings with a backslash, yEd writes labels
with raw newlines and CRLF.

#### What graph-io does today

Node `graphics` x / y / z become the position; everything else in node `graphics`, all of
`LabelGraphics` and all of edge `graphics` are kept as JSON columns (`graphics`, `LabelGraphics`)
without interpretation. Nothing is dropped, nothing is mapped to a viz role.

#### How a style is attached

- **Per element**: the parameters on each vertex or line ("Default values can be changed for each
  vertex in definition line"). The manual does not say whether a parameter carries over to
  following lines; igraph, NetworkX and graph-io all read it as belonging to that line only. Real
  files written by Pajek set parameters on some vertices and leave others bare (B02.net: 47 of 80).
- **Partitions** (`*Partition` in a project file `.paj`): a class number per vertex. Pajek's Draw
  window colors vertices by partition with a fixed 40-color palette (manual Figure 20: 0 Cyan,
  1 Yellow, 2 LimeGreen, 3 Red, 4 Blue, ...), and "partition colors will overwrite the specified
  interior color". This is a real group-level, data-mapped mechanism; the palette is Pajek's, not
  the file's.
- **Vectors** (`*Vector`): a number per vertex that the Draw window can use as the vertex size.

#### Value syntax

Colors are names from Pajek's list of 96 (manual Figure 19: the 68 dvips "Crayola" CMYK names such
as GreenYellow, Dandelion, CadetBlue, defined as in LaTeX's `dvipsnam.def`, plus LightYellow,
LightCyan, Pink, LSkyBlue, LFadedGreen, Canary, Gray05..Gray95), case sensitive, or `RGBFF0000`,
`RGB(1,0,0)`, `CMYK00FF0000`, `CMYK(0,1,0,0)` with no spaces. Pajek `Green` is CMYK(1,0,1,0), #00FF00, not
CSS green #008000. Coordinates are in 0..1; `x_fact` multiplies
a default size; widths are in PostScript points.

#### What graph-io does today

Parameters become per-element columns under their Pajek names (`ic`, `bc`, `x_fact`, `c`, `w`...),
typed by the shared cell grammar (so `x_fact 2` is i32 and `ic Red` a string); the shape keyword
goes to `shape`; `*Partition` and `*Vector` become `partition` / `vector` columns (a second one
`partition#2`), losing the partition's name (`World_system_1980`, `Continent`). igraph's reader is
prior art for naming: it renames `ic` to `color`, `bc` to `framecolor`, `x_fact` to `xfact`, `c` to
`color`, `w` to `edgewidth`, `p` to `linepattern`.

#### How often each mechanism is used

Fixtures: 9 of 114 files carry parameters (`ic` in 8, `x_fact` / `y_fact` in 7, `bc` 1, edge
parameters in 1); the shape keyword appears in 36 files, only 9 with anything but `ellipse` (the
NetworkX and Pajek writers put `ellipse` on every vertex); 7 carry a partition, 6 a vector.

Real files (15): 12 carry a shape keyword or parameters, 2 project files carry partitions (4 in all). Distinct values stay small: MIT.NET 93 styled vertices with
31 combinations (12 interior colors, 4 boundary colors, 3 shapes, 3 sizes); B02.net 6 vertex and 6
edge combinations; B96.NET 9; kidscontest.net 3; radical-pictographic.net 2. The one wide case is
A02.net, where `x_fact` takes 21 values on 23 vertices (a size per vertex). world_trade.paj carries
3 partitions and 3 vectors.

#### Hypothesis verdict for Pajek

A mix: parameters are per element; partitions are group-level and data-mapped. graph-io keeps the
partition numbers but nothing records that Pajek draws them as colors.

### JSON dialects

#### Cytoscape.js

- **Properties**: the full Cytoscape.js style vocabulary (`background-color`, `border-color`,
  `border-width`, `shape`, `width`, `height`, `label`, `color`, `font-size`, `text-valign`,
  `line-color`, `line-style`, `target-arrow-shape`, `target-arrow-color`, `curve-style`,
  `opacity`, `z-index`, `background-image`...).
- **Attachment** (https://js.cytoscape.org/): a stylesheet of `{selector, style}` rules (older
  files use `css` instead of `style`) applied in order, later rules winning; selectors by group
  (`node`, `edge`), class (`.highlighted`), id (`#n1`), data (`[weight > 50]`, `[?flag]`,
  `[name = 'x']`) and state (`:selected`); values are literals, `data(attr)` (the element's own
  value) or `mapData(attr, lo, hi, a, b)` (linear). Elements carry `classes`. An element's own
  `style` field is a bypass that beats the stylesheet; the docs say "DO NOT USE THE style FIELD
  UNLESS ABSOLUTELY NECESSARY".
- **This is the closest format to graphty's layers**: a rule is a layer, a selector is a layer
  selector, `data()` is a passthrough binding, `mapData()` a linear one.
- **But per-element rules appear inside stylesheets too.** The `network-images.json` fixture styles
  each node with its own `#n1`, `#n2`... rule. Cytoscape desktop's style export writes a discrete
  mapping as one rule per value: a real export (scIDseq `styles.json`) holds 107 rules of the form
  `node[name = 'ITGB1']`, one per node, each setting `border-opacity`. Rules that share a property
  set and differ only in the value of one attribute must be re-collapsed into one lookup binding,
  or the 107 rules become 107 layers.
- **Rule counts**: 21 stylesheets in 7 real files (Cytoscape desktop exports and cytoscape.js demos),
  2 to 111 rules each; selectors 43 group, 374 data comparisons, 37 state, 6 class; values 961
  literals, 28 `data()`, 20 `mapData()`.
- **graph-io today**: elements, `classes` (role classes) and the element `style` bypass (JSON column
  `style#element`) are read; the top-level stylesheet is kept verbatim in
  `meta.extra.json.cytoscape.style` and not interpreted. Two fixtures carry a stylesheet; the
  cytoscape.js demos keep theirs beside the data (`cy-style.json`, `.cycss`, or code), so a data file
  alone often has no style at all.
- **Verdict**: group-level and data-mapped by design, with per-element escape hatches.

#### graphology, sigma and Gephi JSON

- **Properties**: sigma reads `x`, `y`, `size`, `color`, `label`, `hidden`, `forceLabel`, `zIndex`,
  `type` on nodes and `size`, `color`, `label`, `hidden`, `type` on edges (sigma `types.ts`,
  `NodeDisplayData` / `EdgeDisplayData`); anything else is computed in code with node and edge
  reducers, never stored.
- **Attachment**: per element only. Gephi's JSON exporter writes `color: "rgb(r,g,b)"` and `size`
  on every node and edge after its partition and ranking passes.
- **Recovered mappings** in real Gephi output:
    - WorldCup2014.json (736 nodes, 9,228 edges): node color has 30 values and is exactly a function
      of `Modularity Class` (and of `Country`); node size has 16 values, exactly a function of
      `Degree`; every edge color equals the mean of its two endpoint colors (Gephi's "mixed" edge
      color mode), 9,228 of 9,228.
    - eurosis.json (1,285 nodes): color has 13 values, a function of `country`; size has 49 values.
- **graph-io today**: graphology files read fine (`color`, `size` columns). Gephi's JSON export
  shape (`nodes` with `id`, `attributes`, `color`, `size`) is misread as graphology and the import
  fails (E_MISSING_ID on every node); the fixture `sigma/clique3.json` records the same known
  failure.
- **Verdict**: per element as written, data-mapped in origin.

#### vis.js

- **Properties** (https://visjs.github.io/vis-network/docs/network/nodes.html, .../edges.html):
  node `color` (string, or `{background, border, highlight, hover}`), `shape` (ellipse, circle,
  database, box, text, image, circularImage, diamond, dot, star, triangle, triangleDown, hexagon,
  square, icon, custom), `size`, `borderWidth`, `font` (`"14px arial red"` or an object),
  `opacity`, `image`, `shapeProperties.borderDashes`, `hidden`; edge `arrows` (`"to, from"` or an
  object), `color` (with `inherit: from | to | both`), `dashes`, `width`, `smooth`.
- **Attachment**: per element, plus `group` on a node with `options.groups` defining each group's
  options. Precedence: node options beat group options beat global options. Unknown groups get a
  default palette in rotation (`useDefaultGroups`). Edge `color.inherit` takes the color from the
  `from` node's border, the `to` node, or a gradient of both.
- **graph-io today**: node and edge keys become columns (`color` objects as JSON); `options` and
  `groups` are reported with W_JSON_UNREAD_KEY and dropped. The fixture `vis/network.json` records
  that `x` / `y` are not mapped to the position.
- **Real use**: vis-network's own DOT converter (`lib/network/dotparser.js`) writes per-element
  `color`, `shape`, `font`, `width`, `height` from DOT attributes (a 213-node conversion with
  per-node font objects). Groups live in application code, not in data files.
- **Verdict**: per element in files; group-level only in code.

#### d3, NetworkX node-link, JSON Graph Format

- d3 examples (`miserables.json`) carry `group` on nodes and `value` on links; the color comes from
  `d3.scaleOrdinal(d3.schemeCategory10)` in code. The data mapping is real but the palette is not in
  the file, so an importer cannot reproduce a specific drawing; it can only see that `group` is a
  categorical attribute.
- NetworkX node-link and JGF have no style vocabulary; a `color` or `size` key is whatever the user
  wrote. No fixture carries one.
- **Verdict**: no styles, or per element by user convention.

### What the findings mean for the design

1. **Bound the layer count by properties, not by values.** For every file seen, one layer per style
   property per element kind is enough to reproduce the file exactly, by binding the property to the
   element's own value (a passthrough binding over a column). graphty-element already has
   `by: <path>` bindings with a `passthrough` scale (`graphty-element/src/session/styles/encoding.ts`).
   The widest real file has 14 node and 11 edge style properties. One layer per distinct combination
   is not acceptable: it reaches 878 on a real file.
2. **Look for the hidden rule before falling back to passthrough.** A functional-dependency test
   (does attribute A determine style S, with fewer values of A than elements?) found the real
   mapping in every Gephi file and in the Linux kernel diagram. A rule over `ModularityClass` is one
   layer with a meaningful legend; a passthrough over the color column is one layer with no meaning.
   Also test structural rules: an edge color equal to its source, its target, or the mean of both
   (exact in the Gephi JSON export; vis `color.inherit` says it explicitly).
3. **Keep the group structure the file already has.** DOT defaults and clusters, Pajek partitions,
   vis groups and Cytoscape.js stylesheets are group-level styles that graph-io flattens or ignores
   today. An importer that records where a value came from (this cluster's `node [..]`, that root
   default) can emit the author's own groups instead of inferring them.
4. **Re-collapse degenerate rule lists.** Stylesheets written by tools (Cytoscape desktop's one rule
   per discrete value, `#id` rules) must be merged into one lookup per attribute before they become
   layers.
5. **Resolve colors in the right namespace.** DOT names are X11 (or a Brewer scheme with an index),
   Pajek names are dvips CMYK, CSS names are CSS; the same word differs in value. Color lists and
   gradients (`red:blue`) need a fallback (first color) plus a loss note.
6. **Normalize units per format**: DOT inches and points, GML drawing units, Pajek size factors and
   0..1 coordinates, Cytoscape.js pixels.
7. **Report rather than throw.** Invalid values occur in real files (`shape=rounded` on 108 nodes,
   style `invisible`, unknown arrow names, Cytoscape integer arrow codes): each must become a loss
   note with a count.

### Prior art in converters

Every converter found flattens to per-element styles and none recovers groups:
Cytoscape's GML reader sets each `graphics` key as a per-node locked value (bypass) and maps yEd and
legacy integer arrow names (`GMLNetworkReader.java`); vis-network's DOT parser copies DOT attributes
onto each vis node and edge through a small mapping table (`color` to `color.border` and
`color.background`, `style` to `dashes`); igraph's Pajek reader renames parameters to attribute
names. Gephi computes styles from partitions and rankings and then writes the results per element,
which is why its output is the easiest to reverse.

## Prior art: turning per-element styles into a few group rules

Date: 2026-10-11. Research for the design of style import in graph-io. Plain prose; every claim
about outside work cites a URL in "Sources" at the end of this part. Prototype code and raw output were kept outside the
repository.

### Bottom line

1. **Nobody has solved "per-node styles to group rules" for graph files.** Cytoscape, Gephi and
   yEd all go one way only: rules to per-element values. Gephi's own users report that a GEXF
   file cannot say "color comes from this column", and Cytoscape has no command that turns
   bypasses (per-element overrides) back into a mapping. The closest real prior art is from
   chart reverse engineering (Harper and Agrawala's D3 deconstructor, which tests each data
   field against each mark attribute for a linear or a one-to-one categorical mapping) and from
   database theory (functional dependency discovery, which decides "column X determines
   column Y" exactly and in linear time with partitions).
2. **The passthrough observation holds, with conditions.** One layer per channel whose binding
   reads the value straight from a data column reproduces any per-element style exactly, so
   the layer count is bounded by the number of channels (about 35 in graphty-element today),
   never by the number of nodes. It needs graph-io to write each style value into a column in
   a value graphty can draw (canonical color, graphty shape name, scaled size). What it does
   not give is meaning: the legend has one row per distinct value, and recoloring "all
   proteins" means editing data. So passthrough is the correctness floor and the fallback, and
   the real problem is choosing a more meaningful explanation when one exists and proving it
   is still exact.
3. **Meaningful explanations exist in the wild, and simple methods find them.** On 40 GEXF
   files (3 conformance fixtures, 37 found online; 34 carry node
   colors) with per-node color and size, the spike in this folder found:
    - node color determined exactly by one categorical attribute (disclass, Modularity Class,
      country, type, Category, Gender, actor, cluster) in 13 files, so one layer with a
      discrete map reproduces every node;
    - node size an exact linear function of degree or of a stored attribute in 12 files, so one
      layer with a linear scale;
    - node size a monotone but curved function of degree in 5 files: Gephi's ranking "spline"
      (a cubic Bezier easing curve). The curve was fitted to within float precision on one file
      (2.7e-7 max error) and to within 0.1 percent of the size range on three more;
    - no explanation for color in 6 files of more than 10 nodes, and for size in about 6 (for example 281 distinct
      colors on 374 nodes), where a synthesized group map or passthrough is the only honest
      answer.
4. **A layer stack is an ordered rule list, and that settles the algorithm family.**
   graphty-element's layers stack bottom to top and the last writer wins, which is exactly a
   decision list read from the top (Rivest 1987), or a "default plus exceptions" tree (Ripple
   Down Rules). Finding the smallest such list is NP-hard (minimum decision lists, minimum
   decision trees, minimum biclique cover of CSS rules), so exact minimality is not a goal.
   It also is not needed: a fixed recipe of "default, one explanation, one exception layer"
   per channel is exact by construction and bounded by a constant, and minimum description
   length (MDL) picks between the candidate explanations.
5. **Recommended bound:** per channel at most 1 default layer + 1 explanation layer (a
   discrete map, a linear or curved scale, or a passthrough) + 1 exception layer (a
   passthrough over a sparse column holding only the elements the explanation gets wrong),
   plus one layer per segment of a piecewise mapping that a file declares or that inference
   finds, capped at 8. Worst case for a file that styles 10 channels with no structure: 10
   layers. Never a function of graph size.
6. **graphty-element gaps found while mapping prior art onto its API** (each is a
   graphty-element fix, not a graph-io workaround): no multi-stop or unevenly spaced
   piecewise-linear scale (CX2 and Cytoscape continuous mappings have both), a continuous color
   ramp only from a registered palette with evenly spaced anchors, no easing-curve scale for
   Gephi's spline, and a ramp table that can differ from exact interpolation by up to half a
   unit per color channel. Details in "What this means for graphty-element".

### The target: what a graphty layer can say

Read from `graphty-element/src/catalog/types.ts`, `session/styles/Layer.ts`,
`session/styles/selector.ts`, `session/styles/scales.ts` and `session/styles/palettes.ts` on
2026-10-11.

- A layer targets nodes or edges, has a **selector** and writes a **set** of literal values
  and/or an **encode** map from channel to binding.
- Selectors: `everything`, `expression` (a JMESPath query over the element's data), `has`
  (the element carries a value at a path; 7.3 ns per element against 1,322 ns for an
  expression, measured in the source), `ids` (named elements), `top` (top n by a run field),
  `member` (a kept set).
- A binding is either `{ value }` or `{ by: path, scale, palette, domain, range, clamp, map,
other, missing, ... }`. Scales: linear, log, neglog10, sqrt, pow, bins, quantile, ordinal,
  passthrough, plus any registered by a plugin. `missing: "skip"` is the default, so an
  element without a value is left as the layers below painted it.
- Continuous color comes from a palette (`PaletteId`, built in or `registerPalette`), whose
  anchors are evenly spaced and interpolated in sRGB, then sampled into a table of 512 steps
  per anchor gap.
- Channels: 14 node channels and 21 edge channels (color, size, shape, label, opacity,
  outline, edge width, style, arrows, and so on).

The stack semantics matter for everything below: the value an element ends up with is the
value written by the highest enabled layer whose selector matches it and whose binding does
not miss. That is an ordered rule list with a default at the bottom.

### The passthrough observation, evaluated

Claim: copy each element's value for a channel into a data column, add one layer per channel
with selector `has` on that column and a passthrough binding, and every element is reproduced
exactly with one layer per channel.

It holds when four conditions are met, and each is graph-io's job at import time:

- **The value is in graphty's vocabulary.** Colors normalized to one spelling (graphty's
  passthrough hands strings straight to the channel; `hexToRgb` accepts six-digit hex only),
  shapes mapped to graphty's shape names, sizes scaled to graphty's units, line styles mapped
  to `edge.style` values. Anything with no graphty equivalent is dropped from the column and
  reported as a loss note, never thrown.
- **One file property becomes one or more channels.** A yEd label or a Cytoscape label position
  is a compound value; graphty splits label text, label style and tooltip into channels, so a
  compound value becomes several columns.
- **The column does not collide with the user's data.** Style columns need a reserved
  namespace so a node attribute called "color" is never overwritten.
- **Defaults stay defaults.** A file default (DOT `node [color=red]`, a Cytoscape default
  value) should be a `set` on an `everything` layer, not copied into every element's column,
  or a user who later changes the default sees nothing happen.

Two equivalent spellings of the fallback exist. Passthrough over the raw value column, or a
synthesized category column ("style group 1..k", one per distinct value) bound with an ordinal
scale and an explicit `map` from group to value. Both are one layer and both are exact; the
second gives a legend of k rows and lets a user recolor one group by editing one map entry,
which is the "atomic CSS" idea (one rule per distinct property value, bounded by distinct
values, not by elements). The second is the better fallback when k is small (for example 12 or
fewer); the first when values are nearly unique.

So the bound is easy. The hard part is producing groups and mappings that mean something,
which is what the rest of the prior art is about.

#### 2. Reverse engineering visualizations

- **Harper and Agrawala, "Deconstructing and Restyling D3 Visualizations" (UIST 2014) and
  "Converting Basic D3 Charts into Reusable Style Templates" (TVCG 2017).** The deconstructor
  reads the data bound to each SVG mark and, for each data field and mark attribute, checks
  for a linear mapping (by regression) or a categorical mapping (a one-to-one table of
  correspondences), plus text mappings with a common prefix or suffix. Marks are grouped by
  element type and groups whose mappings are equivalent are merged. Stated limits: no
  non-linear or algorithmic mappings.
  _Gives us:_ the exact shape of our problem (data bound to marks, recover the mapping) and
  the basic test set: linear, categorical, text template. _Guarantee:_ none stated; heuristic.
  _Fit:_ direct. Our candidate features are the node's attributes plus a few structural ones
  (degree); our candidate mappings are graphty's scales.
- **Poco and Heer, "Reverse-Engineering Visualizations: Recovering Visual Encodings from Chart
  Images" (EuroVis 2017)** and **Poco, Mayhua and Heer, "Extracting and Retargeting Color
  Mappings from Bitmap Images of Visualizations" (TVCG 2018).** From pixels: classify text
  roles, OCR the legend, classify the color encoding as categorical or continuous, recover the
  mapping. _Gives us:_ the categorical versus sequential versus diverging decision, and the idea
  of matching recovered colors to a known palette catalog. _Guarantee:_ statistical accuracy on
  corpora, not exactness. _Fit:_ weak for the core (we have exact values, not pixels), useful
  for palette naming: if a file's 9 colors are exactly a known categorical palette, say so.
- **Mystique (Chen et al. 2023)** deconstructs SVG charts for layout reuse; same family, less
  relevant.
- **Visualization by Demonstration (Saket et al., TVCG 2016).** A user resizes or recolors a
  few points and the system "solves for data attributes that can be mapped" to that channel
  and suggests them. _Gives us:_ exactly our inference step framed as user intent; it also
  suggests a later product feature (recolor two nodes, graphty proposes "color by type").
  _Fit:_ same algorithm, smaller input.

#### 3. CSS refactoring and minification

- **Mazinanian, Tsantalis and Mesbah, "Discovering Refactoring Opportunities in Cascading Style
  Sheets" (FSE 2014)** and CSSDev (ICSE 2017): detect duplicated declarations across selectors
  with FP-Growth frequent pattern mining and extract them into a shared rule or a preprocessor
  mixin. _Gives us:_ the idea of grouping by shared property-value sets across several
  properties at once. _Guarantee:_ behavior preserving for the detected cases. _Fit:_ the
  cross-channel merge step (one layer setting color and shape for "disease" nodes).
- **Hague and Lin, "CSS Minification via Constraint Solving" (TOPLAS 2019, SatCSS).** Models a
  stylesheet as a bipartite graph of selectors and declarations with an order on the edges
  (because the cascade makes order matter), and minimizing a stylesheet as covering that graph
  with a sequence of bicliques that respects the order. NP-hard; solved greedily, one merge at
  a time, each chosen with a Max-SAT solver. _Gives us:_ the precise formal statement of our
  problem when order matters (graphty layers are ordered like the cascade) and the evidence that
  optimal is out of reach. _Fit:_ informs the design; a solver is not needed because our
  per-channel recipe is already bounded.
- **Atomic CSS (one class per property-value pair).** The industrial answer to unmanageable
  style sheets: a rule per distinct value, never per element. It is the synthesized-group
  fallback above.

#### 4. Covering: biclique cover, formal concept analysis, Boolean matrix factorization, set cover

- **Formal concept analysis** (Ganter and Wille) enumerates every maximal "these elements share
  these style values" rectangle (a concept) and orders them in a lattice. Exact and complete,
  but the number of concepts can be exponential.
- **Role mining** (Vaidya, Atluri and Guo, 2007): find the fewest roles so that user-permission
  assignment equals the Boolean product of user-role and role-permission matrices. Replace
  users by elements and permissions by (channel, value) pairs, and roles are layers with an
  `ids` selector. NP-complete (from Set Basis); heuristics exist.
- **Tiling databases** (Geerts, Goethals and Mielikainen 2004): cover the ones of a binary
  matrix with few large tiles; the greedy algorithm gives a 1 - 1/e approximation of covered
  area for k tiles.
- **Set cover**: greedy is within ln n of optimal (Chvatal 1979), and no polynomial algorithm
  does better unless P = NP (Feige 1998).

_Gives us:_ the vocabulary and the hardness results. _Fit:_ these methods group elements by
their style values but invent groups with no data behind them; the resulting layers would be
`ids` selectors listing members. That is exact and can be small, but an `ids` layer is as
opaque as passthrough and breaks the moment a node is added. Use the idea (find rectangles of
shared style across channels) only to merge channels that share an already-explained partition,
not to invent groups.

#### 5. Rule induction: decision trees and rule lists

- **ID3 (Quinlan 1986), C4.5 (1993), CART (Breiman et al. 1984):** split elements by attribute
  tests until each leaf has one style value. Each root-to-leaf path is a conjunction of
  predicates, which is a JMESPath `expression` selector. Building the smallest consistent tree
  is NP-complete (Hyafil and Rivest 1976).
- **Decision lists (Rivest 1987)** are "if test1 then v1 else if test2 then v2 ... else
  default". A graphty stack read from the top is exactly this. Learnable efficiently for bounded
  test size, but the minimum decision list is NP-hard to find or approximate.
- **RIPPER (Cohen 1995)** learns ordered rule sets with pruning and an MDL stopping rule;
  **CORELS (Angelino et al. 2018)** finds certifiably optimal rule lists for categorical
  features by branch and bound, in seconds on practical problems, under a regularized objective
  (accuracy minus a penalty per rule).
- **Ripple Down Rules (Compton and Jansen):** rules with exceptions, where an error is fixed by
  adding an exception that only sees the cases the parent rule covered. This is "default layer,
  explanation layer, exception layer".

_Gives us:_ the exact correspondence between a layer stack and a rule list, a way to explain a
style with predicates over several attributes ("type == 'gene' and degree > 10"), and an
optimality option (CORELS) if ever needed. _Guarantee:_ a consistent tree or list is exact on
the training elements by construction; size is minimal only for CORELS within its feature set.
_Fit:_ secondary. In the spike every explainable color was explained by ONE attribute, which
does not need a tree. Trees and lists are the tool for the residue: when one attribute explains
most elements, a short list of exceptions in data terms beats an opaque exception layer, but
only if it stays short (MDL decides). They also overfit easily on small graphs.

#### 6. Functional dependency discovery and partition refinement (the workhorse)

- **TANE (Huhtala et al. 1999):** column X determines column Y exactly when the partition of
  rows by X refines the partition by Y, equivalently when the number of groups of X equals the
  number of groups of (X, Y). One hash pass per candidate column. Approximate dependencies use
  the g3 error: the smallest share of rows to delete for the dependency to hold exactly.
  Papenbrock et al. (VLDB 2015) compare seven such algorithms.
- **Partition refinement (Paige and Tarjan 1987)** is the general machinery for computing the
  coarsest partition consistent with a set of splits.

_Gives us:_ the exact test "does attribute A determine node color", linear in n per attribute,
and a number (g3) that says how many exceptions an almost-dependency has. _Guarantee:_ exact and
complete over the attributes tried. _Fit:_ direct. A dependency A determines style S with k
keys becomes ONE layer: `has A`, ordinal scale, `map` from each key to its value. An approximate
dependency with g3 error e becomes that layer plus an exception layer over e times n elements.
This is what the spike used, and it explained 13 of the 34 colored files exactly.

Two traps the spike exposed:

- On tiny graphs anything determines anything (2 nodes, 2 values). Require support: the
  number of keys well below n (the spike used keys < n; a real rule should be stricter, for
  example keys at most n/2 and at least 2 elements per key on average).
- Near-unique attributes (labels, ids) "determine" everything trivially. Exclude keys close to
  n, and prefer the dependency with the fewest keys (MDL).

#### 7. Continuous mappings: linear, piecewise linear, monotone, known curves

- **Linear regression** (Harper and Agrawala's test) decides one linear piece. With exact data
  the right test is not r squared but "every point within the file's rounding tolerance".
- **Fewest pieces within a tolerance.** Imai and Iri (1986) for polygonal curves; Hakimi and
  Schmeichel (1991) fit a piecewise-linear function to points in the plane with the minimum
  number of pieces under a maximum-error bound in O(n). For a function y = f(x) (one y per
  distinct x after the dependency test), the greedy "extend the segment while a line fits" is
  optimal for discontinuous pieces because feasibility is hereditary.
- **Isotonic regression and the Pool Adjacent Violators algorithm** (linear time) decide whether
  the value is monotone in the feature and give the best monotone step fit.
- **Known transfer curves.** Gephi's ranking applies an interpolator to the normalized value:
  linear, or a cubic Bezier easing curve. The spike fitted that curve family to size versus
  degree: celegans to 2.7e-7 (exact up to float printing), eurosis, yeast and arctic to within
  0.08, 0.07 and 0.09 percent of the size range, french-ipr not at all (its degree is probably
  computed differently, for example directed or with multi-edges). A linear fit missed by
  9 to 25 percent of the range.
- **Cytoscape continuous mappings** are already piecewise linear with explicit points and
  separate below, at and above values, which makes them discontinuous on purpose (a threshold
  mapping). Inference must allow discontinuities; translation must reproduce them.

_Gives us:_ an exact, bounded menu for numeric features: one linear piece; s pieces; a monotone
curve from a known family; or, when none of these is exact, a discrete map keyed by the
feature's distinct values (exact, one layer, k keys, and it still records "size depends on
degree"). _Fit:_ direct, with the graphty gaps listed below.

#### 8. Colors and palettes

- Gephi writes colors as integers per channel; a gradient fitted in sRGB must match after
  rounding, so the tolerance is half a unit (the spike used 0.5 and, for truncation, 1).
- graphty interpolates palette anchors in sRGB too, so a two-stop sRGB gradient from Gephi can
  be reproduced, but only with a palette whose anchors are the file's stops, evenly spaced.
- Categorical palettes: compare a file's distinct colors with the palette catalog (ColorBrewer,
  d3, graphty's own). An exact match lets the import name a palette instead of a hand-written
  map, which is what Poco, Mayhua and Heer do with recovered legends.
- Spike warning: numeric category codes (Modularity Class) also "fit" a piecewise-linear color
  ramp with 3 to 8 pieces. The discrete map with the same number of keys is the shorter
  description, so MDL must compare them; a numeric fit must never win just because the column
  is numeric.

#### 9. Minimum description length (the selection rule)

- **MDL (Rissanen 1978):** choose the model that minimizes the bits to describe the model plus
  the bits to describe the data given the model.
- **Krimp (Vreeken, van Leeuwen and Siebes 2011)** selects the itemsets that best compress a
  database and cuts millions of candidate patterns to hundreds; Slim is a faster successor.

_Gives us:_ one principled score to choose among passthrough (cost: n values), a synthesized
group map (k values plus n group labels), a discrete map on an existing attribute (k entries
plus exceptions), a linear scale (4 numbers plus exceptions), s pieces (4s numbers), a decision
list (its tests plus exceptions). _Guarantee:_ none about truth, but it prevents both
overfitting (8-piece ramps over category codes) and underfitting. _Fit:_ the decision rule of
the pipeline. A crude but adequate version: count the numbers and strings each candidate
writes into layers, plus the exceptions, and take the smallest.

#### 10. Programming by example and verification

- **FlashFill (Gulwani, POPL 2011):** synthesize a program consistent with input-output examples
  from a small language, ranked by simplicity. Our input-output pairs are (element data, style
  value); our language is graphty's selectors and scales. The PBE lesson that matters: the
  candidate program is checked against every example before it is accepted.

_Fit:_ the guarantee of the whole design. After choosing layers, resolve every element through
the produced stack and compare with the file's own value within the channel's tolerance. Any
mismatch moves that element into the exception layer. Exactness then holds by construction,
not by the correctness of the inference.

### What the prior art implies for the design

An ordered recipe per channel and target (nodes, edges), each step checked by replay:

1. **Normalize** each element's value into graphty's vocabulary (color spelling, shape names,
   units). Unknown values are dropped and reported as loss notes. Nothing throws.
2. **Translate declared rules first** (Cytoscape style in .cys, XGMML, CX, CX2; Cytoscape.js
   stylesheets; DOT defaults and subgraph scopes). File defaults become `set` values on an
   `everything` layer; discrete mappings become an ordinal `map`; passthrough stays
   passthrough; continuous mappings become linear pieces. Bypasses become the exception layer.
3. **Infer where nothing is declared**, in order of cost and meaning:
    - one distinct value: a default (`everything`, `set`);
    - an exact or near dependency on one attribute (TANE partition test, g3 for the near case):
      one discrete-map layer, exceptions above it;
    - a numeric attribute or degree that explains the value: one linear piece, then a known curve
      family (Gephi Bezier), then at most 8 pieces, then a discrete map keyed by the feature's
      values;
    - optionally, a short decision list over two attributes when it beats the alternatives by
      MDL;
    - otherwise a synthesized group column with a map (few distinct values) or passthrough
      (many).
      Choose among the candidates by a simple MDL count, never by "numeric column so use a ramp".
4. **Merge channels** that share the same explaining attribute into one layer (the CSS
   duplicate-extraction and concept-analysis idea), so "type" drives color and shape together.
5. **Verify by replay** and push every mismatch into the exception layer: a sparse style column
   that only mismatched elements carry, read by one passthrough layer with selector `has` at the
   top of that channel's stack. Exact by construction; one layer however many exceptions.

Layer bound per channel: 1 default + 1 explanation + 1 exception, plus up to 7 extra pieces
when a piecewise mapping needs one layer per piece. Independent of graph size.

Structural features such as degree raise a design question for the main design document: graph-io
can compute degree while importing and store it as a column, or the layer can bind to a
graphty degree run. Binding to a stored column is self-contained and exact for the file as
loaded; binding to a run follows later edits. This is a decision for the design, not for the
prior art.

### What this means for graphty-element

These are gaps between what files declare or what inference finds, and what a graphty layer
can express today, read from source on 2026-10-11. Per the repository's rules each is a
graphty-element change (all additive), not something graph-io should work around:

- **No multi-stop piecewise-linear scale.** `linear` maps one domain interval to one range.
  A Cytoscape or CX2 continuous mapping with 3 points, unequal spacing, or a jump at a point
  needs one layer per interval with an `expression` selector bounding the interval. Bounded
  (by the mapping's points) but clumsy; a `stops` option on the linear scale (a list of
  `[domainValue, outputValue]` pairs, plus below and above values) would make it one layer.
- **Continuous color only through palettes with evenly spaced anchors**, and a custom palette
  has to be registered globally with `registerPalette`. An imported gradient (Gephi's color
  stops, Cytoscape's color points) needs either inline colors on the binding or the same `stops`
  option taking colors.
- **No easing-curve scale.** Gephi's ranking spline is a cubic Bezier from (0,0) to (1,1). The
  scale registry accepts plugin scales, so it is possible today, but an import that needs a
  plugin scale is not self-sufficient; a built-in `bezier` (or `ease`) scale with four control
  numbers would make Gephi sizes one exact layer.
- **The ramp table rounds.** Continuous color is sampled at 512 steps per anchor gap, which the
  source documents as never moving a channel by half a unit or more. An exact reproduction check
  must use a tolerance of one unit per color channel for ramp-painted colors, or the element
  should expose the exact interpolated value. The verifier needs to know which.

### Adversarial notes for the reviews to come

- Spurious dependencies on small graphs and on near-unique columns (see section 6).
- Numeric category codes fitted as ramps (see section 8).
- Degree is not one thing: directed, undirected, weighted, with or without self-loops and
  multi-edges; the french-ipr miss is probably this.
- Ties and floats: a value printed with 7 significant digits needs a tolerance relative to the
  range, not an absolute one; the verifier must use the same tolerance the inference used.
- Missing values: an element with no style value must be left to the layers below, which
  graphty's `missing: "skip"` already does; a file default must still reach it.
- Order: a layer that explains one channel must never write another channel it has no value
  for (the rule in CLAUDE.md about algorithm styles applies equally to imported layers).

## graphty-element's side of style import: what a layer can say, and how a graph file's styles could reach it

This note maps the receiving end of a style import: everything a graphty-element style layer can
express, how a layer chooses the elements it paints, how values are bound to data, how layers are
added, saved and checked, what a data source hands the element today when it reads a file through
graph-io, and which style properties found in graph files the element can draw, can only
approximate, or cannot draw at all.

Everything here was read from the source on master (2026-10-11) and the load-bearing claims were
run headlessly against the source (probe scripts run with `tsx` against the
workspace sources).

### 1. The answer in brief

- A layer paints EITHER nodes OR edges, chooses elements with a selector, and writes channels
  (closed list of 35, 34 drawable) either as fixed values (`set`) or as bindings to a data path
  (`encode`). Layers stack bottom to top; per channel the highest layer that wrote a value wins.
  Label styles are the one exception: they merge field by field across layers.
- **A per-element style can be reproduced exactly by ONE layer per element kind**, whatever the
  graph's size, as long as the per-element value sits in a data column and the channel takes a
  color, number, enum, text or boolean: `encode: { "<channel>": { by: "data.<column>", scale:
"passthrough" } }`. One layer can bind every channel of its kind at once. Verified: 5,000 nodes
  with 5,000 distinct colors, sizes and opacities, one layer, every node painted exactly, 41 ms.
  Elements with no value in the column, and values the channel cannot carry (an unknown shape
  name, an unparseable color), are left to the layers beneath. Nothing throws.
- **A discrete value-to-style table is one layer too**: `scale: "passthrough"` plus a `map` of
  `{ fileValue: styleValue }` paints mapped values exactly and leaves the rest alone. Verified with
  20 categories and no palette (no palette-capacity refusal when every value is mapped). Avoid
  `scale: "ordinal"` for this: it gives an unmapped category a palette color the file never named.
- **The weak spot is label typography.** `node.labelStyle`, `node.tooltipStyle`,
  `edge.labelStyle` and the arrow caption styles are whole objects (font, size, weight, color,
  background, location...) that cannot be bound to data; they can only be `set` on a layer. So a
  file whose label font size or label color varies per element needs one static layer per distinct
  label-style tuple. If those tuples are continuous (a font size per node computed from a metric),
  layer count approaches node count. Ways out, in order of preference: an additive element change
  (label-style sub-channels such as label color, label size and label font that accept bindings);
  grouping by distinct tuple with a cap and a report; or the label markup escape hatch (section 6).
- **Today nothing about styles crosses from graph-io to the element.** A data source built with
  `DataSource.fromImporter` turns the import into plain node and edge records (every attribute
  column copied under its own name), drops graph-level attributes, drops columns named
  `graphty.*`, and forwards only error-severity issues. GEXF's `viz:color` arrives as a 4-number
  array in 0..1 that no binding can read as a color (verified: 0 of 4 nodes painted). The import
  report's warnings and loss notes reach no consumer.
- There is a precedent for a file telling the element something besides records:
  `DataSource.declareDirection`, which flows through `ChunkReader.declaredDirection` in
  `session/project/ingest.ts` and `HeldRows.declaredDirection` in `session/commands/data.ts`. A
  style hand-off would follow the same path and end in `session.styles.applyTemplate(document,
{ templateId })`, which already exists, is atomic, and disables (rather than drops) layers whose
  paths nothing answers.
- Four element defects turned up that a style import would trip over (section 9), among them:
  `styles.explain()` reports label styles replaced wholesale while the repaint merges them field
  by field, so verifying an import through `explain()` would disagree with the screen.

### 2. The layer model

Source: `src/catalog/types.ts` (the published types), `src/session/styles/Layer.ts`,
`src/session/styles/StylesApi.ts`.

```ts
interface LayerSpec {
    // what an author, an import or an export writes
    name: string; // free text, not an identity
    target?: "node" | "edge"; // one layer never paints both
    kind?: "base" | "encoding" | "highlight" | "custom"; // default "custom"
    selector: Selector; // which elements
    set?: StaticStyle; // Partial<Record<Channel, ChannelValue>>
    encode?: Encoding; // Partial<Record<Channel, Binding>>
    source?: LayerSource; // who put it there; default { by: "user" }
    enabled?: boolean; // default true; a disabled layer keeps its place
    userData?: Record<string, unknown>; // carried untouched, never read by the element
}
interface StyleDocument {
    version: 1;
    layers: readonly LayerSpec[];
    palettes?: readonly PaletteDescriptor[];
}
type LayerSource =
    | { by: "element"; reason: "default" | "selection" | "hover" | "notes" }
    | { by: "run"; runId; algorithm; params }
    | { by: "user" }
    | { by: "template"; templateId: string }
    | { by: "plugin"; name: string };
```

Rules that matter for an import:

- **Identity is an element-minted id**, built from the name plus a counter (`file-styles-nodes_1`).
  Never an index. Positions are given as `{ above }` / `{ below }` a neighbor id, or the top.
- **The stack starts with two locked base layers**, "Node defaults" and "Edge defaults"
  (`elementBaseLayers()` in `src/session/GraphSession.ts`), each `{ match: "everything" }`. They
  paint node color `#6366F1`, size 1, shape `icosphere`; edge line solid, width 8, color
  `darkgrey` (`#A9A9A9`), head arrow `normal`, animation 0. Everything an import adds sits above
  them, so an element the file says nothing about keeps these defaults.
- **One channel, one writer per layer**: writing the same channel in both `set` and `encode` is
  refused. Writing both node and edge channels in one layer is refused.
- **Every check happens before the layer is accepted** (`checkLayerSpec`): the selector is
  compiled, every channel name is looked up, every literal value is checked against the channel's
  accepted kind and range, every scale and palette name is resolved. All problems are reported at
  once, with a dotted path into the spec. `styles.validate(spec)` runs the same check without
  writing.
- **A path nothing answers is not an error.** `{ match: "has", path: "data.nope" }` is accepted and
  reported in `unresolvedPaths`; through `applyTemplate` such a layer is added DISABLED and listed
  in the report's `unbound` (verified).

### 4. Selectors

Source: `src/session/styles/selector.ts`, `src/session/styles/predicate.ts`.

```ts
type Selector =
    | { match: "everything" } // no test at all; the empty string is refused
    | { match: "has"; path: Path } // element carries a non-null value for the column
    | { match: "expression"; where: Query } // JMESPath subset, compiled once
    | { match: "ids"; nodes?: NodeId[]; edges?: EdgeId[] } // named outright
    | { match: "top"; path: "results.<run>.<field>"; n } // run results only
    | { match: "member"; of: Scope }; // members of a kept set or other scope
```

- **Paths**: `data.<column>` is a data column (the column name literally, dots and spaces
  included), `results.<run>.<field>` a run's result, `graphty.<x>` a value the element provides
  (never a column; a file column literally named `graphty.x` reads as `data.graphty.x`).
- **The expression subset**: paths, JSON and raw string literals, `== != < <= > >=`, `&& || !`,
  parentheses. No functions, projections, wildcards, pipes, slices. JMESPath truthiness (0 is
  true). Anything outside the subset is refused with a character offset. A column whose name needs
  quoting goes through the exported `quotePath()` (`data."shared name"`; verified, matched 1,667
  of 5,000).
- **Edge ids are element-minted counters** (`String(counter)`, `src/data/edgeIdentity.ts`), not the
  file's edge ids, so an import cannot name edges in an `ids` selector before the load. Edge groups
  must be selected by data (`has`, `expression`) or by a kept set. Node ids are the file's ids.
- **Cost**: `has` 7 ns per element, `ids` and `member` one lookup or bit test, `expression` about
  8 ns compiled (`predicate.ts` header). Not a concern at import sizes.

### 5. Bindings, scales and palettes

```ts
type Binding =
    | { value: ChannelValue }
    | {
          by: Path;
          scale?:
              "linear" | "log" | "neglog10" | "sqrt" | "pow" | "bins" | "quantile" | "ordinal" | "passthrough" | string;
          palette?: PaletteId;
          domain?: [number, number] | "auto";
          clamp?: [number, number];
          range?: [number, number];
          map?: Record<string, string | number>; // per-value overrides, consulted before the scale
          other?: { threshold: number; value: string | number };
          overflow?: "other" | "shape" | "extend"; // categorical colors past the palette's capacity
          missing?: "skip" | { value: string | number }; // default "skip": leave the element to the layers beneath
          hidden?: (string | number | boolean)[];
          reverse?: boolean;
          midpoint?: number;
          bins?: number;
          exponent?: number;
      };
```

Behavior that decides an import (from `scales.ts`, `encoding.ts`, `palettes.ts`, verified in the
spike):

- **`passthrough`** reads the value as it is. Per channel kind:
    - color: a string is parsed by the element's one color parser (hex 3/4/6/8 digits, CSS names,
      `rgb()`, `hsl()` and the rest colorjs.io reads); unparseable is unpainted. A number, an array
      or an object is unpainted (so GEXF's `[r, g, b, a]` array cannot be passed through).
    - number: finite numbers pass, numeric strings pass, then CLAMPED to the channel's range
      (`-1` size painted as 0, opacity 1.5 painted as 1; both counted as painted, not as out of
      range). An importer must range-check and report itself.
    - enum: the string must be one of the channel's values exactly; anything else is unpainted.
    - text: anything is stringified. boolean: `true/false`, `"true"/"false"`, 1/0.
    - labelStyle: refused, but only at repaint time (section 9).
- **`map`** is consulted first, keyed by the value spelled as a category (`0` and `"0"` are the
  same key); with `scale: "passthrough"` unmapped values fall through to passthrough, which for
  category names that are not colors means unpainted. That makes `passthrough + map` an exact
  discrete table. With `scale: "ordinal"`, an unmapped category gets a palette slot color the file
  never named.
- **Continuous scales** (`linear`, `log`, `sqrt`, `pow`, `bins`, `quantile`) take a `domain` and a
  `range` (numbers) or a `palette` (colors). A palette interpolates evenly spaced stops, so a file
  mapping with uneven breakpoints (Cytoscape continuous mappings with arbitrary points) is only
  reproduced exactly when the breakpoints are even; otherwise the exact route is for graph-io to
  compute each element's value and hand it over for passthrough.
- **Palettes** are global registrations (`registerPalette` from `./extend`), not per session. A
  `StyleDocument` may carry palette descriptors, but `applyTemplate` refuses a document naming a
  palette nobody registered (`E_UNKNOWN_PALETTE`). A file-derived gradient would therefore have to
  register a page-wide palette with a unique id. Prefer passthrough or `map` over minting palettes.
- **Missing values**: `missing: "skip"` (the default) leaves the element to the layers beneath,
  per channel, inside a multi-channel layer (verified: node b had no shape value and kept the base
  `icosphere` while its color and size came from the import layer).

### 6. How layers stack and merge

- Per channel, last writer wins (bottom first). `explain()` and the repaint walk the same compiled
  closures.
- Label styles merge field by field in the repaint (`writeColumn` in `repaint.ts`): `{ sizePx: 24 }`
  under `{ color: "#f00" }` draws a red 24 px label. `explain()` does not (section 9).
- An arrow cap with no color follows its line's color.
- Node color alpha is discarded (`Node.ts` writes the instance color with alpha 1); a file's fill
  alpha must become `node.opacity` (multiplied with any node opacity the file states).
- **Label markup**: label, tooltip and caption text from data is parsed for inline tags
  `<bold>`, `<italic>`, `<color='...'>`, `<size='N'>`, `<font='...'>`, `<bg='...'>`
  (`src/meshes/RichTextParser.ts`); only text bound to `graphty.notes.*` is drawn plain. Two
  consequences: (a) per-element label color, size, font, bold and italic CAN be reproduced exactly
  by one passthrough layer whose text carries the tags, which also covers italic, which no label
  style field can; (b) a file label that literally contains such a tag is reinterpreted, and there
  is no escape syntax. Mixing style into the words is a last resort: the style is then invisible to
  `explain()`, the legend and a style editor.

### 7. How layers are added, saved, checked and swept

`session.styles` (`SessionStylesApi`, published from `./session`; the types from `./schema`, which

### 8. What a data source hands the element today

Source: `src/data/DataSource.ts` (`fromImporter`), `src/data/graph-io-import.ts`,
`src/session/project/ingest.ts`.

1. `importWhole()` runs the graph-io importer into a scratch `GraphBuilder` and freezes it.
   Error-severity issues go to the source's `ErrorAggregator`; a fatal import becomes
   `E_PARSE_FAILED`.
2. `toRecords(imported, columnsMapping(snapshot))` makes one plain record per declared node
   (`{ id, ...columns }`) and per logical edge (`{ source, target, weight?, ...columns }`).
   `copyColumns` copies every node and edge attribute column under its own name, skipping any
   column whose name starts with `graphty.` (graph-format's reserved prefix). Multi-component
   cells become arrays.
3. The records are yielded in chunks; the session writes them as data columns, readable by layers
   as `data.<name>`.

What is lost on the way:

- **Graph-level attributes** (the graph table) are not read at all, so a format's defaults
  (a DOT `node [color=red]` statement after it has been applied, a GraphML `<default>`, a canvas
  color) reach the element only if the importer has already copied them onto every element.
- **Warnings and loss notes** (`ImportReport.issues` with severity warning, `ImportReport.lossy`)
  are not forwarded to any consumer surface.
- **Column roles** (graph-format's `color`, `size`, `shape`, `thickness` roles, set by the GEXF
  importer for `viz:*`) are not consulted; style columns arrive as ordinary data attributes, appear
  in `session.data.attributes()` beside the file's real data, and in GEXF's case in a form no
  binding reads (`color` is f32 x4 in 0..1).
- **Edge identity**: the file's edge ids become ordinary data; the session's edge ids are
  counters.

The precedent for a non-record hand-off is direction: `DataSource.declareDirection(directed,
statedBy)` (protected), read by the ingest as `reader.declaredDirection` per chunk, and carried by
a draft's `HeldRows.declaredDirection`. A style hand-off would add a sibling (for example a
declared style document) on the same three shapes: the `DataSource` base class, `ChunkReader` in
`ingest.ts`, and `HeldRows` in `session/commands/data.ts`, and the ingest would apply it with
`applyTemplate` after the records are written, so `unresolvedPaths` are answered.

Dependency direction constrains where the hand-off type lives: graph-io sits below
graphty-element (`graph-format -> graph-io -> ... -> graphty-element`), so graph-io cannot import
`LayerSpec` or `StyleDocument` from `./schema`. Either graph-io (or graph-format) defines a neutral
style description that the element translates into layers, or the element's types move down.

### 9. Element defects found

Each is a real defect a style import would hit; per the repository's rules the fix belongs in
graphty-element, not in an importer or the app.

1. **`explain()` disagrees with the repaint on label styles.** `explainStyle`
   (`src/session/styles/explain.ts`, `merged[channel] = result`) replaces a label-style object
   wholesale, while the repaint's `writeColumn` (`src/session/styles/repaint.ts`) merges it field
   by field. Spike: layers `{ sizePx: 24 }` then `{ color: "#ff0000" }` on node `a`; `explain()`
   reports `node.labelStyle: { color: "#ff0000" }` (the size is gone) although the screen draws
   both. Any verification of imported label styles through `explain()` is wrong until this is
   fixed. Applies to `node.labelStyle`, `node.tooltipStyle`, `edge.labelStyle` and the four arrow
   caption style channels.
2. **A label-style binding passes validation and then paints nothing.** `validate()` and `add()`
   accept `encode: { "node.labelStyle": { by: ... } }` (`ok: true`, no errors); the repaint then
   disables it with a console warning (`E_BAD_LAYER`, "carries a whole label style, which no scale
   produces"). Through `applyTemplate` such a layer would be reported as applied while drawing
   nothing. `checkBinding` in `Layer.ts` should refuse it, as `assertChannelTakesScale` in
   `encoding.ts` already does.
3. **Passthrough clamps instead of reporting.** A number outside a channel's range is clamped and
   counted as painted (size -1 drawn at 0; opacity 1.5 drawn at 1). `counts().outsideScale` does
   not see it, so an import cannot learn from the element that a value was altered.
4. **Node color alpha is silently dropped.** `node.color` accepts `#rrggbbaa` and `rgba()` and the
   resolved value carries `a`, but the instance color is written with alpha 1. Either honor it or
   document and refuse it; today a translucent fill imports as opaque with no note.

Not defects, but gaps an import design has to plan around: label-style fields cannot be bound to
data (the main layer-count risk); no channel for gradient node fills, node border width, node
border style, node width-and-height, node images, edge bend points, edge tooltips, italic labels.

### 11. What this means for keeping the layer count small

From the element's side, the smallest exact representation is:

- **One node layer and one edge layer** of passthrough bindings for every per-element value of a
  drawable, bindable channel (color, size, shape, opacity, outline, glow, line, arrows, curvature,
  label and tooltip text). This holds for any graph size. Values the channel cannot carry are left
  to the base layer and must be reported by the importer, because the element only counts them
  (`counts().outsideScale`) and says nothing for clamped numbers.
- **One layer per channel family for a file's discrete mapping** (passthrough plus `map`), which
  stays editable value by value.
- **Plus one static layer per distinct label-style tuple**, which is the only part that can grow
  with the graph. Bound it (for example, a cap of a few dozen tuples, quantizing font size and
  reporting the quantization) or fix it in the element with bindable label-style sub-channels,
  which would be an additive, non-breaking API change.
- **Plus one layer per real group the file declares** (a Cytoscape discrete mapping column, a GEXF
  or GraphML class attribute, a DOT cluster), selected by a data predicate or a kept set; never by
  edge id.

A render-cost note, separate from layer count: every distinct value of a `mesh`-role channel is a
source mesh. Passing through a continuous per-node size, opacity, glow or arrow setting from a file
can mint one mesh per node even though it is one layer. The element documents this
(`intern.ts`); an import of continuous sizes may want to quantize and say so.

### 12. Public API a style hand-off would touch

- `./schema` and `./catalog`: `LayerSpec`, `StyleDocument`, `Selector`, `Binding`, `Encoding`,
  `StaticStyle`, `Channel`, `ChannelValue`, `LabelStyle`, `LayerSource`, `PaletteDescriptor`
  (types), `NodeShapes`, `EdgeLineTypes`, `EdgeArrowTypes` (value lists to map file vocabularies
  onto).
- `./session`: `session.styles.validate / add / applyTemplate / removeBySource / toDocument /
explain / counts / agreement`, `quotePath`, `session.visibility.set` (hidden elements),
  `session.sets` (file-declared groups).
- `./extend`: `DataSource.fromImporter` (where a declared style would be read from the importer's
  result), the protected `DataSource.declareDirection` pattern, `registerPalette` (only if file
  palettes are minted, which this note recommends avoiding).
- Element configuration: `element.background` / `session.config` for the canvas color.
- graph-io side (for the other half of the design): `ImportReport.lossy` and `issues`, which today
  stop at the data source; and the graph table, which today is not read.
