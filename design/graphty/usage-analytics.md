# Usage analytics: anonymous PostHog counts for everyone, full PostHog after consent, Sentry for errors only (with the usage-analytics experiment on)

Issue #8818. Branch feat/usage-analytics.

## 1. What this is

With the `usage-analytics` experiment on (see "The experiment flag" below), the graphty app (graphty.app) gets three data paths; with it off it keeps master's one, Sentry after Share. Each has one job. The first two are the same PostHog project, so one query (and the PostHog API or MCP server) sees every count; each event says which path sent it (`tracking`, section 4.1).

| Service                                                                               | Who it covers                                                               | What it answers                                                                                                                                                                       | Identifier                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostHog Cloud EU, anonymous mode (`tracking: "anonymous"`, PostHog's cookieless mode) | every visitor who has not chosen "Share usage data" (undecided or declined) | How many people come, which channel sent them (`?ref=hn`), do they come back, do they load a sample or their own file, run a measure, export, and how many choose to share usage data | nothing is stored in the browser and no id is sent from it. Each count reaches PostHog with the IP address and User-Agent; PostHog's ingestion turns them into a daily id, hash(project, daily salt, IP, User-Agent, host), keeps each day's salt for about four days (the day plus a buffer for late events) and then deletes it, and strips the IP and raw User-Agent before it stores the event. It keeps the browser name, operating system name and device type the page reports (no versions), and no location |
| PostHog Cloud EU, shared mode (`tracking: "shared"`)                                  | only readers who said "Share usage data"                                    | What people are trying to do (survey), how far they get (funnels and paths), where they struggle (masked replays, rage and dead clicks, failure codes)                                | a random id in this browser, deleted when sharing is turned off                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Sentry                                                                                | only readers who said "Share usage data"                                    | What broke: errors, a masked replay of the moments before an error, and user feedback                                                                                                 | none                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

The pitch of the app is "your files never leave your computer". Three rules follow from it, and tests enforce each one:

- No event property carries the reader's data. That means no file names, URLs, labels, column names, note text, project names or journal command payloads. Every property value comes from an allowlist: catalog ids, command ids, the app's own ids, fixed enums or buckets. Anything else is sent as `"other"`. The one exception is the survey's optional "Other" text box, which sends what the reader types there, disclosed next to the box and on the privacy page.
- Before or without "Share", only the anonymous counts in section 4.1 leave the page, at most once per name per page view. They carry no identifier from the page and PostHog writes nothing to cookies, localStorage or sessionStorage for them. PostHog's code is downloaded after first paint for every visitor (decision 6), but in this mode it records nothing on its own: no autocapture, heatmaps, page-leave, web vitals, replay, surveys, remote config or feature flags.
- Every URL sent to any vendor, at any depth of any payload, Sentry included, is cut: a same-origin URL to its path plus a sanitized channel parameter, any other URL to the fixed token `"external"` (not even its origin: the origin of a server the reader opens is that server's address). Referrers are cut to their origin. PostHog's stored first referrer and first URL (`$initial_person_info`) are turned off, because posthog-js sends them in its feature-flags request, which never passes `before_send`. Before either recorder (Sentry's error replay or PostHog's session replay) starts, the address bar's query string and hash are removed, so a replay never records them.

Architecture rule: facts about the graph come from graphty-element's public events. PostHog and Sentry live only in the graphty app, and graphty-element never imports either. graphty-element gains additive, neutral API (section 8): one session event `source:loaded`, one optional load option `callerKey`, a `trigger` on journal entries, a `trigger` on run changes, a `via` on selection changes and one camera event.

### The experiment flag

Everything in this document that PostHog does, and every word about it in the app, is behind the graphty app's own experiment `usage-analytics` (tracking issue #8818), declared in `graphty/src/features.ts` as an app-only experiment (design/ci/channels-pipeline/features.md, section 5.3). graphty-element does not declare it: its `resolveFeatures` lists an id it does not know under `unknown`, so the app reads the combined raw list the site configuration holds (site.json's `features`, then `?features=`), where `"all"` switches it on too.

- **On:** canary (`graphty/sites/canary.json`), any site opened with `?features=usage-analytics`, and the test suite's On configuration. The words and controls this document describes show wherever it is on, but PostHog is sent something only where the site's `site.json` also has an `analytics` block and the page is on that site's own host (section 5). Only `production.json` has PostHog ids, so canary and nightly show the words and send PostHog nothing; the one place to try the whole feature end to end is `https://graphty.app/?features=usage-analytics`.
- **Off** (nightly and production, the default): the app never loads posthog-js and sends PostHog nothing, in either mode; no survey or SurveyCard; no `graphty.visits.v1`, `graphty.surveys.v1` or PostHog key is written, and a No (here, in Settings) deletes those an earlier visit with it on wrote, as the privacy page promised that reader; the channel parameters stay in the address bar; and every reader-visible word, the corner the usage data card sits in and the links to `/privacy.html` are as before this change. Share and No start and stop Sentry alone, in the tab that answered, exactly as before (no query strip, no cross-tab following).
- **Timing:** the flag is known only once `loadSiteConfig` settles. `startAnalyticsAtBoot` runs after it and starts nothing else when the flag is off; a Share clicked before it settles takes the Off path (Sentry only), and boot then starts PostHog's shared mode if the flag turned out to be on.
- **`/privacy.html` is not behind the flag:** it is a static file every build deploys, so it is served on every site. Its opening says the PostHog counts, recordings and surveys are sent only where the site has switched them on, so it stays true with the flag off; a static page cannot read the flag.
- **Not behind the flag:** the Sentry trimming (sections 7 and 10), because it only removes collection and is right on every site; and the graphty-element API of section 8, because it is additive and inert unless a consumer listens, and flags gate behavior, not API.
- **Owner setup:** switch it on for production by adding `"usage-analytics"` to the `features` list in `graphty/sites/production.json` (the analytics ids are already there) and running a configuration-only promotion. Nightly would also need its own `analytics` block before switching it on there sends anything.

## 2. Decisions

All of these are two-way doors unless marked otherwise.

1. **Vendor ids live in `site.json`, not `VITE_*` env vars.** One build serves canary, nightly and production byte for byte. Without an id nothing loads, so dev, Storybook, vitest and the acceptance dry run (whose site is `unknown`) send nothing, with no extra code. No CI, nx-input or `.env` change is needed.
2. **Only `graphty/sites/production.json` gets ids at first.** That keeps launch numbers clean. Copying the block into `nightly.json` turns it on there.
3. **The anonymous counts go to the same PostHog project through a second, named posthog-js instance in `cookieless_mode: "always"`; the shared-mode instance stays as it is.** PostHog's free plan allows one project, and one project lets an agent read every count through PostHog's API. The two ways posthog-js 1.445.1 offers were compared from its source (paths under `graphty/node_modules/posthog-js/`):
    - One instance with `cookieless_mode: "on_reject"` and `opt_out_capturing_by_default: true` is cookieless while consent is pending or denied (`lib/src/consent.js:52-56`, `lib/src/posthog-core.js:411-414`). Its move to full tracking builds the session id manager and the recorder only inside `opt_in_capturing()`, and only when the instance is still cookieless at that moment (`posthog-core.js:4335-4365`). PostHog's consent marker is shared localStorage, so another tab's Share switches this tab out of cookieless at its next capture (`_syncCookielessIdentity`, `posthog-core.js:482-512`); a later `opt_in_capturing()` in this tab then skips that branch, and the tab has no session id and no replay until it reloads. In this mode every extension (autocapture, heatmaps, dead clicks, web vitals, and console-log capture switched on by remote config, which posts to `/i/v1/logs` past `before_send`) also runs while cookieless, held back only by `before_send`. And a page view captured in cookieless mode before the app could opt a sharing reader in would be reported in the wrong mode.
    - A named instance in `"always"` mode never reads or writes storage (`_is_persistence_disabled`, `posthog-core.js:4263-4266`; the persistence is built with reads off too, `:663`), ignores consent calls (`:4330-4333`), never builds a recorder (`:980`), never loads surveys (`@posthog/browser-common/dist/surveys.js:159`), and flags every capture with `$cookieless_mode: true` (`:1833-1836`). With autocapture, heatmaps, dead clicks, web vitals, page-leave and page view capture switched off in its options and `advanced_disable_flags: true`, it requests no remote config (`lib/src/remote-config.js:47-51`) and no `/flags` (`@posthog/browser-common/dist/feature-flags.js:685`, fed by `_shouldDisableFlags()` in `lib/src/posthog-featureflags.js:32`), so the only thing it can send is what the app captures. The shared-mode instance, its tests and its consent handling are unchanged. This is the chosen way.
    - Re-initializing one instance to switch modes is not possible: `init` on a loaded instance is a no-op (`posthog-core.js:614`).
4. **Do Not Track and Global Privacy Control stop the visit record, not the counts.** With either set, nothing is written to `graphty.visits.v1` and no `first_visit`, `return_visit` or `usage_data_shared` is sent. The page view and the action counts, which touch no storage, are still sent, because the agreed goal is that the anonymous mode counts everyone. This is flagged for the owner (section 12): honoring DNT and GPC fully would undercount by an unmeasured share, likely larger than usual for a Hacker News audience because Brave sends GPC by default.
5. **One consent switch covers both PostHog and Sentry.** It is the same disclosure and the same reader decision. Making "Report a problem" work without consent is launch-plan item 1, a separate issue.
6. **PostHog is one dynamic `import("posthog-js/full/no-external")`, made after first paint for every visitor, with `disable_external_dependency_loading`.** `startAnalyticsAtBoot` waits for the window `load` event (or runs at once when `document.readyState` is already `"complete"`), then for `requestIdleCallback` with `{ timeout: 2000 }` where the browser has it (so a page that keeps the main thread busy, such as the start screen's live HeroGraph, still loads it within two seconds of `load`), then imports. `startPostHog()` (a reader who already shares, or one who clicks Share before that moment) does not wait for it: it starts the same memoized import at once. Both instances come from that one chunk (about 231 KB gzip at 1.445.1), so a reader who shares later downloads nothing more. It never enters the landing chunks, and no PostHog script is fetched from its CDN. A slimmer entry for the anonymous mode alone (`dist/module.slim.no-external.js`, about 54 KB gzip) would load a second copy of posthog-js for every reader who shares; it is the upgrade if bounces before the chunk loads prove costly (risk R1).
7. **In shared mode PostHog keeps its anonymous id in `localStorage`, and `identify()` is never called in either mode.** This lets the sample-to-own-data funnel and retention work across visits for readers who opted in. It is disclosed, and turning sharing off deletes it in every open tab.
8. **PostHog masks everything.** All text in autocapture and replay is masked. In autocapture every element attribute is masked except one allowlisted control id (decision 15). In replay every attribute is masked except a short allowlist that carries no reader text (section 6). Sentry's error replay accepts only a list of attribute names to mask, so it masks a named list that also covers `name`, `href`, `download`, `label`, `for` and `id` (section 7). Inputs are masked, and the graph element, canvas, images, video and file inputs are blocked. Menus, tables, the inspector, notices and `aria-label`/`title` attributes all carry project, file and column names, and a selective mask would leak through whichever surface was missed. A replay shows a blank rectangle where the graph is, so the canvas events in section 4.2 are the only signal of what happens on the canvas.
9. **PostHog region is EU (`eu.i.posthog.com`).** One-way door: data cannot move between regions later. The owner confirms this when creating the project.
10. **The survey is a PostHog "API" survey drawn by the app with existing Mantine components.** PostHog's popover brings its own styling into a UI locked to Figma. PostHog still stores the questions and the targeting.
11. **Load facts come from a new graphty-element session event, `source:loaded`.** Each load door publishes it after its load commits, and it sends a kind and ids, never a name. Opening a project, undo, redo and restore publish none. It is a different event from the existing forwarded graph event `data-loaded`, which fires whenever data arrives for any cause (section 8.1). Without it the app would have to read `sources()` and work out the facts itself, which the architecture rules forbid.
12. **Exports and layout choices are recorded by the app, not by element events.** The element cannot tell an export from a preview: `DataOutput.tsx:471` calls `exportGraph` on every option change to preview losses. Likewise `layout.set` journal entries also come from the app's own `layout` attribute at boot, project and sample setup and the assistant. "The reader pressed Export and it finished" and "the reader applied a layout" are the app's own actions. The app reads the format or layout id from its own choice and computes nothing about the graph.
13. **Sentry keeps errors, replay-on-error and feedback.** It drops full-session replay, dead tracing config, release-health session pings, client reports, console breadcrumbs and the integrations listed in section 7. Its URL cleaning is tightened to the same rule as the analytics (cross-origin URLs become `"external"`), an error's message is treated as the reader's data (a graphty-element error is sent as its code, any other message cut at its first quote mark, as the quoted text may hold quotes of its own), the error replay is sent once per error and never turns into a session recording, and its replay masks the same attributes as PostHog's.
14. **The anonymous mode sends each event name at most once per page view; the shared mode sends every occurrence.** There are nine names (the page view, one visit event, six actions and `usage_data_shared`), so an anonymous page view sends at most nine events. The once-per-name set belongs to the page, not to a mode: the first occurrence of each section 4.1 name on a page carries `first_on_page: true` in whichever mode sends it, and a name already sent in one mode is never first again after a switch. Counting events with `first_on_page = true` across both modes therefore counts each page view once, with no de-duplication.
15. **Clickable controls carry a safe id that survives masking.** Controls that run a registered command render `data-ph-capture-attribute-control="<command id>"`. posthog-js copies that attribute into `$autocapture`, `$rageclick` and `$dead_click` properties as `control`, and `cleanPostHogEvent` keeps it only when the value is a registered command id or one of the app's fixed control ids. This is what makes clicks, rage clicks and paths readable with everything else masked.
16. **Every PostHog event names its mode** in the property `tracking`: `"anonymous"` or `"shared"`. At any moment one mode is current (`wanted` in `analytics.ts`, true while the reader shares), and `count()` hands each event to that mode's instance only.

## 3. Consent and data flow

```
boot (main.tsx): bootQuery = snapshot of location.search (before anything strips it)
                 loadSiteConfig().then(startAnalyticsAtBoot)
  startAnalyticsAtBoot(config):
  |-- readChannel()                   keep the cleaned channel params and the path in a module value
  |-- startUsageDataIfShared()        if stored answer is "share":
  |                                     stripQueryForRecorders()  remove every query param, synchronously
  |                                     initSentry()              errors, error replay buffer, feedback
  |                                     startPostHog()            wanted = true synchronously; shared instance after the import
  |-- startPageCounts(config)         if a PostHog key and the site's own host:
  |                                     count("$pageview")        once per load, into the mode current now
  |                                     first_visit or return_visit unless DNT/GPC
  |                                     then remove the four channel params from the address bar
  '-- after load + idle: import posthog-js once; init the anonymous instance (section 5); flush the buffer

Workspace (project element and session only, never the start screen's HeroGraph)
  useUsageEvents(element, session, store)
     element events --> count(name, props)   anonymous mode: first per name per page only
                                             shared mode: every time (first one marked first_on_page)
                    --> detail(name, props)  shared mode only
  app's own actions (export, layout, project open, command run) --> count() or detail()

answerUsageData("share")    -> count("usage_data_shared") (anonymous mode, unless DNT/GPC);
                               stripQueryForRecorders(); initSentry(); startPostHog()   -> shared mode from here
answerUsageData("declined") -> stopSentry(); stopPostHog()   (opt out, delete id, keep opt-out marker) -> anonymous mode
storage event in another tab: graphty.usageData.v1 became "share" -> the same start here (taking that tab's id;
                              while that tab has not saved one, this tab stays in the anonymous mode and waits);
                              became "declined" or was removed -> the same stop here
```

`usageData.ts` keeps its single `{ start, stop }` sender and its `setUsageSenderForTests` seam. Only the default sender changes:

```ts
const live = {
    start: () => {
        stripQueryForRecorders();
        initSentry();
        startPostHog();
    },
    stop: () => {
        stopSentry();
        stopPostHog();
    },
};
```

`stripQueryForRecorders()` (in `analytics.ts`) calls `history.replaceState` to drop every query param and the hash, keeping the path, but only when a recorder will actually start (a PostHog key in `site.json`, or a Sentry DSN as reported by `sentryConfigured()` in `sentry.ts`, which reads the same default config that `initSentry()` reads and which tests feed through the Sentry seam, section 10 item 16); otherwise it does nothing, so dev, vitest and Storybook keep their query. It runs synchronously before either recorder initializes, so neither Sentry's replay Meta event nor PostHog's records `?url=`, `?graphty-element-logging=` (which can carry a `remoteLogUrl`), `?features=` or anything else. Nothing in the app reads `location.hash`, so dropping it costs nothing. Readers of the query that run after boot read `bootQuery()` instead of `location.search`: `App.tsx:22` (`?demo`, read on every render) and `main.tsx` `logPageStart` (`?features`). `siteConfig.ts` and `parseLoggingURLParams` read before any strip. A consenting reader who reloads loses those params; they are developer and demo switches, and the shared-link case keeps working because the params are read before they are removed.

`usageData.ts` also listens for `storage` events on `graphty.usageData.v1`. When another tab writes "declined" or removes the key, this tab runs the live sender's stop; when another tab writes "share", it runs the start, taking the id that tab saved. If that tab has not saved its id yet (its posthog-js is still loading), this tab neither loads posthog-js nor sets `wanted`: its counts keep going to the anonymous mode until the id's own `storage` event arrives, and only then does it switch. A Share tab that closes or fails before saving an id therefore costs this tab nothing; it stays anonymous until it reloads. Without the listener, a second open tab would keep recording and PostHog's persistence would write `ph_<token>_posthog` back after the first tab deleted it.

Every existing test that installs a stand-in sender keeps working unchanged.

**Mode switching.** `wanted` (true while the reader shares) decides the mode, and only `count()` and `detail()` route events, so nothing else can report a page view twice:

- The page view is the app's own `count("$pageview")` at boot, sent once per load into the mode current at boot. Both instances run with `capture_pageview: false`, so neither PostHog instance sends one of its own, and a later switch sends none: a page view stays reported by the mode it started in.
- Share mid-page: events from then on go to the shared instance; the anonymous instance is no longer handed anything. Names already sent in anonymous mode are not `first_on_page` again.
- No mid-page (or another tab's No): `stopPostHog()` runs as before (opt out, delete the shared id, keep the opt-out marker); counts from then on go to the anonymous instance, once per name per page, skipping names already sent on this page in either mode.

**Before PostHog loads.** `count()` and `detail()` calls made before the instance of their mode is ready are kept in one page-lifetime buffer, each tagged with the mode current when it was made. The buffer holds at most 20 entries, but a page's first count of a section 4.1 name (the one carrying `first_on_page`) is always kept: there is at most one per name, and dropping it would leave the name marked sent, so the page would never count it in either mode. Anonymous entries are captured by the anonymous instance once it is ready; shared entries on the shared init if `wanted` is still true. On a stop, a shared entry carrying `first_on_page` is re-tagged anonymous (when the anonymous mode would have sent that name, under the same DNT/GPC rule for `usage_data_shared`) and sent once the anonymous instance is ready, so a No that comes before the shared instance loaded loses no page view; every other shared entry is dropped, and a dropped first count's name is unmarked. Anonymous entries are never moved into shared mode. If the posthog-js chunk fails to load (a network error, or a deploy that removed the hashed chunk), the start that asked for it is remembered and tried again on the next `count()` and on the window's `online` event, so the buffered page view still leaves once the chunk loads. Every browser keeps a failed module load in the page's module map and answers a later `import()` of the same URL with the same failure without a request (checked in Chromium, Firefox and WebKit), so each load after a failure asks for the file at a new URL, `?retry=<n>` (section 6). `startPostHog()` sets `wanted` synchronously, and boot calls `startUsageDataIfShared()` before `startPageCounts()`, so the page view, `first_visit`, `return_visit` and an early `sample_loaded` of a reader who already shared are tagged shared.

**Counts stream.** `analytics.ts` also exposes `onUsageEvent(listener)`, called with every `count()` and `detail()` (name and allowlisted props). `SurveyCard` uses it to pick its moment (section 4.4), so it never subscribes to the session itself.

**What `analytics.ts` may import.** `main.tsx` imports it statically, so it is part of the landing page. It imports only types and modules that are already on the landing page (the element's session entry already is, through `start/library.ts` `DEFAULT_LIMITS`), and never the workspace command registry, the frame or an element catalog. What only the workspace knows reaches it at runtime: `WorkspaceContext` calls `setCommandAllowlist(ids)` with the registered command ids once its registry is built, and the catalog checks (algorithm keys, `FormatId`, `LayoutId`, error codes) are applied by `useUsageEvents`, the export and layout handlers and `WorkspaceContext` before they call `count()` or `detail()`, all of which load with the workspace chunk. Until `setCommandAllowlist` has run (on the start screen), `cleanPostHogEvent` keeps `control` only for the fixed control ids and drops any other value.

## 4. Event taxonomy

### 4.1 Counted in both modes

These are the same names in both modes. `count()` sends each to the current mode only (section 3): in anonymous mode at most once per name per page view, in shared mode on every occurrence. The first occurrence of a name on the page carries `first_on_page: true` in either mode. Every event also carries `tracking` (`"anonymous"` or `"shared"`), `site`, the channel properties below and, outside DNT and GPC, `visit`. These are the only events the anonymous mode ever sends.

Mapping rules for `source:loaded`: the event's `kind` is always the `LoadedSource.kind` that `session.data.sources()` records for that source (section 8.1). A load counts as a sample when its kind is `"sample"` (catalog datasets and generators, and the app's own sample loads, which pass `origin: "sample"`) or when it carries a `sample` field (a network example from `loadExample`, whose recorded kind stays `"server"`). A sample maps to `sample_loaded`. Its `sample` is the event's `sample.datasetId`, `generatorId` or `exampleId`, each checked against its own allowlist; when the load was a start-screen tile, the app's own id from `callerKey` (`"sample:<StartSample.id>"`) checked against the app's sample list. Any other load maps to `own_file_opened`: kinds file and url with `format`; kind server as `{format: "other", via: "server"}` (the source id is not sent); kind join as `via: "join"`. The event's `source` key and `sourceId` are never forwarded to any vendor.

A Recent-project reopen is not `own_file_opened`. It is sent to PostHog only, as `project_reopened` (section 4.2).

**Visit bucket.** The localStorage key `graphty.visits.v1` holds `{ "first": "YYYY-MM-DD", "last": "YYYY-MM-DD" }` in local calendar dates. Every access is wrapped in try/catch. `startPageCounts` never reads or writes it when there is no PostHog key or the host is not allowed (section 5). Under DNT or GPC it removes the key and sends no visit event, so a record written before the signal was switched on is not kept.

- No record: send `first_visit` and store first = last = today.
- A record whose `last` is not today: send `return_visit` with `days = visitBucket(first, today)`, then store last = today. This sends at most one per day.
- A record whose `last` is today: send nothing.
- Storage blocked: send the page view only.
- A record whose last visit is older than 395 days, or that does not parse, is reset.
- A record whose last visit is dated up to two days after today (a trip west across time zones) was already counted: nothing is sent and the record keeps its dates. A date more than two days ahead came from a clock that was wrong, and the record is reset as unreadable; keeping it would stop every count from that browser until the real date caught up.

Only the bucket leaves the machine. The dates never do.

**Channel.** `cleanUrl(href)` turns a same-origin URL into its path plus only the `ref`, `utm_source`, `utm_medium` and `utm_campaign` params. A value is kept only when it is in the app's short channel list (`KNOWN_CHANNELS` in `analytics.ts`: `hn`, `reddit`, `x`, `bluesky`, `mastodon`, `linkedin`, `github`, `newsletter`, `email`, `producthunt`, extended by editing the list); any other non-empty value is sent as `"other"`, so a per-recipient tracking value such as `utm_campaign=u_8f3k2q9` never leaves the page. It drops every other param and the hash. Any other URL becomes `"external"`. `readChannel()` stores the path and the four cleaned params in a module value at boot. Right after `count("$pageview")` (which reads the saved value, whenever its instance sends it), `history.replaceState` removes those four params from the address bar (keeping the path, the hash and every other param), so a reader who shares a link does not pass their channel on. PostHog never sees them in the address bar; `cleanPostHogEvent` adds them to every event of either mode as `channel_ref`, `utm_source`, `utm_medium` and `utm_campaign`.

**Budget.** PostHog's free plan allows 1M events and 5k replays a month for the one project, both modes together. A front-page Hacker News day (about 50k visitors at 3-6 anonymous events each) is 150k-300k events, so a launch month fits with room for the shared mode, whose readers send far more events each. Past the limit PostHog drops events unless a billing limit above zero is set; that is the owner's choice (section 12).

### 4.3 Funnels, paths and insights (owner builds them in PostHog, no code)

An algorithm's suggested styles paint inside the run's own journal entry (`algo.run`), so after a single Analyze run the only style entry is the reader's own re-coloring. `suggested: true` appears only on the separate style entries of a batch release and of an explicit `applySuggestedStyles()` call (section 8.3).

1. Core analysis: (`sample_loaded` or `own_file_opened`) -> `algorithm_run` (succeeded) -> `graph_action` (op `style.encode` or `style.patch`, `suggested` not set) -> `export_done`. Both ops are needed: re-coloring by a result from the Style panel's value picker updates a layer (`style.patch`), and only "Show anyway" on the "Hidden by your layer" notice sends `style.encode`. A second version without the third step measures load -> result -> export.
2. Own data straight in: `own_file_opened` -> `algorithm_run` -> `export_done`.
3. Sample to own data: `sample_loaded` -> `own_file_opened`, within 7 days.
4. Layout exploration: `own_file_opened` -> `layout_changed` -> `graph_action` with op `view.dimension`.
5. Canvas use: `own_file_opened` -> `canvas_selected` -> (`algorithm_run` or `export_done`).
6. Struggle board:
    - `load_failed` by `code`
    - `algorithm_run` failed by `code`
    - `command_failed` by `command` and `code`
    - `$rageclick` and `$dead_click` by `control`
    - `command_run` with `command` `history.undo`
    - a saved replay filter: sessions with a load but no `algorithm_run`
7. Paths: a PostHog Paths insight over custom events only (`sample_loaded`, `own_file_opened`, `command_run`, `panel_opened`, `graph_action`, `algorithm_run`, `layout_changed`, `export_done`), with `command_run` broken down by `command` and `panel_opened` by `panel`. Page-view paths are meaningless here: the app has no router, so there is one `$pageview` per load.

Break funnels down by `channel_ref` and by `use_case`, with PostHog's breakdown attribution set to "last touch". `use_case` is on every event after the answer and on every event of later visits. A funnel whose last step comes after the answer gets the reader's use case; a reader who never answers shows as "none". Person profiles stay off (`identified_only` with no `identify()` in shared mode, `never` in anonymous mode), so no cohort or person property is used. Scale any shared-mode rate by the opt-in rate (section 4.1) before reading it as the whole audience's.

**Whole-audience insights** use both modes and need no de-duplication:

- Visitors, channels and returns: `$pageview`, `first_visit` and `return_visit` by `channel_ref`, `utm_*` and `days`, with no filter on `tracking`.
- Pages that did something: section 4.1 events with `first_on_page = true`, for example the share of page views with `sample_loaded` and with `own_file_opened`, and with `algorithm_run` and `export_done`.
- Opt-in rate: `usage_data_shared` over `first_visit`, as a formula insight.
- Breakdowns by `tracking` show the split between modes.

A funnel or a unique-visitor count across days over anonymous events is not meaningful: an anonymous visitor's id changes every day and between modes (risk R8), so weekly and monthly uniques overcount and a reader who shares mid-page appears as two people. Funnels and retention stay shared-mode insights (filter `tracking = shared`).

### 4.4 Surveys

Surveys are created in PostHog as type "API". The app draws them with `SurveyCard.tsx`.

- "What are you trying to do?"
    - Single choice: Explore my own network data / Analyze a network for research or work / Make a figure for a paper or talk / Teach or learn about graphs / Journalism or investigation / Just looking around / Other (optional text).
    - When the reader answers, the app stores the choice id in localStorage `graphty.surveys.v1`, and `cleanPostHogEvent` adds it as `use_case` from then on, on this and later visits. The "Other" text is sent only as the survey response, never as `use_case` (which is `"other"`).
- "How easy was it to get this export?", a 1-5 rating, asked only at the first `export_done` of a page view.

Each survey is found by a fixed name kept in `analytics.ts` (`SURVEY_NAMES`: `use_case` for the first, `export_ease` for the second); the owner gives the PostHog surveys exactly these names (section 12).

`SurveyCard` is mounted in `Workspace.tsx`.

- It renders nothing unless `postHog()` returns a client. `postHog()` returns undefined whenever sharing is off, including after a stop on the same page, so the card never asks PostHog for surveys after the reader withdrew.
- It listens on `onUsageEvent` (section 3). Each moment belongs to one survey:
    - `use_case`: the first of the first succeeded `algorithm_run`; a `load_failed` or a failed `algorithm_run`; or three minutes (a `setTimeout` started by a `sample_loaded` or `own_file_opened`, cleared by an `algorithm_run`) after a load with no `algorithm_run` since.
    - `export_ease`: the first `export_done`.
- At a moment it calls `posthog.getActiveMatchingSurveys(cb)` and shows only the survey with that moment's name, and only if its id is not in `graphty.surveys.v1`. It never falls back to another active survey. At most one survey is shown per page view, so a reader asked `use_case` is asked `export_ease` at an export on a later visit.
- A shown, answered or dismissed survey id is stored in `graphty.surveys.v1` and never shown again. The answered `use_case` choice is stored there too; turning sharing off deletes the stored choice and keeps the ids, so a reader who shares again is not asked again and no old answer returns as `use_case`.
- It uses the same pinned `<aside>` pattern as `UsageDataCard`, built from existing components.
- Next to the text box it shows: "Do not paste data from your graph. What you type here is sent."

## 5. Anonymous mode (exact)

`startAnonymous()` in `analytics.ts` runs once per page, after first paint (decision 6), only when `site.json` has a PostHog key and host and the page is on its site's own host (`onOwnHost`, below). It awaits the one memoized `importPostHog()` promise and creates a named instance, whatever the reader's answer, because a reader who withdraws later needs it. When both instances start on one page it is created first, before the shared `init`; with the storage options below the order does not matter, and the reload test pins the worse order (section 11):

```ts
anonymous = posthog.init(
    key,
    {
        api_host: host, // https://eu.i.posthog.com
        defaults: "<the same pinned defaults date as the shared instance>",
        cookieless_mode: "always", // no storage, no id from the page, $cookieless_mode on every event
        disable_persistence: true,
        persistence: "memory", // see 'What is stored': without it init deletes the shared instance's stored id
        persistence_name: "graphty_anonymous",
        person_profiles: "never",
        disable_external_dependency_loading: true,
        advanced_disable_flags: true, // no remote config request and no /flags request
        advanced_disable_feature_flags: true,
        capture_pageview: false, // the app's own count("$pageview")
        capture_pageleave: false,
        autocapture: false,
        rageclick: false,
        capture_dead_clicks: false,
        capture_heatmaps: false,
        capture_exceptions: false,
        capture_performance: false,
        disable_session_recording: true,
        disable_surveys: true,
        disable_product_tours: true,
        disable_conversations: true,
        disable_scroll_properties: true,
        save_referrer: false,
        save_campaign_params: false,
        before_send: (event) => cleanPostHogEvent(event, "anonymous"),
    },
    "anonymous",
);
```

Every option name is checked against `@posthog/types` 1.425.1, the types posthog-js 1.445.1 resolves (`posthog-config.d.ts`). With these options no extension of this instance captures anything, and init sends nothing: the only requests it makes are the batched `/e/` posts of what `count()` hands it. `before_send` runs on every capture (`posthog-core.js` `capture`, after `calculateEventProperties`), so `cleanPostHogEvent(event, "anonymous")` sees each event:

1. Return `null` unless the name is `$pageview` or a section 4.1 name, and unless the event carries `$cookieless_mode: true` (proof it was built in cookieless mode).
2. Delete `$set`, `$set_once`, `title` and `$title`.
3. Clean URLs exactly as the shared mode does (section 6, step 5): `$current_url` becomes the boot path plus kept channel params, `$pathname` the boot path alone, `$referrer` an origin, `$referring_domain` a host.
4. Keep only: the event's own allowlisted keys (section 4.1); `token`, `distinct_id`, `tracking`, `site`, `channel_ref`, `utm_source`, `utm_medium`, `utm_campaign`, `visit`, `first_on_page`; and these `$` keys: `$cookieless_mode`, `$raw_user_agent`, `$host` and `$timezone` (with the IP, the inputs of PostHog's server hash: its ingestion drops a cookieless event that lacks the user agent, IP or host, and picks the day's salt by `$timezone`), `$current_url`, `$pathname`, `$referrer`, `$referring_domain`, `$browser`, `$os`, `$device_type`, `$lib`, `$lib_version`, `$insert_id`, `$time`, `$config_defaults`, `$process_person_profile`. Everything else is dropped, including `$browser_version` and `$os_version` (Umami never recorded versions, and the server hash does not use them), `$screen_*`, `$viewport_*`, `$browser_language*`, `$timezone_offset`, `$device`, `ph_keyword` and any key a later posthog-js adds.
5. Add `tracking: "anonymous"`, `$geoip_disable: true` and the super properties of section 4.2 except `use_case` (a survey answer is shared-mode data).

`count()` hands the anonymous instance a section 4.1 event only while `wanted` is false and only if the name is not yet in the page's once-per-name set; `detail()` never hands it anything.

**What is stored.** Nothing, by PostHog, in cookies, localStorage or sessionStorage, and nothing of the shared instance's is removed. Two options are needed for that, and `cookieless_mode: "always"` alone is not enough. In `"always"` mode the persistence reads nothing (`posthog-core.js:663`, `:4263-4266`), there is no session id manager (`:692-705`), and consent calls are ignored, so no opt-out marker is written (`:4330-4333`, `:4406-4409`). But the disabled persistence's constructor calls `update_config` (`posthog-persistence.js:235`), whose `set_disabled(true)` (`:1707`, `:1753-1757`) runs `remove()`, which deletes the persistence's storage name from its store, cookie and localStorage, plus every `<name>__<group>` localStorage entry (`:1468-1490`). The name is `ph_<token>_posthog` unless `persistence_name` is set (`:108-118`), and both instances share the token, so without a name of its own the anonymous init would delete the shared instance's `distinct_id`, `$device_id`, session and flags entries on every load. The default store (`localStorage+cookie`, `posthog-core.js:221`) would also build a sessionStorage sibling (`:669`) that removes `ph_<token>_posthog` from sessionStorage, and its support probes write and remove test keys. So the anonymous options set `persistence_name: "graphty_anonymous"`, which points every removal (including the `ph_<name>_session_registered_properties` key, `:676-686`) at keys nobody uses, and `persistence: "memory"`, which makes the session persistence the same in-memory object, builds no sibling. Two things still touch localStorage, and neither leaves anything behind. posthog-js's own localStorage support check (`storage.js:223-228`, run by the consent manager and the `debug` config whatever the options) writes `__mplssupport__` and removes it at once, once per page; no option turns it off. The toolbar extension, which the `full/no-external` bundle includes, would write and remove a `test` key on every init (`extensions/toolbar.js:64-69`), so the anonymous options leave it out with `__extensionClasses: { toolbar: undefined }` (`posthog-core.js:964`, `:1018`). The real-chunk test spies on `setItem` and `removeItem` and pins exactly that: `__mplssupport__` is the only key PostHog writes, and it removes only that key, `ph_debug` and keys under its own `graphty_anonymous` name. The one exception left is PostHog's own toolbar on the shared instance, which a PostHog project member can launch with a `__posthog=` link and which writes `_postHogToolbarParams` (`lib/src/extensions/toolbar.js:146`); no reader link carries it. The app's own `graphty.visits.v1` is unchanged (section 4.1).

**What PostHog does with it** (PostHog docs, "Cookieless tracking", and its ingestion source, `nodejs/src/ingestion/common/cookieless/cookieless-manager.ts` in PostHog's repository, read on 2026-11-18). Events flagged `$cookieless_mode` are dropped unless the project's cookieless server hash mode is on (section 12). Ingestion computes the distinct id as hash(daily salt, project, IP, root domain of `$host`, `$raw_user_agent`), with the salt chosen by the calendar day in the event's `$timezone`. Each salt is a random 128-bit value kept in Redis while its calendar day is still valid for ingestion: from 12 hours before the UTC day starts until 14 + 72 hours after it ends (`isCalendarDateValid`, `MAX_POSITIVE_TIMEZONE_HOURS = 14`, `MAX_SUPPORTED_INGESTION_LAG_HOURS = 72`), so about four days, then deleted by its Redis TTL. While it lives, PostHog holds what it needs to recompute an id from a known IP and User-Agent; once it is gone, the id can no longer be traced back to the browser. A new salt each day means ids cannot be linked across days. It then strips `$ip` and `$raw_user_agent` before the event is stored, and before GeoIP and bot-detection transformations run, so no location is ever added. Sessions are derived on the server (in the stateless mode, one per id per day).

**DNT and GPC** affect only the visit record (decision 4). The anonymous instance keeps `respect_dnt` at its default, false, so the counts are still sent.

**Own host.** The same host check (`onOwnHost` in `analytics.ts`) gates both modes: `production` maps to `graphty.app`, `nightly` to `nightly.graphty.app`, `canary` to `canary.graphty.app`. Off the site's own host nothing is imported, neither instance starts, and Share starts neither PostHog nor Sentry. A local build or a studio server that answers with a real site's `site.json` therefore never sends into that site's project. It also means Sentry never starts on `localhost`, a dev server or Storybook: a story that shows Sentry's dialogs calls `initSentry` itself. The hostname and the DNT/GPC reads go through the test seam (section 10, graphty app item 3), so tests on `localhost` can reach the positive cases.

## 6. Shared mode: PostHog setup (exact)

The shared mode is posthog-js's default instance, initialized only after Share, from the same memoized import the anonymous mode made (decision 6). Loading uses the documented entry `posthog-js/full/no-external` (its `package.json` points at `dist/module.full.no-external.js`; types come from `dist/module.d.ts`), imported by URL: `importPostHogModule()` in `analytics.ts` takes the file's URL from `posthog-js/full/no-external?url` and runs `import(url)`. The file is self-contained (it has no imports), so Vite emits it unchanged as one hashed file in `dist/assets`; going by URL is what lets a load after a failure ask for `?retry=<n>` (section 3), and a load that succeeded always uses the plain URL, so every caller gets the one module. It inlines the recorder, surveys, web vitals and dead clicks and loads nothing external. It is one lazy file of about 790 KB raw and 231 KB gzip at posthog-js 1.445.1, the pinned version. PostHog contacts two hosts: the ingest host (`eu.i.posthog.com`) and the assets host (`eu-assets.i.posthog.com`) for the remote config JSON.

```ts
posthog.init(key, {
    api_host: host, // https://eu.i.posthog.com
    defaults: "<an explicit dated defaults string, pinned with the version>",
    persistence: "localStorage", // no cookies
    person_profiles: "identified_only", // identify() is never called: no person profiles
    opt_out_capturing_by_default: true, // a missing opt-in marker means "out"
    disable_external_dependency_loading: true,
    advanced_disable_flags: false, // surveys need the remote config call
    capture_pageview: false, // the app's own count("$pageview") at boot (section 3)
    capture_pageleave: true,
    autocapture: { dom_event_allowlist: ["click", "change", "submit"], capture_copied_text: false },
    mask_all_text: true,
    mask_all_element_attributes: true, // autocapture only; data-ph-capture-attribute-* still collected
    rageclick: true,
    capture_dead_clicks: true,
    enable_heatmaps: true,
    capture_exceptions: false, // Sentry owns errors
    capture_performance: { web_vitals: true, network_timing: false },
    enable_recording_console_log: false, // log lines can hold graph values
    save_referrer: false,
    save_campaign_params: false, // else $initial_person_info (full referrer, boot URL) rides in every /flags body
    opt_out_persistence_by_default: true, // opted out = persistence disabled and ph_<token>_posthog removed
    session_recording: {
        captureJsonLd: false, // a recorder option; on by default from the 2026-08-30 defaults
        maskAllInputs: true,
        maskTextSelector: "*",
        maskAttributeFn: maskEveryAttribute, // replay: attributes are NOT masked by default
        blockSelector: 'graphty-element, canvas, img, video, input[type="file"]',
        recordHeaders: false,
        recordBody: false,
        maskCapturedNetworkRequestFn: (request) => ({ ...request, name: cleanUrl(request.name) }),
    },
    disable_surveys: false,
    before_send: cleanPostHogEvent,

posthog.opt_in_capturing(); // only if `wanted` is still true
```

`input[type="file"]` is blocked because `maskAllInputs` masks every input value except file inputs. `compact-mantine/src/components/inputs/pickFiles.ts:41-66` appends a file input to `document.body` and its change listener fires while it is still in the DOM, so without the block the recorder would capture `C:\fakepath\<file name>`. Both `start/open.ts:7` and `project/files.ts:83` open files through it.

Both graphty-element hosts in the app get `className="ph-no-capture"`: the project's in `frame/ElementHost.tsx` and the start screen's in `start/HeroGraph.tsx`. Autocapture then ignores clicks on the canvas, and because `ph-no-capture` is also PostHog's default replay `blockClass`, both hosts are blank in replay.

There is no `register()` call. Super properties (section 4.2) are merged into every event inside `cleanPostHogEvent`, because posthog-js captures `$pageview` and `$opt_in` synchronously inside `init` and `opt_in_capturing()`, before any `register()` could run.

`maskEveryAttribute(key, value)` is an allowlist. It returns the value unchanged only for `class`, `role`, `type`, `tabindex`, `disabled`, `style`, the `aria-*` state attributes (`aria-expanded`, `aria-selected`, `aria-checked`, `aria-pressed`, `aria-disabled`, `aria-hidden`, `aria-current`, `aria-haspopup`) and `data-ph-capture-attribute-control`, and returns `"*"` for every other attribute. An attribute that starts carrying reader text later is therefore masked without anyone listing it; `name` already does (`Fields.tsx:695` builds it from a field name). `style` is kept because masking it breaks the replay's layout, and it holds only CSS. The app has over 100 interpolated `aria-label` and `title` attributes carrying project, source, column and label names (for example `RecentProjects.tsx:30`, `CanvasOverlays.tsx:318`, `SourceRow.tsx:274`, `LabelCard.tsx:292`), so this mask is required.

`cleanPostHogEvent(event, "shared")` runs these steps in order and returns the event or `null` (the anonymous mode's steps are in section 5):

1. If `wanted` is false, return `null`. This guard does not depend on PostHog's own consent state. An event carrying `$cookieless_mode` is also returned as `null`: the shared instance never runs in cookieless mode.
2. Drop the event unless its name is allowlisted. `$` names allowed: `$pageview`, `$pageleave`, `$autocapture`, `$rageclick`, `$dead_click`, `$web_vitals`, `$$heatmap`, `$snapshot`, `$opt_in` and the survey events. Own names: those in section 4. Any other name, including one a later defaults date turns on, is dropped.
3. Drop `$autocapture`, `$rageclick` and `$dead_click` whose element chain contains `graphty-element` or `canvas`.
4. Delete `$set`, `$set_once`, `title` and `$title` (the document title can hold a project name). Merge the super properties from section 4.2, `tracking: "shared"` among them.
5. For every event except `$snapshot`, clean by value at any depth of `properties`: every string that parses as an `http:` or `https:` URL is replaced by `cleanUrl` of it. Every key of `$heatmap_data` is replaced by `cleanUrl` of it. `$referrer`, `$initial_referrer` and `$referring_domain` become origins. This covers `$current_url`, `$pathname`, `$initial_current_url`, `$session_entry_url`, `$prev_pageview_pathname`, `$external_click_url` and the `$current_url` inside each `$web_vitals_*_event`, and any key a later posthog-js version adds. `$snapshot` is skipped: walking every recording batch costs CPU on each flush, and rewriting stylesheet and font URLs to bare origins breaks replay styling. The replay's own URLs are protected by the address-bar strip (section 3) and `maskCapturedNetworkRequestFn`.
6. For every event, `$` events included, drop every non-`$` property key that is neither in that event's allowlist nor one of `token`, `distinct_id`, `tracking`, `first_on_page`, `site`, `channel_ref`, `utm_source`, `utm_medium`, `utm_campaign`, `visit`, `use_case`. For `$` events the allowlist is empty except `control` on the autocapture events, so keys posthog-js adds on its own, such as `ph_keyword` (search terms parsed from the referrer on every capture), are dropped. Keep `control` only when it is in the command allowlist injected by `setCommandAllowlist` (section 3) or a fixed control id, and drop it otherwise. `$`-prefixed keys are kept, because `$session_id`, `$window_id`, `$lib` and the rest link events to sessions and replays. For the survey events, the allowlist is `$survey_id`, `$survey_name`, `$survey_response` and any key starting `$survey_response_`.

The lifecycle mirrors Sentry's page singleton:

- `startPostHog()` does nothing without a key, then sets `wanted = true` synchronously.
    - If PostHog was already initialized on this page, it calls `reset(true)`, then `opt_in_capturing()`, then `startSessionRecording()`. `reset(true)` makes a new device id as well as a new distinct id: opt-out removed the stored ids but posthog-js still holds them in memory, and a plain `reset()` keeps `$device_id` and saves it again, linking the reader to what was recorded before they said No. The flags request that `reset()` makes is fine here: the reader has just shared.
    - Otherwise it awaits one memoized import promise (a second start while the import is in flight reuses it). It sets an `initialized` flag synchronously when it calls `init`, so two starts give exactly one `init`. It calls `init` only if `wanted` is still true, so a No that arrives before the chunk loads wins. After `init` it calls `opt_in_capturing()` and flushes the buffer from section 3. The query was already stripped by the sender (section 3).
- `stopPostHog()` sets `wanted = false` and empties the buffer of shared entries, moving each first count to the anonymous mode as section 3 says; from then on `postHog()` returns undefined. If PostHog was initialized, it calls `stopSessionRecording()` and `opt_out_capturing()`. It never calls `reset()`: in posthog-js 1.445.1 `reset()` always ends with `reloadFeatureFlags()`, which posts a new `distinct_id`, `$device_id`, person properties and the time zone to `/flags`, and that request is not a capture, so neither the opt-out nor `before_send` stops it. Deleting the id is persistence's job: with `opt_out_persistence_by_default: true`, `opt_out_capturing()` disables persistence and removes `ph_<token>_posthog` itself, and every later save (a debounced save, a session-id touch, a survey cache write) writes nothing. As a backstop it then removes every other `ph_`-prefixed key in localStorage and sessionStorage, keeping the `__ph_opt_in_out_<token>` marker, which says "out". The backstop also removes PostHog's survey records, `seenSurvey_*`, `inProgressSurvey_*` and `lastSeenSurveyDate`: capturing "survey sent" or "survey dismissed", which the survey card does, makes posthog-js write `seenSurvey_<id>` straight to localStorage before `before_send` runs and whatever the persistence setting (`posthog-core.js:1652-1660`), and only its surveys `reset()` would delete it. It also deletes the stored `use_case` choice from `graphty.surveys.v1` (section 4.4). Every step is best effort, inside try/catch.

**Events captured before No.** An event captured while consent held may still be sent after the reader withdraws. posthog-js batches captures in a request queue that flushes every few seconds, and a failed send waits in a retry queue; `opt_out_capturing()` stops new captures but drains neither, and posthog-js offers no public call that drops them. So the last few seconds of events captured before the stop, the `$autocapture` of the No click itself included, can still go out, under the id that was just deleted from storage. They were captured with consent, nothing captured after the stop is sent, and the privacy page says so ("How to turn it off"). Sentry is disabled at once instead of closed (section 7), so it sends nothing captured after the stop either.

Three independent layers keep a withdrawn reader's events from being captured in every tab: PostHog's own opt-out marker, `opt_out_capturing_by_default` (a lost marker still means out), and step 1 of `cleanPostHogEvent`, which the `storage` listener (section 3) flips in each other open tab. Requests that are not captures (feature flags, surveys) are kept off by never calling `reset()` or `reloadFeatureFlags()` after a stop and by `postHog()` returning undefined, so no app code asks the client for anything; the real-chunk test pins this (section 11).

## 8. graphty-element API addition (additive, no owner approval needed)

All of the following are additive: one new session event and its DOM mirror, one optional `ImportOptions` field, one optional `JournalEntry` field, one optional `RunChange` field, one optional `SelectionDelta` field and one new session event for the camera.

### 8.1 `source:loaded`

```ts
/**
 * A load added a source to the graph: one event per source added.
 * Published by every load method after its load commits.
 * Not published by opening a project, by undo, redo or restore, or by
 * `runPendingSourceLoad`, which fills a source a project already listed.
 * Carries no contents; `source` is whatever key the load was given.
 * Unlike the graph event `data-loaded`, which fires whenever data arrives for any cause,
 * this fires only for a load a caller asked for.
 * Mirrored to the DOM as `graphty-source-loaded`.
 * @since <next minor>
 */
"source:loaded": SourceLoaded;

export interface SourceLoaded {
    /** The source's key in `session.data.sources()`. */
    readonly source: SourceKey;
    /** The source's `LoadedSource.kind`, exactly as `session.data.sources()` records it. */
    readonly kind: LoadedSourceKind;          // "file" | "url" | "server" | "sample" | "join"
    /** For kinds "file" and "url": the format read, named or detected; absent when none was settled. */
    readonly format?: FormatId;
    /** For kind "server", and for a sample read from a network source: the source id. */
    readonly sourceId?: string;
    /** Whether the load replaced the graph or merged into it. */
    readonly mode: "replace" | "merge";
    /** Present when the load was a catalog sample: a dataset, a generator or a network example (whose kind stays "server"). */
    readonly sample?:
        | { readonly datasetId: string }
        | { readonly generatorId: string }
        | { readonly exampleId: string };
    /** The caller's own `ImportOptions.callerKey`, echoed unchanged. */
    readonly callerKey?: string;
    /**
     * Present when the source was not added but replaced in place, under the same key, with
     * mode "merge": "replaceSource" for a newer copy, "reloadSource" for the same input read
     * again with other choices (`reloadSource`, `remap`).
     */
    readonly replaced?: "replaceSource" | "reloadSource";
}
```

The app counts a `replaced: "replaceSource"` (Replace with a newer copy) as an own file opened, and skips `replaced: "reloadSource"`, which reads the same input again.

**Where it is emitted.** By each load door itself, after its command resolves as committed: `import` (inline and through `importVia`), the draft load, `loadDataset`, `generate`, `loadExample`, and `import` of a network source (`sources/load` `importSource` through `hostInTurn`). Each door already holds its own facts in its closure: the format it read, `mode: modeOf(command)`, `{ dataset }` (data.ts:1360) as `datasetId`, `{ generator }` (data.ts:1309) as `generatorId`, never `baseUrl` or `params`. It calls one private `SessionData` helper, `publishLoaded(record, facts)`, through the publish handle the class's other events use; the `sources/load` doors reach it through the host that `hostInTurn` hands them. `loadExample`, and an `import` of a `readExample` result, keep the kind the source records (`"server"`, unless the caller passed `origin`) and add `sample: { exampleId }` and `sourceId`. A consumer can tell a network example from the reader's own data, and the event never disagrees with `sources()`. Nothing changes in what `sources()` returns.

Nothing new goes on any command: the facts never enter the journal or a saved project, and `callerKey` is not saved.

Why not the sources slice: a project open is an ordinary `session.transaction("Open project", ...)` whose `importInto` runs `data.setSource` with the whole saved source list (`projectFile.ts:1644-1649, 2970-2990`; `commands/data.ts:1305-1307`), and its cause is `"command"`, not `"restore"`. Emitting on writes to the slice would publish one `source:loaded` per saved source on every Recent reopen, picked project file and autosave restore. The project path never calls a load door, so it publishes none.

**Relation to `data-loaded`.** The element already forwards a graph event `data-loaded` (`GraphDataLoadedEvent`, `events.ts:172-189`, emitted at `DataManager.ts:1394`). It says data arrived in the graph, for any cause including undo, redo and restore (its `cause` field). `source:loaded` says a load method a caller invoked added a source, and never fires for history or a project open. Extending `data-loaded` instead would put caller facts (`callerKey`, sample ids) on an event that also fires for undo, and every listener would have to filter by cause. `docs/guide/events.md` gets one line on each: use `source:loaded` to react to a load you or the reader asked for, `data-loaded` to react to the graph's data changing for any reason. `data-loaded` is not deprecated.

**Failures** stay on the existing `progress:changed` (task `"load"` or `"prepare"`, phase `"end"`, `error.code`).

### 8.2 `ImportOptions.callerKey`

```ts
/** An opaque value the caller chooses; the load does nothing with it but echo it as `SourceLoaded.callerKey`. */
readonly callerKey?: string;
```

It is declared on `ImportOptions`, the options base that `LoadChoices` and `DatasetLoadOptions` extend and that `generate` takes directly, so `import`, the draft load, `loadExample`, `loadDataset` and `generate` all accept and echo it. One generic echo field rather than analytics-shaped inputs: any consumer can tag a load and recognize it on the event. The app's start-screen sample tiles load by URL (`openSample`, `open.ts:391-396`), so the element has no catalog id for them; the app passes `callerKey: "sample:<StartSample.id>"`. The app's `openAgain` (`open.ts:236-263`, a reload that came before autosave wrote anything) passes `callerKey: "reopen"` to every load door it re-runs, so a reload is not counted as a new load. The name ends in `Key`, which the api-report plain-string rule accepts.

### 8.3 `JournalEntry.trigger`

```ts
/**
 * Why the session ran this command, when it was not a direct call.
 * "suggestion": an algorithm's suggested styles, applied as their own entry.
 * "project": one of the commands that opening a project, or a graphty document that is not one, ran.
 * "load": one of the commands a load ran (the import and the configuration it settled beside it).
 * OPEN UNION: triggers may be added in a minor release.
 */
readonly trigger?: "suggestion" | "project" | "load";
/**
 * The caller's own key for the work this command belongs to, echoed unchanged: a load's
 * `ImportOptions.callerKey`, or a transaction's `TransactionOptions.callerKey`.
 */
readonly callerKey?: string;
```

It is named `trigger`, like `RunChange.trigger` (section 8.4), because `cause` elsewhere in the public API means what moved the state (command, undo, redo, restore, user, api).

`"suggestion"` is set only where suggestion commands become separate journal entries: the batch hold release (`RunsApi.ts:3099`, `await via(suggestionCommand(...))` inside a transaction) and the public `Graph.applySuggestedStyles(algorithmKey)` method (`Graph.ts:4476-4497`), which a caller invokes to apply an algorithm's suggestions after the fact. A single run with `applySuggestedStyles: true` (the app's `analyze/run.ts:99` and `data-place/Runs.tsx:192`) paints inside the run's own draft (`RunsApi.ts:2265, 2505`; one step, one undo, per `autoApply.ts`), so its paint rides in the `algo.run` entry and needs no cause; the reader's own re-coloring after it is already the only style entry.

`"project"` is set on every member entry of the `project.open` transaction and of the `document.open` transaction that opens a graphty document that is not a project (styles, notes or a graph alone). Without it those reach `journal:appended` as ordinary entries, so an open would look like a burst of reader actions (`style.encode`, `data.apply` and others). Neither open publishes `source:loaded`; the app counts a picked or dropped `.graphty` file, project or document, as `own_file_opened {format: "graphty", via: "file"}` from the open's own report.

`"load"` is set on every entry a load door runs (`data.import`, `loadExample`, `loadDataset`, `generate`, a draft's `load`, `replaceSource`, `reloadSource`, and the renderer's own loads), so the configuration a load settles beside its import is not read as the reader's.

Set by `TimeApi.ts` `rerunAll` (2368-2376), which runs for every window move under the `results: "rerun"` policy (3254-3256, whether from playback, a manual step or a window drag) and when the setting flips to re-run (2933-2935). ### 8.6 `camera:gesture-end`

```ts
/** A reader's camera gesture on the canvas ended: once per gesture, never per frame. */
"camera:gesture-end": { readonly kind: "orbit" | "pan" | "zoom" };
```

Published by the camera input controllers. A gesture's end is defined by input, never by time:

- Pointer (orbit, pan, pinch): the pointer up that ends the drag.
- Wheel: a run of wheel events ends when the zoom's inertia reaches rest (velocity damped to zero). A wheel event that arrives before rest belongs to the same run. Wheel events dispatched in one task always form one gesture, because no frame runs between them, so the count does not depend on frame rate.
- Keys: the key up of the last held camera key, followed by inertia reaching rest; a key down before rest continues the gesture.

## 9. Configuration

`graphty/src/siteConfig.ts` gains one optional field, validated in `parse()` separately from the rest of the file. An invalid `analytics` block is dropped on its own, with one console line, and the rest of the file (`site`, `features`, `datasets`, `sentryEnvironment`) is kept, so a typo turns off analytics and nothing else.

```ts
/** Analytics ids for this site; absent means nothing is sent. All are public client ids. */
readonly analytics?: {
    /** PostHog project key ("phc_..."). */
    readonly posthogKey?: string;
    /** PostHog ingest host: exactly "https://eu.i.posthog.com". */
    readonly posthogHost?: string;
};
```

The validation rules are:

- `posthogKey` must match `/^phc_[A-Za-z0-9]+$/`.
- `posthogHost` must be exactly `https://eu.i.posthog.com`. The US host is refused: the privacy page names the EU region (decision 9), so a site that wrote the US host would send readers' data somewhere they were not told about. A refused block switches both PostHog modes off for that site, with the existing console line.
- Any other key in the block (a leftover `umamiWebsiteId`, say) is ignored and the rest of the block kept, as `parseAnalytics` already reads only the keys it knows.

Tests never point PostHog at another host through `site.json`; they use the test seam (section 10, graphty app item 3).

`graphty/sites/production.json` holds `posthogKey` and `posthogHost` only. Because an invalid block fails silently on the site, the `siteConfig` test runs every committed `graphty/sites/*.json` through `parse()` and fails when an `analytics` block is present but dropped (section 11).

## 11. Test plan

All tests go through seams and never `vi.mock`. Assertions count recorded calls and check state; they never wait on flush timers or assert that nothing arrives after a delay (`local/no-test-timing`). UI tests drive real input. Every analytics test file calls `resetAnalyticsForTests()` in `beforeEach`. **Negative assertions need a barrier.** An assertion that something was not sent ("sends none", "no second", "nothing new") is checked only after waiting on the event that proves the guarded work finished. ## 13. Open risks

- **R1. A visitor who leaves before PostHog loads is not counted.** The anonymous mode loads after the `load` event and an idle moment of at most two seconds (decision 6), so a bounce in the first seconds sends nothing, and the page-view count runs below the real one by an unmeasured share. If it matters, the anonymous instance can move to posthog-js's slim entry (about 54 KB gzip instead of 231 KB) at the cost of a second copy for readers who share, or start before `load`.
- **R2. Replay Meta events record `location.href`.** Neither PostHog's `before_send` (which skips `$snapshot`) nor Sentry's `beforeAddRecordingEvent` (which never sees the Meta event) cleans it. The defense is the address bar: `stripQueryForRecorders()` runs synchronously before either recorder initializes (section 3). The real-chunk test in section 11 and analytics test 3 pin it. A future query param read after boot must use `bootQuery()`.
- **R3. Two DOM recorders run at once for consenting readers:** Sentry's error buffer and PostHog's session recording. Sentry's buffer is one-shot: an error sends the recording of the moments before it once, through `beforeErrorSampling`, then buffering restarts under a new replay, and `stickySession` is off, so Sentry never becomes a second session recorder. `minReplayDuration` is 0: Sentry's default holds a replay shorter than 5 s back for a later flush, which the restart would cancel, so an error in a buffer's first seconds would send no replay. Measure on a 10k-node graph before shipping. If the cost shows, set Sentry `replaysOnErrorSampleRate` to 0 and link the PostHog session id on Sentry errors instead.
- **R4. Masked attributes make autocapture element names and replays coarse.** The `control` id (decision 15), command ids, `panel_opened` and the canvas events cover the gap; controls with no command get a fixed control id only when a funnel needs one.
- **R5. API surveys and `getActiveMatchingSurveys` need PostHog's remote config call.** Verify it works with `disable_external_dependency_loading` in the first build.
- **R6. The camera gesture end.** Section 8.6 defines it by input (pointer up, inertia at rest after a wheel or key run). If a controller has no inertia state to read, the element adds one inside the controller; the app never debounces camera input. Key gestures are tested only through the element's own tests.
- **R7. Assistant-started actions count as the reader's.** Runs carry cause `"command"`, and the assistant's and group collapse's `positions.set` count as `nodes_dragged`. Accepted for now. The path when a funnel needs the split is an `"assistant"` value on `JournalEntry.trigger` and `RunChange.trigger`, set by the element's AI tool dispatch, and a drag marker on `positions.set`; both are additive.
- **R8. Anonymous ids last one day.** PostHog's server hash changes with its daily salt (and with the IP, so a phone moving between networks is two visitors), so weekly and monthly unique visitors overcount, an anonymous reader's return is visible only through `return_visit`, and a reader who shares mid-page is two ids. Two people behind one IP with the same browser version are one id. Whole-audience numbers therefore come from event counts with `first_on_page` (section 4.3), never from unique users; funnels and retention stay shared-mode insights.
- **R10. No location in either mode.** Cookieless processing strips the IP before GeoIP runs, and every event carries `$geoip_disable`. Country-level reach cannot be measured; adding it would mean letting GeoIP run on shared-mode events and saying so on the privacy page.
- **R11. The billing limit on a launch day** is the owner's choice (section 12, step 5).
- **R9. Report a problem still needs consent.** That is launch-plan item 1, tracked separately.
