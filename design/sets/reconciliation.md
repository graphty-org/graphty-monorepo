# Sets and the design framework: how each difference was settled

Two documents describe sets in graphty-element. The **design framework**
(`design/ui/framework/` in the main checkout) is the conceptual model, glossary and element
contract written from the analysts' workflows. The **sets design** (`design/sets/sets-design.md`
on this branch, `feat/element-sets`) is the design the code on this branch implements. The sets
design was written from early drafts of the framework, so the two disagreed in places. This
document lists every difference, what was settled, and why. Both documents now state the settled
position.

Each entry is one of two things:

- **Decided**: reversible at the cost of an edit or a rerun (a screen word, a placement, a test,
  internal wording). It is written into both documents.
- **Recommended**: a one-way door for the owner, because it fixes a published name, a published
  default, a stored field or the file format. An additive name or option counts: once released,
  consumers call it and files store it, so removing it is a breaking change. The recommendation is recorded in the framework's
  `one-way-doors.md` (door numbers below) and in section 15.3 of the sets design (item numbers
  below); neither document treats it as settled until the owner answers.

**Status, 2026-09-27**: the owner ruled that none of the recommended entries is a one-way door
while the names are unpublished, and decided every one exactly as recommended. Where an entry
below says "Recommended", read "Decided". The code changes they needed are made and tested on the
branch, except the two the design defers (`combine`'s `live`, and the node type in stored members);
section 24 of the sets design lists each with its test.

## The differences

| # | Difference | Settled | Reason |
|---|---|---|---|
| 1 | Is a path its own object, or a kind of set? | **Recommended** (door 11; item 3): a path is the third kind of set definition, keeping its walk with repeats; its kind (simple, trail, cycle, walk) is derived, never stored. **Decided**: on screen it stays its own object type with Create path. | One id space, one reference type and one lifecycle cost nothing the analyst loses, since the walk is kept; a derived kind can never disagree with the walk. |
| 2 | What a path step names | **Decided**: the edge the walk took; a group only where the algorithm genuinely used one (a reciprocal pair read undirected). **Recommended** (item 3): a one-edge group is canonicalised to that edge. | "Which transaction" is the question a path over a transaction graph answers; once Dijkstra takes the shortest parallel edge it uses one edge per step, and two spellings of one step must have one revision. |
| 3 | A third edge reading, `clipped`, for rules | **Recommended** (door 11; item 3): add it. **Decided**: its screen value is "Edges: clipped". | A filter's edge step keeps the nodes it isolates, so "Save as rule set" on it can mean what the step meant only with a reading that is neither induced (re-adds the cut edges) nor listed (drops the isolated nodes). "Matching" was rejected because "match" and "matching" already name graph concepts. |
| 4 | An old saved `"visible"` scope: frozen as induced or listed | **Recommended** (door 11; item 15): listed, or induced when no edge was hidden; an old `"selection"` stays induced. | Induced would re-add every edge the filter hid, so the saved set would not be what the analyst saw. |
| 5 | Do Union, Subtract, Intersect and Exclude make a fixed set or a live one? | **Recommended** (door 11; item 1): the published `combine` keeps writing a fixed set, and gains an optional `live: true`, with the leaf field that lets an induced operand speak its edges, in the release that builds the screen's set operations. **Decided**: on screen the four verbs make a rule set whose Rule row names its operands; Create set on it freezes it. | Replace data must replay what the analyst meant ("a project is its own template"), which a frozen "top 10% Intersect suppliers" cannot; Figma's boolean groups stay live until Flatten. A fixed door is still needed, and the edge rule for mixed readings belongs in graphty-element, not in the app. |
| 6 | Freshness: add `unresolvable`; is `detached` stored or derived? | **Recommended** (item 5): add `unresolvable` to the open union. **Decided**: screen word "Cannot evaluate", verbs Edit rule or Update graphty-element, placed after Detached in the state line; `detached` is derived from the tombstone, never stored. | A cycle, a failed compile or an unknown kind removed nothing, so "Restore" would misstate the fix; the framework already said freshness is never stored, and its contract contradicted itself. |
| 7 | What a reference to a deleted set resolves to | **Recommended** (door 18; item 33): it resolves through the deleted set's kept record. | Deleting a set then never blanks a style layer or changes a filter (Figma's rule for a deleted main component), and the branch's open problem, a filter over a removed set hiding every node, disappears. The record is a definition, so the answer does not depend on freeze timing. |
| 8 | How long a deleted set's record is kept | **Recommended** (door 18; item 33): while any live layer, filter, rule set, layout scope, note, view or run with kept values names it; dropped once nothing does; no byte cap. | A byte cap could drop the one record a visible Detached mark needs, so "Restore set" would fail where it is offered; dropping unreferenced records still keeps an assistant's create-and-delete loop from growing the file. |
| 9 | Is `sets.restore` published? | **Recommended** (door 18; item 33): yes, in this release. | The Detached state offers exactly one verb, Restore set, and today only undo can bring a set back. |
| 10 | The removal verb: `remove` or `delete` | **Recommended** (item 1): `remove` in the API. **Decided**: the screen keeps Delete. | Every published removal verb is `remove` (`runs.remove`, `styles.remove`, `scope.remove`); on screen Remove is the data operation, so the object command stays Delete. |
| 11 | "Use current" or "Carry over to new run" for a partition group | **Decided**: Carry over to new run for groups, Use current for items whose key means the same in every run. | A community number means nothing in a new run; the framework already said so except in one generic line, now fixed. |
| 12 | A layout's default scope, and which layouts accept one | **Recommended** (door 17; item 39): the whole graph in 2.x; the filtered graph in the major version that ships incremental placement and a placement rule for static layouts. **Decided**: only simulation layouts accept a scope until then. | The filtered graph is the right target, but a static layout has no rule yet for where a subset lands, and a published default is a door. |
| 13 | One carried layout scope for the whole element | **Decided**: acceptable now; clients show the scope in force on the Layout row; per-set layout settings remain the target. | `layoutScope` is readable, so it is not hidden, but an outcome must never depend on state the analyst cannot see. |
| 14 | `{ set: SetId }` widened, or kept with `{ define }` added | **Recommended** (door 11; item 4): kept, with `{ define }` added. | Widening the field breaks every reader of `spec.set` as a string; `{ define }` still lets every grammar accept one definition. |
| 15 | `Filter`, `FilterDirection`, `SetOp`: renamed? | **Recommended** (door 11; item 35): keep them, deprecated, behind `RuleTree`, `SelectionDirection` and `SelectionOp` aliases shipped in this release. | Aliases cost one line each; shipping `SetCombine` beside an un-aliased `SetOp` would document two `Set*` names meaning a combination and a selection mode. |
| 16 | `neighborhood.seeds` renamed to `nodes`? | **Recommended** (door 11; item 35): keep `seeds`. | A published 2.x field must be read in both spellings forever whatever is done, and `nodes` would mean start nodes in one leaf and members in another; the screen never shows the word. |
| 17 | The membership leaf `scope`, and the rule's own scope `within` | **Recommended** (door 11; item 6): rename the leaf to `{ kind: "member", of }`, the selector to `{ match: "member", of }`, and the rule's scope field to `scope?`. | The leaf tests membership; it does not say what anything reads, which is what "scope" means everywhere else. Both names are unreleased, so the rename is an edit now and a breaking change later. |
| 18 | The item address and `ResultItem { run, key, execution? }` | **Recommended** (door 8; item 8): same content; if results and runs split (door 7), spell it `{ result, run?, key }` with `ResultId` an alias of `RunId`. | The names are stored in every kept item reference, and a field called `run` holding a result id would invert the vocabulary in every file. |
| 19 | The framework's rule-leaf list lacked the membership leaf and `item` | **Decided**: the framework's documents now list them, the published leaves (`neighborhood`, `degree`, `component` and the rest), and `threshold` keyed on a value path. **Recommended** (door 11; item 6): the new leaves' published shapes. | The framework's own Membership predicate needs them, and a path key expresses thresholds over imported scores a run key cannot. |
| 20 | Stamping the `graphty.source` column | **Recommended** (door 3; item 20): not in this release; its name is decided with edge identity and stamped no later than the release that writes the first project file. | The name is published once stamped, and it joins an edge's identity after Add data. |
| 21 | A per-set `set:changed` event | **Recommended** (item 9): keep it; its cause gains `"undo"` and `"redo"`. | A sets list needs per-id changes that a project-wide event does not carry, as style layers have `style:changed`. |
| 22 | When the deprecated names are removed | **Recommended** (door 15; item 37): the major version that ships the project file. | The first released file format is then written only with the new names. |

## Differences neither document listed

| # | Difference | Settled | Reason |
|---|---|---|---|
| 23 | Run ids hash the scope keyword, and scoped runs now compute over their scope | **Recommended** (door 7; item 34): hash the frozen scope definition, never the keyword, and keep parameters and seed out of the id. Built. | On this branch an unscoped PageRank under filter A and then under filter B keeps one id and re-executes in place, so every layer bound to it silently repaints from a different graph. |
| 24 | Node identity when node types are declared | **Recommended** (door 4; item 11): answer door 4 before the first project file; the branch needs no change before merge. | Member lists, revisions and the node-hash column key a node by `NodeId`, and a member written without a type cannot be given one later; no file is written yet. |
| 25 | The membership digest's promise | **Recommended** (door 10; item 11): `d1:` is promised after a save and reopen of a file that embeds the graph, pinned by a test; re-import and cross-copy comparison wait for a later version. | Run records are kept forever and their digest decides freshness; the columns that make it reproducible are written with the graph. |
| 26 | Reserved path roots | **Recommended** (door 13; item 36): refuse every root but `data` and `results` now; enforce no result field named `runs`; no rename of imported columns; no `sets` query root. | Attributes live under `data.`, so an imported "graph" column cannot collide; today a stored `graph.degree` path silently resolves to nothing and would change meaning later; membership is a rule leaf, not a second grammar. |
| 27 | Which file edge ids count, and the import report | **Recommended** (door 3; item 38): adopt the ordinal counted over every edge of the pair per load, with its count, and minted `graphty:e<n>` ids; default `edgeIdPath` to the format's declared id in the major version that ships the project file; add an edge-identity field to the import report before then. | The ordinal rule never moves when an id is configured later; probing ids now would change how existing loads merge edges; the report is how the analyst learns references match by position. |
| 28 | A rule stores its edge reading | **Recommended** (door 11; item 3): the framework's rule shape now carries `reading`. | "Stated, never inferred" is the framework's own rule, and the branch refuses an induced rule with an edge leaf so no leaf is silently ignored. |
| 29 | What a missing rule scope means | **Recommended** (door 11; items 6 and 40): always the full graph; a filter step reads its predecessor through its own `input` field. | One definition then means the same thing in a step, a kept set and an inline scope. |
| 30 | `FilterStep.set` typed as a widened union | **Recommended** (door 11; item 40): typed `Scope`. | It repeats the widening rejected in entry 14; `Scope` already carries a kept set and an inline definition. |
| 31 | The project file's list of parts | **Recommended** (door 2; item 11): paths are sets; the project's top level gains the set id register and the tombstones, because set ids are unique across the project's graphs; each session part gains the held-item captures; the graph part gains the reserved edge and hash columns. | A reopen needs each of them to rebind members and reproduce digests. |
| 32 | Whether rule sets are project-owned (door 5) | **Recommended** (door 5): style layers project-owned, sets per graph. | A fixed set's members and a rule's run paths name one graph; the evidence for door 5 is about style layers. |
| 33 | `createFrom(..., { follow })` against "Create set always gives a fixed set" | **Decided**: no conflict; the screen's Create set never passes `follow`, and Save as rule set on one item does. | API options and screen verbs are different layers. |
| 34 | Item keys `{ field, value }` against keys that name content | **Recommended** (door 8; item 8): `{ field, value }` now, since every kept item reference stores it; content keys (a component by its smallest node) are additive and arrive with Merge nodes forwarding. | A group number is meaningful while every item reference holds its run. |
| 35 | Words: "seeds" for the edge-counter binding; "offer" missing from the glossary | **Decided**: documents call the binding the counter binding (a code rename is optional); the glossary gains "offer" as a documentation word. | "Seed" is reserved for the random seed; every published name must be in the glossary. |
| 36 | The file's edge-id column is named `graphty.edgeId`, which 2.x snapshots already carry as the session counter | **Recommended** (door 3; item 11): write the stable edge id (the file's id, or a minted `graphty:e<n>`) under a column name that no snapshot uses for the counter, decided with door 3; the counter column is never written. | `session.snapshot()` publishes the counter under `graphty.edgeId` today, so a file column of that name would hold a different value than the same-named snapshot column, or tempt a writer to store the counter, which re-attaches every edge reference after a reopen. |
| 37 | The framework's list of set verbs lacked `offers` | **Decided**: door 11 now lists it; its name is item 1. | The branch publishes `sets.offers`, and a door list that omits a published verb cannot be answered for it. |
| 38 | The glossary ruled "Restore" to mean values only, while its Restore and Detached rows offer Restore run and Restore set | **Decided**: the collision row now allows the three commands, each naming what it brings back. | A deleted set or run is brought back from its kept record, exactly as dropped values are, so it is the same verb; the collision row was written before door 18. |
| 39 | The conceptual model's and the information architecture's door 5 rows said rule sets are project-owned | **Decided**: both now match door 5's recommendation: style layers project-owned, sets per graph. | Entry 32. |
| 40 | What `sets.restore` emits | **Recommended** (door 18; item 33): one `set:changed` with change `"created"` and the caller's cause, because the set comes back with a new record in the list. | A sets list must learn of the returning set from the event it already watches; a new change value would add a union member no list handles. |
