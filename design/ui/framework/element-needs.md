# Element needs

**Job.** The one list of work graphty-element owes the framework: each capability a document relies
on that the element does not yet publish, what the element does today, which sections need it, and
the one-way door it touches. With `implementation-mapping.md`, it is one of the two documents that
state what the element does today; every other document points at a row here by its opening
words. **Not here:** what the element publishes today and its exact semantics
(`element-contract.md`); the rule that a part whose need has not landed is not built (`implementation-mapping.md` 7); open expensive decisions (`one-way-doors.md`). **Owner:**
graphty-element API steward (front-end architect). **Ceiling:** the README's table. **Validated
by:** section 1's checks.

**graphty-element** owns every graph capability; the **graphty app** is only the window around it
(`CLAUDE.md`, "Architectural Principles"). Every row is element work, never an app workaround.

## 1. How the list is kept

- **One list.** No other document keeps a list of element needs. A document names a need in one
  line and cites this document with the row's opening words; `research/scripts/check-flows.mjs`
  checks every such quotation from `task-flows.md`.
- **Issues.** A defect the app works around today is filed before the first build slice merges
  (`implementation-mapping.md` 8), with the repository's type, priority and effort labels; the
  owner files them. A
  new capability is filed one area at a time, at the start of the build slice that needs the area,
  one issue per area or per row. Every issue carries the repository's type, priority and effort
  labels. Filed today: issues #388 and
  #405 (the drawing cliff), #545 (zoom step and zoom to selection), #546 (modularity bands) and #551
  (automatic paint suppressed by one hand-colored node).
- **No fallbacks.** A surface part is built in the pull request that lands its row here, and its
  slot is empty until then (`implementation-mapping.md` 7), so no app code stands in for a row.
- **The Door column.** A number is an open door in `one-way-doors.md`. "Was N (additive)" marks a
  proposal that used to be listed as a door: an additive name, read or event is a two-way decision
  until the release that publishes it, and the API steward decides its spelling then, with the
  recommendation kept in `research/archive/one-way-doors-long-form.md` under its number.
- **What already shipped** (the sets work and scoped computation, 2.6.0; `decided-doors.md`,
  "Walked through") is not a need; the release is the status line of `implementation-mapping.md`.
