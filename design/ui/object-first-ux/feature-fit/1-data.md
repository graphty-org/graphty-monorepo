# Feature fit, area 1: data in and out

Loads, formats, replace and add, export, screenshots and video. Every capability in this area
from the two inventories (`../inventory/element-capabilities.md` sections 1 and 11, and
`../inventory/app-today-and-personas.md` sections 3.3, 3.7, 3.10, 3.11 and 3.12) is placed in
the object model of `../object-model.md`. Nothing here changes the app; it is a design check.

## Terms

- **Object-first model**: the design in `../object-model.md`. The left panel is a tree of
  objects the reader made from the data (Sets, Measures, Groupings and their Groups) with the
  Dataset as the root; the toolbar holds the verbs that make objects; the right panel (the
  **inspector**) shows the selected object. Nothing in this area creates a tree row except a
  computed attribute, a type role and a recipe, which is the point: data in and out is what
  happens to the ROOT, not to the objects.
- **The Dataset**: the root row of the tree and the inspector shown when nothing is selected.
  Its sections, in order: Summary, Arrangement, Showing, Canvas, Attributes, Findings, Made by,
  Export, Notes (`../object-model.md` section 4.1).
- **Made by**: the collapsed inspector section that holds the record of how an object was
  produced. For the Dataset it is the load record.
- **Import dialog**: the one dialog the model allows (section 9, "Import"): tabs File / URL /
  Paste, a format select, the field mapping shown only when detection is unsure, and a
  Replace / Add to current choice. It is reached from the Welcome sheet, from "Add data" (+)
  on the Dataset header, from the file menu and from a drop anywhere on the canvas.
- **File menu**: the menu behind the chevron in the left panel header (Open, Open recent, Open
  sample, Add data, Save project, Run a recipe, Settings, Keyboard shortcuts, Help).
- **Share**: the one filled button, top right. Its menu is the export of the whole picture:
  Export image, Export data, Export report, Copy image, Copy methods text, Export recipe.
- **Export section**: the per-object inspector section. The Dataset's exports the whole
  graph; a Set's exports its members; a Measure's exports its ranked list.
- **Stale rule** (section 5): a data change re-runs every object whose estimate is under one
  second and marks the rest stale, with Re-run and the estimate in the row. A stale object
  keeps painting its old values.
- **Home**: the one place a capability lives. Other appearances are shortcuts to that place.
- **Fit**: natural (the model has a slot and the slot is the obvious one), awkward (it has a
  slot but the slot bends a rule or needs a note), or does not fit (the model has no slot).

The columns of the table: what it is and its status today; where it lives; the fit; the
element API it uses today, or the gap it would need (a "gap" is something the element must
grow, since the app may not compute over the data itself); and what it does to the tree, the
object states and the paint precedence.

## Notes on the awkward ones

**A. Service sources (STRING, BioGRID, a Neo4j server).** A file has a format; a service has a
query (species, score cutoff, a seed gene list). The Import dialog can hold a Service tab, but
the fields differ per service, and the app must not hard-code them. The fit works only if a
registered data source publishes its inputs as option descriptors (the same
`OptionDescriptor` shape algorithms use), so the tab is drawn from the catalogue. The model's
section 10 already lists external enrichment services as a rough edge; this is the same edge.
Fit once descriptors exist; awkward until then.

**B. Changing import options after the load.** Field mapping, repeated-edge policy and id
coercion are decided before anything exists, which is why the model gives them the one
dialog. Changing them afterwards is a re-import, and a re-import is a Replace (note C), which
deletes the tree. Worse, id coercion can change which records are one node, so a tree kept
across the re-import could reference ids that no longer exist. The honest UI is: Dataset
overflow > "Import options..." reopens the dialog on the current values, and the dialog says
"Re-importing replaces the dataset and deletes its 6 objects (a recipe can re-create them)".
Not hidden, not pretended to be cheap.

**C. Replace, and what happens to the tree.** Today the app calls `clearData` and loads. In the
model a Replace deletes the root and everything under it, so it confirms with the count. That
is correct for "open a different file" and wrong for the Condition Comparison and
Reproducible Session workflows, where the reader wants the SAME objects on NEW data ("load
Tuesday's network, keep my communities and my top-10 rule"). The model's answer is Export
recipe, Replace, Run recipe: three steps for one intent. Proposed: the Import dialog's Replace
choice carries a checkbox "Keep the objects and re-run them on the new data", which is those
three steps in one, and every re-created row lands by the stale rule (cheap rules re-run at
once, a four-minute betweenness waits with its estimate). Objects whose definition cannot
apply (a Path from node 1 to node 34 when node 34 is gone) land frozen with the reason. This
needs the load mode on the element, the recipe (#145, #337) and the objects API; until then
Replace deletes the tree and the dialog says so.

**D. Direction is an edit of the root.** "Direction [Undirected v]" is the one Summary row a
reader can change. It looks like a harmless property; it is a data change that makes every
run stale (degree, betweenness, PageRank and every community detector read direction, and
each run's caveats say which direction it used). The stale rule handles the consequence (the
rows dim, cheap ones re-run), but the row should say so before the change: the select's
tooltip reads "Changes what every object computed; 4 objects will re-run". The element side
today is `el.directed` as configuration with no defined effect on existing runs; it needs an
explicit `session.data.setDirection()` whose contract is "existing runs are marked stale".

**E. Data edits.** Removing nodes, editing an attribute value and merging nodes change the
material every object was computed from. The model has no verb for that: objects are made
FROM the data and never edit it; Filter and Focus are the non-destructive ways to leave
things out. One of the three fits with a stretch: editing an attribute value in a Table dock
cell is contained (one cell, one attribute, the stale rule on the objects that read it), and
Figma's Variables table is the precedent. Removing nodes and merging nodes do not fit: both
rewrite membership in every Set and Group under the reader's feet, and merging needs an
inverse (design 9.3's mutation API) the element does not have. They are listed as not fitting
below. The knowledge-engineer and enrichment-map workflows that need them are next-phase, as
`../object-model.md` section 10 already says.

**F. Expanding from a server.** A double-click that fetches neighbours is a data load
triggered from one node. It fits the node inspector and the context menu as a verb, but two
things bend: the Dataset now has more than one source (Made by must list every fetch, with
counts), and every fetch is a data change that fires the stale rule, so a reader expanding
node after node watches their Measures dim and re-run each time. That is honest and the
model accepts it, but the Dataset's Made by is the only place the reader can see why. On the
element side the fetch source is a pair of callbacks a consumer writes
(`layoutBehavior.fetchNodes`); by the architectural rule it should be a registered data
source with a descriptor, so the app can show "Connected to <server>" without owning the
connection.

**G. Computed attributes: a column or an object?** An imported column is material (section
2.2: it becomes an object only when used). A formula is something the reader authored, with
a definition, a state and a re-run, so it is a Measure row. But the analyst also expects to
see it in the Attributes list and the Table dock beside the imported columns, and to feed it
to Filter by. Decision: it is a Measure in the tree (that is where it is edited and
re-run) and it also appears in Attributes with origin "computed", exactly as result fields
already appear with origin "result". Two appearances, one home; the Attributes row's "..."
has "Show in tree". Awkward because it is the first Measure made without the Rank tool, and
the model's rule "every algorithm has exactly one flyout" gains an exception: formulas come
from the Attributes header, not the toolbar.

**H. Loaded but not drawn, and loading in pieces.** The status bar's "showing 12 of 34" counts
the data mask, never the render set (the inventory is explicit). Once the render ceiling is
enforced (#302), there is a third number: nodes loaded and in the mask but not drawn. The
model has no word for it, and a Set whose members are partly undrawn paints only some of
them with no visible reason. The least-bad placement is a single Summary line and a status
readout ("350,000 nodes (200,000 drawn)"), plus a caveat line in the Fill section of any
object with undrawn members ("12 of 40 members not drawn"). Progressive loading is the same
problem over time: while chunks arrive the Dataset's member list is changing, and the stale
rule would re-run every cheap object on every chunk. Rule proposed: while the Dataset row is
computing, the tools are disabled (as they are before a load); objects are created only once
the load is current. That keeps the model simple at the cost of not analysing a half-loaded
graph, which no persona asked for.

**I. Video.** The model's Share menu does not mention video, and the inventory lists it as a
shipped export. A camera path with waypoints is a list of camera states in order, which is
exactly what the Views list holds. So video lives on the Views section: "Export video..."
turns the saved Views in list order into the waypoints, with a seconds field per row. It is
natural once seen that way, and it gives the Views list a second reason to exist. What does
not fit is a video of something other than a camera move: recording the layout settling or
time playback is a capture of a process, and the element's video capture takes a camera
path, not a time window. Not offered.

**J. Reports.** The persona's Report Builder view (V03) becomes unnecessary because the tree
IS the outline: a report is the objects in tree order, each with its reading, its Made by
record and its values, then the image and legend, then the notes. The gear is a checklist of
tree rows. The one rule to keep: the element writes the document (methods paragraph,
rankings, legend), the app only chooses the rows and saves the file, or a third-party consumer
gets no report.

**K. The project file.** The menu item is trivial; the format is the model's one true one-way
door (`../object-model.md` sections 11 and 12, decision 25). A project file must carry the
tree (kinds, names, parents, order, definitions, states, Fills, links, notes) and it can do so
only if the element owns the tree. Until the objects API exists, a "project" saved by the app
would be an app-private format that no other consumer could open, which the root
architectural rule forbids. So Save project waits on the objects API and is not offered
before it, not even as a tracked workaround.

**L. Style presets and templates.** `applyTemplate` replaces the whole style stack, and in the
model the style stack IS the tree's Fills. Applying "Print" would overwrite every object's
colour. So a preset in the object model can only touch what no object owns: the Dataset's
default look (the locked base layers) and the default palettes new objects pick up. That is
"Look [Default v]" in the Canvas section, and it is a smaller thing than today's five-row
Styles section promises. Exporting the stack as a document survives only as a palette
command for consumers who want the raw layers; the reader-facing way to carry a look to
another dataset is the recipe or the project file, which carry the objects the Fills belong
to. The element needs a template scope ("base and palettes only") to make the preset safe.

## What does not fit

- **Removing nodes from the data** (row 25): rewrites the members of every Set and Group; the
  model's way to leave things out is Filter and Focus. API-only.
- **Merging nodes** (row 27): a destructive edit with no inverse on the element; rewrites
  membership everywhere. Next-phase, as `../object-model.md` section 10 says.
- **Video of a process** (note I): recording a layout settling or a time-window playback; the
  capture API takes a camera path. Camera-path video does fit, on the Views list.
- **A style preset that restyles objects** (note L): a template applied to the whole stack
  overwrites every Fill; only a base-look preset fits.
- **Analysing a half-loaded graph** (note H): objects cannot be created while the Dataset is
  loading in pieces without re-running on every chunk.
- **A project file before the element owns the tree** (note K): fits as a menu item, cannot be
  built until the objects API exists.
