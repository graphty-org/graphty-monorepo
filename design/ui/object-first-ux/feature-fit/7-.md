# Feature fit 7: the assistant, voice, commands, notes, undo and history, keyboard shortcuts, events and session persistence

This file places every current and proposed capability in one area of the app into the
object-first model described in `design/ui/object-first-ux/object-model.md`. The area is
everything that is not a graph object but surrounds the objects: the AI assistant and its voice
input, the command palette and the command vocabulary, notes and annotations, undo and history,
keyboard shortcuts, the events the element publishes, and what survives a reload.

The capabilities come from the two inventories, `inventory/element-capabilities.md` (sections
9, 10 and 11) and `inventory/app-today-and-personas.md` (sections 3.1, 3.4, 3.8, 3.9, 3.11 to
3.14), plus the requirement files `design/designloom/capabilities/annotation.yaml`,
`analysis-history.yaml`, `keyboard-shortcuts.yaml` and `guided-onboarding.yaml`, and the
element API design `design/element-api/element-api-design.md` (sections 4.11.2 journal, 4.15.3
notes, 9.2 what stays with the consumer). Issue numbers are open issues in
graphty-org/graphty-monorepo.

## Terms used in this file

The object model's words, restated so this file stands alone:

- **Object**: a row in the left panel's tree. Something the reader made from the data (a Set, a
  Group, a Measure, a Grouping) or the data itself (the Dataset). Only objects are edited.
- **Tree**: the left panel's ordered, nested list of objects. Its order is the paint order.
- **Inspector**: the right panel. It shows the properties of whatever was selected last, in
  titled **sections** (Definition, Members, Fill, Findings, Made by, Export, Notes).
- **Fill**: an object's appearance, stored as one or more style layers in the element. Every
  style layer belongs to an object; a reader never sees a layer that is not on an object.
- **Precedence**: when two objects paint the same visual channel of the same element, the one
  nearer the top of the tree wins.
- **State**: whether an object's members and values are up to date: current, computing,
  waiting, stale, failed, frozen.
- **Mask** (what is **showing**): the element's one visibility filter. **Focus** sets it to one
  object's members.
- **Made by**: the collapsed inspector section that records how an object was made (method,
  parameters, scope, engine, time, and who asked: the reader, the assistant or a recipe).
- **Dock**: a surface at the bottom of the canvas that takes space from it. The model has two
  tabs, Table (Shift+T) and Assistant (backtick); this file adds History.
- **Palette**: the command list opened with Ctrl+K. Every command and every tool variant is in
  it under both its plain and technical names.
- **File menu**: the menu behind the dataset name in the left panel header (Open, Save project,
  Run a recipe, Settings, Keyboard shortcuts, Help). There is no top bar.
- **Flyout**: the dark menu behind a toolbar tool's chevron that lists its variants.
- **Command**: one session verb written as data (`{op: "algo.run", ...}`), so a recipe, the
  journal, the assistant and a console all use the same door. Only `algo.run` exists today
  (issue #337).
- **Journal**: the element's record of every command that changed state, each with its
  **inverse** (the command that undoes it) and a **coalesce key** (so one drag or one slider
  sweep is one entry). Proposed in issue #145.
- **Recipe**: a journal export, a list of commands that can be replayed on another dataset.
- **Project file**: one document holding the whole session (data, tree, layers, runs,
  positions, mask, views, notes, journal), issue #301.
- **Note**: text anchored to a node, an edge or a point. Not a tree row; it lives in the Notes
  section of what it annotates and as a marker on the canvas.
- **Marker**: the small glyph the element draws on a node to show it carries a note (the
  `node.marker` channel, issue #295).
- **Two-way hover link**: hovering a row outlines its members on the canvas, and hovering a
  node highlights the rows of the objects it belongs to.

Fit words: **natural** (the model has a home and the capability needs no bending), **awkward**
(it has a home but something about it fights the model, explained in the notes), **does not
fit** (no home without breaking a rule of the model; the notes say what replaces it).

The last column, "Tree / state / precedence", says whether using the capability adds, removes
or reorders tree rows, changes an object's state, or changes which Fill wins. "none" means it
touches none of the three.

## Notes on the awkward ones

### A. The assistant's tools were written for a layer stack, not for a tree

Today `findAndStyleNodes` adds a style layer whose source is "plugin: graphty-ai" with an
expression selector and static values, and `clearStyles` removes every layer that is not the
element's own. Both are correct against the current element and both break the model's first
rule: every layer belongs to an object, and a reader never sees a layer that is not on one.
An assistant-made layer with no tree row would paint nodes red with no chip, no eye, no
precedence position and no way to edit or delete it except asking the assistant again.

The fix is not in the app. Once the session has an objects API (object model section 11) and
the commands entry point (issue #337), the assistant's tool list becomes the command list, and
"find nodes with degree over 10 and make them red" is `objects.create` with a rule Set and a
Fill, exactly what the Filter tool's Create plus one paint row does. The transcript row links
to the tree row and the row's Made by says "Assistant: <request>". `clearStyles` has no honest
equivalent as a verb: "clear the styles" from a reader means either "hide every Fill" or
"undo what you did", and the tool should be replaced by `setVisible` and `remove` over the
assistant's own rows. Until the objects API exists, the assistant's layers should at least
carry the `userData` the objects API will read, so nothing it made is lost at the migration.

Cost: the assistant's tool schemas are a published contract for the LLM prompts and their
tests (`design/ai/ai-tools-testing-design.md`); rewriting them is a medium change in the
element and a rewrite of the prompt tests.

### B. One palette for commands and questions

A sentence typed into the palette can be a command ("bridges"), a node ("34"), or a question
("who bridges the two halves"). The model says: command matches first, the "Ask: <sentence>"
row always last. The ambiguity is "bridges" alone: is it Rank > Bridges or a question about
bridges? Rule: Enter on a query that matches a command by name or alias runs the command; Enter
on a query of more than three words, or one that matches nothing, asks. A reader who wants the
other one arrows to it. This is an app rule and needs no element change; what the element must
supply is the aliases and descriptions on each catalogue entry, so the matching is not an
app-side table (issue #174's note).

### C. A note on an object

The element's `Note.target` is a node, an edge or a point. The model wants a Notes section on
every object (a note on a Grouping that says "resolution 1.2 matched the lab's clusters" is the
analyst persona's whole reason for notes) and a note on the Dataset (the "case note"). Neither
has a target today. The objects API gives every object an id, so `Note.target` gains
`{object: ObjectId}`, and a note on the Dataset is a note whose object is the root. The
orphaning rule carries over: deleting an object orphans its notes and the Dataset's Notes list
shows them under "Orphaned". This is a small addition and belongs with issue #145.

### D. Annotations as drawing versus notes as records

`annotation.yaml` describes a drawing tool: text boxes at canvas positions with font sizes and
bold, callouts with leader lines, highlight circles and polygons with fill opacity and border
width, resize handles, z-order against the graph, fifty per view, saved with a view bookmark.
That is Figma's own object model (shapes with a position and a Fill) applied to a graph, and it
is exactly what the object-first model says a graph does not have: the only things with a Fill
are objects made from the data.

Each requirement has a home that keeps the model, and one that does not:

- A text label at a canvas position: a note with a point target. Fits.
- A callout with a leader line to a node: a node note whose marker is expanded. The element
  draws the box and the line, because it owns screen positions; the app never draws on the
  canvas. This is beyond issue #295's icon channel: one marker rendering with a collapsed and
  an expanded state. Fits, with element work.
- A highlight shape around a region: does not fit as a shape. The region is a set of nodes;
  make the Set (marquee, Ctrl+G) and give it an Outline or Glow Fill. For a filled region, a
  set-level hull channel (the element draws a soft shape around a Set's members, moving with
  them) is the same piece of element work the model already lists for set-level labels. The
  Set follows the layout, can be hidden with its eye, sits in precedence, and is re-runnable if
  it was a rule; a drawn circle can do none of that, and is stale the moment the layout moves.
- Resize handles, per-note fonts and z-order: do not fit and are dropped. A note is a record
  with one session-wide style, drawn above the graph. Bold and italic inside a note are not
  offered; if a reader needs a poster they export the picture and annotate it elsewhere.
- Fifty per view, saved with a view bookmark: does not fit. Notes are a session-wide document
  in the element (`NotesApi.toDocument()`), saved in the project file, and a View holds only
  the camera, the mode and the mask. A View may remember whether notes were shown.

The persona evidence supports the record reading over the drawing reading: the fraud and
intelligence analysts (`W06`, `W09`) annotate to document a case, and Findings Communication
(`W15`) wants the picture to carry the highlight, which the Set's Fill and "Notes in picture"
provide.

### E. Undo that costs minutes

Two inverses in the element design are expensive. Undo of a creation is cheap (remove the run),
but redo of it is `algo.run` again: four minutes for a heavy Measure on a big graph. Undo of a
re-run must bring back the previous members and values, which the element replaces today. And
undo of Add data is a pre-import snapshot that the journal's byte cap may demote, after which
the row says "Too old to undo".

The model's answer is that the tree is honest about time: a redone creation reappears in the
computing state with its progress ring, or in the waiting state if the cost gate says so, and
the reader sees why. Two element changes make it cheap in the common case: keep a removed run
in memory until its journal entry is evicted (so redo restores rather than recomputes), and
give `run.rerun()` a "keep the previous result" flag so a re-run's inverse is a swap. Both are
additions to issue #145's journal work, not new API surface.

### F. Delete means two things

The model has two selections, tree rows and canvas elements, and the inspector shows whichever
changed last. Delete on a row deletes the object: no confirmation, one Ctrl+Z, dependants
freeze. Delete on a canvas selection, per `keyboard-shortcuts.yaml`, removes the nodes from
the data. That is the one edit in this area that touches the material, and a reader with a Set
row selected and the halo showing its members could reasonably expect either.

Rule: Delete acts on the selection the inspector is showing. When the inspector shows an
object, Delete deletes the object. When it shows a node or several elements, Delete asks
"Remove 12 nodes from the data? (undoable)" before doing it, because data edits are rare and
every object containing those nodes turns stale. The element side exists in the design
(`data.apply {kind: "remove-nodes"}` with its inverse); what the app must not do is remove
nodes by any other route.

### G. Style templates are a layer stack without objects

`session.styles.toDocument()` writes the layer stack; `applyTemplate` reads one back and reports
unbound layers. In the model every layer is an object's Fill, so applying a template to a tree
would create layers with no rows, which is the thing the model forbids. The template's real
job (Reproducible Session, `W25`: "apply last month's look to this month's file") is a recipe
job: export the Fill of every object with its name and rule, replay it, and let the report say
which objects did not bind. So Share > Export recipe gets a "Fills only" option and the
template document is retired or re-based on the objects API. The five built-in presets are a
different thing: they change the Dataset's default look and the palettes, not any object's
Fill, so they are a select in the Dataset's Canvas section and paint below everything.

## Capabilities that do not fit

Each with what replaces it:

1. Highlight shapes drawn on the canvas (circle, rectangle, freeform polygon with fill and
   border), with resize handles and z-order against the graph. Replaced by a Set with an
   Outline or Glow Fill and a set-level hull channel (new element work).
2. Annotations saved per view bookmark, capped at fifty per view. Replaced by one session-wide
   notes document in the project file; a View remembers only whether notes are shown.
3. Per-annotation text styling (font size 10 to 48, bold, italic, colour). Replaced by one
   session-wide note style in Settings > Appearance.
4. Click a history row to preview a past state without applying it. Replaced by hover (summary
   and the touched object outlined) and double-click to restore; the element has one state.
5. Arrow keys move the selection to the nearest neighbour. Arrows are the camera; replaced by
   Tab and Shift+Tab over the selected object's members and Enter for the neighbours.
6. "D" toggles the detail panel. There is no detail panel to toggle; the inspector is always
   present. Ctrl+\ hides both panels.
7. The guided onboarding tour (welcome modal, five-to-seven-step spotlight tour, "What's next"
   panel). Replaced by the three suggestion rows on the empty tree, tooltips with key chips, and
   "Ask:" in the palette (object model decision 17).
8. Export history as a Python script. Replaced by a JSON recipe and a JavaScript wrapper of it;
   there is no Python runtime for the element.
9. The Undo and Redo buttons, the History pop-out on the Undo caret, the status-bar AI chip,
   the notes chip and the Present rail badge, the "Already run" and "More suggestions" Help
   rows, the Analyze History and Recipes sections, the AI rail activity and the Console section.
   All are surfaces of the old frame; their content lives in the tree, the History dock, the
   Assistant dock and the file menu.
