graphty design gallery / Flows

Keyboard walk and leaving the canvas

A keyboard or screen-reader user explores a graph by walking it: keyboard focus sits on one node and moves along its edges, one neighbor at a time, while the selection stays where it was. This flow draws every state of the drawing's keyboard focus, what each key does in it, what is said in each state, and every way out. Plain arrows move the camera; Shift and an arrow walk. Going to a node by name moves the walk there and selects nothing; Enter adds the node the walk is on to the selection, and no key in the walk ever replaces it. graphty-element holds the walk's start and where it left off, so both survive Tab and every visit elsewhere. It all runs on the Les Miserables graph (77 characters, 254 co-appearances), with Javert on the page. The same walk is told as a story in Keyboard and screen reader, and can be tried in the working mock.

Decided by the owner: Shift with the arrows walks and the plain arrows stay on the camera. Alt with the arrows was ruled out: Alt+Left and Alt+Right are the browser's Back and Forward. Decided after the third study: going to a node (Quick actions, Ctrl+K) moves the walk there without selecting it, and Enter selects; the walk's start is held by graphty-element and survives Tab; the walk line names its region, "Walking the drawing"; the key sheet groups its keys by region; every region has a heading; the long welcome plays once per project; and there is no C key, because there is no separate Note tool. That Shift+Down walks on the drawing but extends a row selection in the Nodes table two regions away is accepted: each region's name is said first, and the key sheet lists the two under their own headings. Kept, because the study showed it works: the focus pill, O for the neighbor order, Shift+Enter back, Shift+Home to the start, "where you came from", the key sheet, Space to add or remove, Esc one step per press, Tab to leave, and every overlay putting focus back on the same node.

What a sighted keyboard user sees

The focus pill sits above the toolbar while the drawing has keyboard focus, and only then. It shows on screen what the screen reader says, so a sighted keyboard user gets the same facts as a blind one. Its first words name the region and what focus is doing there. It is drawn at product size on Les Miserables, colored by group and sized by degree.

The states, and what each one says

The walk has Figma's shape of moving through a tree, put on Shift and the arrows, as screen-reader tree views do: Shift+Down goes into a node's neighbors, Shift+Right and Shift+Left move among them, and Shift+Enter comes back out, as Figma's go-to-parent does. Tab cannot step through neighbors, as it steps through siblings in Figma, because Tab must leave the drawing, so a keyboard user is never trapped in a node with 400 neighbors.

a place keyboard focus can be the walk: the one place where a single node holds focus an overlay or a panel focus visits and comes back from dashed: a condition that changes what the keys do

Playback and gestures come first: while playback runs, Esc pauses it before anything else, and a drag in progress ends before Esc reaches the walk. A plain arrow never ends the walk; focus stays on its node while the camera moves. Esc never moves focus off the drawing: it ends the walk with focus on the drawing, then clears the selection. Tab is the one way out, so Esc does the same job on the drawing as in every list and in Figma, with or without a focus ring. The start and the place outlive the walk: Esc, Tab, F6 and every overlay keep them; only going to another node, the start node leaving the drawing, or opening another graph replaces them.

The start node: the node gone to with Quick actions or chosen in Find, held by graphty-element until another replaces it; with none, the first selected node in the selection's own order (path order, rank order, order of addition, otherwise lowest id), the first member when a set is selected, or, with nothing selected, the drawn node of highest degree (Valjean). The pill names it. Neighbor order starts on the graph's edge weight, highest first, then name (in Les Miserables, co-appearances: the chapters two characters share); with no weight, by degree. O switches between the weight, degree (highest first) and name (A to Z); the choice holds for the rest of the session on that graph, and the first step after each Shift+Down says it. The values shown and spoken are the measures the drawing shows (the size's, then the color's), with the rank in the one rank format, "rank 2 of 77". Inside a filter, the walk moves only among the nodes shown, and a degree says how many neighbors are shown: "degree 17, 10 of 17 shown, on: filtered graph". There is no C key: notes are added from the Notes panel. changed marks a behavior that departs from the framework.

Regions, their headings and the same keys

Every region is a landmark with a heading of the same name, so a screen reader moves by region (F6) or by heading (H), and every announcement on arriving in a region starts with that name. That is also how the two jobs of Shift+Down are told apart: the reader always hears which region the key is in.

Before the first key: the usage-data question

The first time graphty opens on a computer, before the start screen, it asks one question: may it collect usage data. Usage data is off until the person says yes. A keyboard or screen-reader user meets this dialog before any graph, so it has to be answerable with the same keys as everything else, and saying no has to be as easy as saying yes.

Usage data
Your data is yours, but please help us. We will never see the data you analyze. With your yes, graphty records how you use the app, so we can make it easier to use. Only graphty's author and his Claude Code sessions will ever use it. Never a node name, a value, a label or anything from your files. Change it any time in Preferences > Usage data.

The dialog is not asked again, and the drawing's welcome never mentions it. A happy-path trace on Les Miserables

A keyboard user is asked: using only the keyboard, find Javert, walk to his most connected neighbor and back, and select two of his neighbors. The project is open on Les Miserables for the first time, all 77 characters drawn, colored by group and sized by degree. Focus starts on the toolbar with nothing selected. Usage data is off: at first use the person answered the usage-data question with Not now (step 0), and nothing on the drawing asks again. The figure is what a sighted colleague sees after step 8: Valjean carries the selection ring, keyboard focus sits on Gavroche, and Javert, the walk's start, is unmarked because nothing marks a start on the drawing; the pill names it.

Valjean: selected, a two-tone ring close to the node Javert: the walk's start, named by the pill Gavroche: keyboard focus, three bands after a 2 px gap

Screens: the walk, in the working mock, with the focus pill above the toolbar, to try with the keyboard.

Numbers: Javert has 17 neighbors, rank 4 of 77 by degree. His most connected neighbor is Valjean under both orders: 17 shared chapters and degree 36, rank 1. By degree the second is Gavroche, degree 22, who shares one chapter with Javert; by co-appearances it is Enjolras, 6.

Built with: the drawing's focus target, its focus mark, its polite live region and the walk's start and place are graphty-element's own (role="application"). A bare embed shows the focus mark, speaks the same words and keeps the start across Tab; the element publishes the pill's text and values in its focused-node event, so any host can draw the pill.

Step 13 is the other fix: the start is still Javert after the visit to the table, where before it had moved to the first selected node. The first step of a walk names the back key, the ways out, O and the key sheet. The order is said only on the first step after each Shift+Down and after O; every step speaks the same values in the same order as the pill -- the edge's co-appearances, then degree, rank and group -- each with its word, never a bare number.

What the next round checks

Intended: a participant reaches a named node from the keyboard, can always say where they are and how to get back, and ends a "select two" task with exactly two. The study asks, after steps 4, 9 and 13, "Where are you, and how would you get back to where you started?" It must also be able to prove these wrong:

  • Every participant reaches Javert with Ctrl+K on the first try, and nobody expects "Go to" to have selected him.
  • Nobody ends "select two of his neighbors" with three selected.
  • After Tab to the table and back, every participant can say where the walk will go on from, and Shift+Home takes them to Javert.
  • Nobody presses Shift+Down in the Nodes table expecting the walk, once they have heard "Nodes table" first; a screen-reader user finds the table and the drawing with H.
  • Participants who used Enter for the inspector in the last round find Alt+Enter from the key sheet, or do not miss the visit.
  • Run with NVDA before the round, not only with the page's text read back.

Errors, dead ends and cancellations

  • A name the graph does not hold. In Quick actions on Les Miserables, "TP53" matches nothing, so the list says "No commands or nodes match "TP53"." Esc returns focus where it was; Find, opened on the same query, says what it searched and offers Search recent projects.
  • A name that is not exact. "jav" finds no exact node, so the row reads "Find "jav""; Enter opens Find with that text, where the ranking by prefix and substring takes over.
  • Enter on a node already selected. Nothing changes: "Valjean is already selected. Space removes it."
  • Nothing drawn. Past the drawing limit (the citation graph, 124,318 nodes), with the canvas unsupported, or with everything hidden, Shift+Down does not walk: "Nothing drawn to walk: 124,318 nodes not drawn. Enter opens Choose what to draw." Cancel or Esc in that dialog returns focus to the drawing.
  • Inside a filter. With the three filter steps on (27 of 77 characters shown), Javert says "degree 17, 10 of 17 shown, on: filtered graph", and his list holds only the 10 shown: Gavroche and Enjolras, filtered out with group 8, are not walked to, and "1 of 10" counts only the ones shown.
  • A dead end. In the published Les Miserables graph, Old Man's one edge goes to Myriel. Reached from Myriel, Shift+Down on Old Man stays and says "Old Man's only neighbor is Myriel, where you came from. Shift+Enter goes back." A node with no edges at all says "{name} has no neighbors. Shift+Enter goes back."
  • The end of a neighbor list. Shift+Right on the last neighbor says "Last neighbor." and stays; the list does not wrap, because a wrap is heard as another node and loses the count.
  • The focused node stops being drawn (an undo, a filter step or a hide). Focus moves back along the walked path to the nearest node still drawn: "Gavroche is no longer drawn; back to Javert." If the start itself goes, the start falls back to the start-node rule and says so: "Javert is no longer drawn. The walk starts at Valjean."
  • Delete on a node that is not selected. Nothing is removed: "Nothing removed; Enjolras is not selected. Enter adds him."
  • A pointer click. Ends the walk and does what the click does. The start and place are kept; Shift+Down goes on from them.
  • The window loses focus (switching apps). The walk is kept, and the drawing still has focus when the window returns; nothing is said on return. Proposed, untested.
  • The focused node is off screen. Each step that lands off screen pans the camera just enough to bring it into view, without zooming, and never under the pill or the toolbar. Proposed, untested.

Changes this flow proposes

Each is recorded with the document, the old text, the new text and the evidence in framework-changes.md.

  • Plain arrows keep the camera and Shift with the arrows walks. Three framework passages still say plain arrows walk: the canvas walk entry (interaction pattern entries 9.2, "the first arrow press on the canvas starts the walk" and "the arrow keys move focus to a neighbor", with the mode table's Canvas walk row and Enter on a set in 4.2); the key dispatch table and the canvas state chart (interaction patterns 3.6 and 3.8, "Idle --> Walk : arrow"); and the Figma departures ledger (figma crosswalk 4.3, "the arrows walk from the focused node to a neighbor").
  • Going to a node moves the walk and selects nothing; Enter adds to the selection. 9.2 says "Enter selects it, and the inspector follows", which replaced the selection. Enter now adds the focused node and never replaces or removes; Space still toggles. Quick actions' node row reads "Go to {name}".
  • The inspector visit moves to Alt+Enter (Option+Enter on a Mac), the platform's properties key, because Enter selects.
  • graphty-element holds the walk's start and place. 3.8 says focus leaving the canvas ends the walk and coming back needs a deliberate key; both stay true, but the start and the place survive, so the deliberate key goes on where the reader left off.
  • Region names and headings. Every region has a heading of its own name, every arrival announcement starts with it, the walk line reads "Walking the drawing", and the key sheet groups its keys under region headings.
  • The long welcome plays once per project; every later arrival says only the region, the kept walk and the selection count.

Still open

  • Alt+Enter for the inspector visit is a new published key, for the owner. In the third study the visit with Enter was one of the parts the screen-reader participant most wanted kept; the next round shows whether moving it costs more than it saves.
  • Enter and Space both select in the walk: Enter only adds, Space adds or removes. If the next round shows nobody uses Space, it can go back to being only the pan key.
  • The 3D camera's pan is on Shift and the arrows in the app today and has to move before the walk can take them. Its new key is undecided (the suggestion is Ctrl and the arrows).
  • Shift+Home on a Mac laptop is Shift+Fn+Left. The next round should see whether people find it.
