Load a file and check it, then come back to it a week later

Every analysis starts by bringing data in, and the costliest mistakes start there: an amount column read as text, repeated transfers between the same two accounts, a weight whose meaning nobody declared. This flow walks a file through the load step to the moment the analyst can say "this graph is what I think it is", and then the return visit a week later, when the same project has to look exactly as it was left.

The situation. Sarah, a fraud analyst, exports March's transfers from her bank's case system as transfers-2026-03.csv: one row per transfer, 9,113 rows between 3,000 accounts, with columns from_account, to_account, amount and timestamp. The export writes every amount with a dollar sign and thousands commas ("$349.71"), and 412 of the rows repeat a pair of accounts already read. A colleague saves the same export as an Excel workbook; another opens patent-citations-sample.csv, 124,318 patents and 1,480,221 citations, which is past what graphty draws. After the load the project is named after the file, transfers-2026-03; before closing, Sarah renames it "March transfers" in the left panel header, which is the name Recent projects shows a week later.

What she can claim at the end. "This graph is what I think it is: 3,000 accounts, 9,113 transfers of which 412 repeat a pair, directed, amounts read as dollars, one connected piece, nothing dropped -- and amount is declared a similarity, so a bigger amount is a closer tie." After the reopen: "This is last week's analysis, as I left it, and I know what changed since." What records it: two undo entries, "Load transfers-2026-03.csv" and "Set amount's role: similarity", and the import report on the data version, read on the graph's Last import row. Reopening records nothing, because it changes nothing.

Against Figma. Figma opens a file in 2 steps (Open, the file) and adds data with defaults; graphty adds one step, Load, because it checks the data first. That departure is already recorded (figma-crosswalk.md 4.2, "adds first with defaults, for data").

How to read the diagrams

Each column is a place in the app, in the order it sits on screen: the start screen and the load step come before a project is open; then the left panel, the canvas and the right column. The rail, the strip of buttons at the far left that switches the left panel, has no step of its own here, so it has no column. Time runs down. Every shape with a link opens the screen mock that shows it. Every step is graphty-element's work drawn by the app; none is the app's own.

1. Load a file and check it

The branches, one line each

  • A file dropped on an open project goes through the drop choice step first; Add data, Add as another graph and Join reach the same load step (the drop choice step).
  • Could it open the file? An Excel workbook is not read: the load step stays open on "Could not open transfers-2026-03.xlsx: Excel workbooks are not read", says how to save it as CSV, and offers Choose another file... and Cancel. Read as... appears only when the name and the content disagree, a CSV saved as .txt say (state 3).
  • An issue in the preview does not change the route, so it has no diamond. Sarah's amount column is currency text in every row, so the issue defaults to "Read as Currency (USD): 9,113 weighted edges" and Load stays on (state 1, its policies). A column where some values are not numbers blocks Load until the analyst chooses (150 "NA" scores in a protein file). Either way the fix is the policy select on the issue row.
  • Repeated pairs. "412 extra parallel edges" defaults to Keep all (9,113 edges, one per transfer); Merge into one, sum of amount, gives one edge per pair of accounts, 412 fewer.
  • How big is it? Within the drawing limit, Load draws the graph. Past it, Load still commits and the graph opens undrawn, with Filter at import... offered first (the citation file, the undrawn frame). A graph that cannot fit in memory is refused, and Filter at import... or Cancel are the ways on.
  • What a higher amount means is not asked in the load step. After the load the Weight row reads "amount, not used yet" with the question "For amount, a higher number means...", and a distance algorithm asks again the first time it reads the column. Left unanswered, no measure reads amount, PageRank included; Sarah answers a closer or stronger link there (state 4).
  • Did it load the way I meant? If not, Re-map columns on the Last import row reopens the load step on the current data.

Where keyboard focus goes. The load step opens with focus on Cancel while it reads. When the preview arrives, and only if focus is still there, it moves once: to the first blocking issue's policy, else to Load. After Load, and after a reopen, focus is on the canvas. Esc closes the load step in any state and keeps nothing. The state-by-state behavior is on the transfer-export mock.

2. Reopen the project a week later

Everything as it was, nothing selected. Recent projects reopens March transfers with its filter chip, style layers and layout exactly as saved, and nothing beside the project name, as at any rest. Nothing is selected, so the inspector describes the whole graph and no number is silently scoped to last week's selection. Keyboard focus lands on the canvas, and a screen reader hears "March transfers reopened, 3,000 nodes, nothing selected".

Did anything change since? Version history replaces the inspector in the right column and lists the data versions since her last session; Done brings the inspector back. Then the Notes panel holds last week's notes, and a result that went out of date says why on its own row in the Results panel, so she never reads a stale number as current.

Against Figma. Recent projects is Figma's Recent files; Figma also reopens a file with nothing selected; and Version history is a mode of Figma's right panel, as it is here. This swimlane departs from Figma nowhere. Saving last week's selection in the project file is proposed for the owner's decision and is not drawn, because no session has shown that analysts want it.

Counts, failures and the keyboard

  • Steps from the start screen. A file: 3 steps, no travel (Open...; the file; Load), plus one per blocking issue and, for Sarah, one more to declare the weight. A sample: 1 step. Past the drawing limit: the same 3, then Narrow the graph.... Reopen: 1 step to rest, and Version history 1 more.
  • First failure. Loading: a weight left unknown that already shapes PageRank and communities; amounts read as text are caught before Load. Reopening: a result read as current that went out of date when the data was replaced.
  • Keyboard. The start screen's lists are one Tab stop each, arrows move, Enter opens. The load step is a dialog: Tab runs format, columns, issues, sample, footer. Every command is also in Quick actions.

What the study checks

Each is a task a participant is given in plain words, never naming the control, with what counts as a pass. The full wording is in the study hypotheses for this flow.

  • "Load this export so that a ranking of accounts reflects how much money moved between them." Passes if the participant declares what amount means before running, or can say afterwards that a bigger amount counted as a closer tie. Half the sessions use the alternative that asks in the load step.
  • "Tell me whether graphty read the amounts correctly, and how you know." Passes if they point to the issue, the marked sample cells or the Last import row.
  • "How many different pairs of accounts moved money in March?" Passes at the 9,113 transfers less the 412 repeats; 9,113 fails.
  • A week later: "Has anything changed since you left it? How can you tell?" Tests whether nothing beside the name is enough, against a line "Last edited 7 days ago" that clears on the first interaction (a departure from Figma, adopted only if clearly better).

Changes this flow proposes

Recorded with the old text, new text and evidence in framework-changes.md, under "Load and characterize":

  • Which issues block Load: only one where no reading keeps every value. This replaces two earlier, contradictory entries and matches the first-look and load-step mocks.
  • Where focus lands in the load step, and that Esc keeps nothing.
  • Read as... is offered only when a file's name and content disagree.
  • Undoing a first load leaves an empty project, not the start screen.
  • Withdrawn: asking what a bigger weight means in the load step (it disagrees with the load-step mock's proposal; the study decides), and a "Last edited" save state after a reopen.
  • For the owner's decision, untested: saving the selection in the project file.
