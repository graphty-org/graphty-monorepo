## Priorities and values

- **Equal path, not a separate path.** A keyboard or screen-reader user does the same tier 1 task
  through the same commands, not an "accessible mode". This also follows the owner's rule of no
  persona-specific features (2026-09-26) -- accessibility is met by the default UI.
- **Get to the data, and get back to where I was.** Morgan's two first-five-minute questions are
  the right summary of what a blind analyst judges a tool by. Text equivalents (table, inspector,
  neighborhood list) and predictable focus return are worth more than canvas tricks.
- **Measure, do not assume.** Contrast by computed ratio, names by accessibility tree, keyboard by
  actual key presses on the real build. A simulated participant's opinion is held one level down.
- **Fix it once, where every consumer gets it.** compact-mantine for controls (focus rings, toast
  roles, segmented control keys, tree row naming), graphty-element for canvas, keys, walk and
  announcements of graph facts. An app-side aria patch over a component defect is forbidden.
- **Quiet but not silent.** One utterance per change; notices never take focus; never speak the
  same thing twice (toast plus live region).

## Design criteria

- **Keyboard (2.1.1, 2.1.2):** every tier 1 control reachable and operable; no trap; the rail and
  the toolbar are one Tab stop each with arrow-key roving focus; Tab leaves the canvas. Reason:
  the framework's focus-region model, Figma parity with WAI-ARIA composite widgets.
- **Focus order and return (2.4.3):** closing a popover, dialog or menu returns focus to its
  opener; deleting a row moves focus to a neighbor row; focus never falls to body (studio rule
  since round 6). Reason: round 8 Morgan lost place after export ("a dead end and a surprise").
- **Focus visible and not obscured (2.4.7, 2.4.11, 1.4.11):** 3:1 ring on every control; inside
  tight rows the ring draws inside the box (tree row fix 2026-10-03); the focused control scrolls
  clear of toolbar, dock, popovers and toast.
- **Names (4.1.2, 2.5.3):** every icon-only control has the tooltip's words as its name; no two
  reachable controls share a name; row actions name their row; disabled controls are
  `aria-disabled`, focusable, with the reason readable. Reason: round 7 finding 16, round 8
  finding 5.
- **Status messages (4.1.3):** run added/finished/failed, selection count ("on canvas"), label
  counts, export saved, load finished/refused reach the screen reader without moving focus, once.
- **Contrast (1.4.3, 1.4.11):** the app theme is `createCompactTheme({ highContrast: true })`
  (confirmed in `graphty/src/theme.ts`); with it off the focus ring and brand-fill text measure
  2.99:1 and placeholders 2.3:1. Canvas: selection, focus and state marks keep 3:1; data fills
  may sit lower because their text form is in the table.
- **Color never the only signal (1.4.1):** failed run, stale set, invalid field carry a word or
  form too.
- **Single-key shortcuts (2.1.4):** Settings > Accessibility and input switches them off; camera
  keys act only while the canvas has focus.
- **Target size (2.5.8):** 24 px minimum, or 24 px spacing; row actions on a 20 px pitch were a
  real defect.
- **Reflow and resize (1.4.4, 1.4.10, 1.4.12):** 200% text and 320 px reflow, canvas and table
  claiming the 2D exception; owner's platform floor is an iPad with a keyboard.
- **Motion (2.2.2, 2.3.3):** a layout that runs over 5 s has a visible pause; reduced motion cuts
  camera animation. Not drawn until the element honors it -- an unbuilt item is not drawn.

## Thinking

- **What a first-time keyboard or screen-reader user's core path needs, in order.** Start screen:
  usage card answerable without hunting (it sits at the foot; check Tab order puts it where it is
  heard early or is announced); sample cards whose names include what each sample is (known gap).
  Load: Data page with focus on Load and a status line that says what arrived, in counts. Read
  what loaded: the graph inspector's Values as plain text. Analyze: the popover's filter box,
  arrow-key list, Run; then an announcement that the run was added and when it finished, and the
  result readable in the table (run-result columns) and the run row's Values. Labels: Label "+"
  opens the attribute list with focus in it. Find a node: "/" then type, Down, Enter; the node
  opens on Values; Degree selects neighbors; the neighborhood list reads names. Export and save:
  dialogs that return focus. Each step is testable with the real-app tool by keys alone.
- **The canvas is not my blocker for tier 1 -- its text equivalents are.** Until #800 and #794
  land, the honest claim is: everything the drawing says is in the table, inspector and legend
  text. The legend card should be real text in the DOM (it is built from `styles.legend()`); the
  exported image needs alt-ish text (method, channels, ranges) or at least the legend's facts in
  the export notice.
- **Scattered live regions are a risk both ways.** Several polite regions can speak in an
  unpredictable order or speak twice with a toast. One app-level announcer fed by element events
  (selection, run status, history) would satisfy 4.1.3 cleanly -- but the facts and events must
  come from graphty-element (a consumer embedding the element alone deserves the same), and the
  words from the app. Decide after hearing what the build actually says.
- **Simulated-participant limits.** I will not count a simulated SR session as a pass. I will
  count an accessibility-tree check and a keyboard-only scripted run as evidence, and name what
  still needs a real NVDA/VoiceOver session (framework `research/interface-checks.md` 5 lists it
  as owed).
- **Where my findings go.** Component defects -> compact-mantine; graph/keys/announcement facts
  -> graphty-element; app-only defects (wrong name, focus not returned, missing region wiring)
  -> fix locally in the studio worktree and re-test.
