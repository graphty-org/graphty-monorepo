# Round 2 insights: the tier 1 study on the real graphty app

Written 2026-10-07 from `scores.md` after two independent skeptics tried to refute every insight
and confirmed problem against the session transcripts, the grades, the reproduction folders
(`repro/<session>/`), the screenshots, the study tool (`tool/real.mjs`) and the app and
graphty-element source. Rule applied: an item both skeptics drop is dropped; an item one skeptic
drops or weakens is weakened.

**Read every item with these caveats.**

- All participants are simulated, and all are the same model playing different personas. "Seen in
  2 or more participants" is not independent confirmation. A finding is solid when it has a
  scripted reproduction or a cause found in the code. A failure is strong evidence; a pass is weak
  until real people confirm it.
- **The study tool has three blind spots in screen-reader mode** (`tool/real.mjs`, `srReport` and
  `watchLive`), and every screen-reader finding that rests on them is "not shown":
    1. It prints only the focused element's own name and does not follow `aria-activedescendant`,
       so it cannot hear which option is highlighted in a list such as the Analyze filter. The
       Analyze filter is built the standard way (`graphty/src/workspace/analyze/AnalyzePopover.tsx`
       around line 264 sets `aria-activedescendant`; each option sets `aria-selected`), and so is
       compact-mantine's `QuickActions.tsx` (line 255).
    2. It has no browse (reading) mode. A real screen reader's reading mode reaches plain text, such
       as the Overview's counts, without anything being focusable.
    3. It logs a live region the moment it appears with text, and logs every intermediate change. A
       real screen reader often says nothing for a region inserted already filled, and a polite
       queue may speak only the last change.
       The browse-mode effects are argued from the tool's code, not measured: no session was re-run
       with a real screen reader.

**The stall rule: "no decline", not "rose".** Round 1's ease was asked the other way round
(7 = very hard) and converted as 8 minus the rating; a reversed scale is a known source of rating
shift, so ease 4.07 to 4.88 (core four), 4.50 to 4.98 (tier 1) and T12's 2.86 to 5.25 cannot be
read as gains. Success on the core four (24 of 26 to 33 of 34) can stay, though both are near the
ceiling with small samples. Round 3 is still justified: nothing declined, and the problems below
are concrete.

## Verified insights, most important first

1. **Export is where the drawing stops telling the truth.** The exported key keeps "Color:
   Connections" after a community run repaints every node (r2-s56, reproduced: `repro/r2-s56/run/07.png`).
   "For print, 4x" is the 2x picture enlarged: graphty-element's `ScreenshotCapture.ts` uses
   Babylon's `CreateScreenshotAsync`, which scales the canvas rather than re-rendering, and the 4x
   file differs from a bicubic enlargement of the 2x file by a mean of 0.14 on a 0-255 scale
   (measured in headless Chromium). The selection ring also travels into a "current view" export,
   though the preview shows it.
2. **The neighbors task now passes on both halves, through one route.** 8 of 8, 0.9x the success
   path. All 8 came through the "Degree N >" row; none used the Neighborhood command. 4 of 6
   pointer users clicked the chevron first and hit nothing, because it is drawn outside the row's
   button (`repro/r2-s19/run1/04.png`: the click at about 1411, 236 lands on the group "Summary
   values"); each recovered in one click.
3. **Layouts are the weakest tier 1 task (T11: ease 3.33, 5.2x, n = 3), driven by real defects.**
   Force re-applied with a changed spring length leaves an unsettled cloud, identical over 12 s
   while other layouts animate (`repro/r2-s40/run/13.png`; cause untraced). The group layouts stay
   disabled after a community run made groups. 2D Fit zooms into one edge or letter. The numbers are
   inflated by the prompt ("clusters ... easier to tell apart" invites trying the disabled group
   layouts), so read the defects, not the ratio.
4. **The app is deciding what counts as a grouping, and it decides wrong.**
   `graphty/src/workspace/layout/methods.ts:83` `groupings()` reads only
   `session.data.attributes()`, so a computed community result never qualifies. Beyond the defect,
   choosing which columns can group a layout is graph logic in the app; under the architecture it
   belongs in graphty-element as a neutral fact, with the app only rendering it.
5. **Hidden names have no way out -- but how often users hit it is unknown.** T10 (8 of 8 SD, ease
   4.25, 3.5x, about 5 wrong turns each) asked for "every character's name"; `answers.md` records
   that the build has no control that shows every name and that success only needs the hidden
   count read. The prompt sent every participant hunting for something that does not exist, so its
   step and wrong-turn numbers measure the wording as much as the app. The gap itself is real; View
    > 2D reaches 0 hidden (r2-s13, r2-s17).
6. **Sizing by a result is still found by guessing** (18 of 18 T9 and whole-session sessions named
   it; severity 2, one model's shared guess repeated). It remains the largest single cost to ease on
   the core path.
7. **Announcements are missing where they matter, independent of the tool.** A load never announces
   that it finished or its size, and a finished analysis run is never announced: the only spoken
   line is "added, running" (`WorkspaceToolbar.tsx:265`), and graphty-element's shadow DOM has no
   live region. The claims that "No nodes to draw" is spoken first and that one event is announced
   twice are weakened (tool blind spot 3).
8. **What worked holds:** loading and ranking are quick; the whole first session passes; save and
   reopen 3 of 3; the usage card raised no wrong belief; the sample is one action from the start
   screen; the keyboard-only persona passed all three core tasks; no false "done" in 56. The
   refusal of a broken file from "Open project or file..." gave cause, line and remedy (all 3
   succeeded, ease 6), though the screen-reader session heard it as two alerts.
9. **Overlays: count events, not sessions.** The fixed layout seed puts Pazzi (Florentine families)
   and Blacheville (Les Miserables) under the key on every load, so "15 sessions" is about one event
   per dataset. The overlap is real; its frequency is the seed's.

## Dropped

- **"The Analyze filter and attribute filter announce no option when arrowed; a wrong measure ran
  twice"** (scored severity 3). Both skeptics: tool blind spot 1. The wrong measures in r2-s07 and
  r2-s47 come from it. "Find an attribute" is presumed to work the same way (a Mantine combobox) but
  was not checked against its code.
- **r2-s47's T6 failure as an app finding** (bar 1). Not shown; see the bars table.
- **"The Overview has nothing focusable"**, and "the shortcut dialog cannot be read". Browse mode.
- **"The search box is not found by its visible text" as participant evidence** (6 sessions). The
  tool's click-by-text failing on a placeholder.
- **"The screen-reader session ran the wrong measure first (the list announced no option)"** as a
  reason in the whole-first-session measure.

## What round 3 should change in the study itself

- **Give the tool's screen-reader mode the active option and a reading mode** (follow
  `aria-activedescendant`; a command that reads the text of the current region or dialog), or stop
  grading screen-reader sessions on reading tasks until it has them. Treat live-region text inserted
  already filled as unconfirmed.
- **Do not ask for what the build cannot do.** T10's "every name" made a 3.5x measure out of a
  missing control. Re-word it, or grade the missing control as a finding and leave the measures out.
- **Report the ease trend only within one scale.** Round 3 asks as round 2 did; compare round 3
  with round 2, not with round 1.
- **Count deterministic layout events once per dataset**, not once per session.
- **A real screen-reader user** is the only way to settle bars 3 and 7.
