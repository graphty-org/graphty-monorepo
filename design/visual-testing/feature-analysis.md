# Visual review: feature analysis

Date: 2026-09-27

## What this document is

The graphty monorepo is replacing Chromatic, the hosted service that screenshots every story in
its five Storybooks (graphty-element, compact-mantine, graphty, algorithms, layout), compares each
screenshot with an approved "baseline" image, and lets the owner accept or reject each difference.
Chromatic billed about $3,750 in half a month with no spending cap. The replacement captures the
screenshots in our own GitHub Actions jobs with Playwright, keeps the baselines as PNG files in
git under a root `visual-baselines/<project>/` directory, and reviews them in a page served from
the development server. Accepts are unsigned records marked "unproven" at first, and from
milestone 3 require a signature made with the owner's hardware security key.

This document lists every feature the replacement could have, from three sources:

1. the owner's own list, with the owner's priority;
2. the Chromatic features this repository actually uses today;
3. useful features of other visual review systems (Argos, Percy, Applitools, Happo, reg-cli,
   Playwright, Vitest, BackstopJS, Visual Regression Tracker, GitHub itself).

For each feature it gives what it is, why it matters here, the owner's tier where the owner gave
one, a recommended tier, and the milestone that delivers it. Tiers: **P0** must have, **P1** nice
to have, **P2** later. Where the recommendation differs from the owner's tier, the reason is given.

Milestones are those of `roadmap.md`: **1** approving again (today), **2** every project and the
local hook (within days), **3** owner-only approval enforced (this week), **4** retire Chromatic
(weeks two and three), **5** later. What each milestone contains, the migration from Chromatic and
the cost are in `roadmap.md`; what approval does and does not guarantee is in `design.md`
section 8; what milestone 1 actually built is in `design.md` section 1a.

The evidence behind the numbers is in the companion documents in this folder:
`chromatic-alternatives.md` (options and measurements), `research-chromatic-use.md` (what we use
from Chromatic, with file and line references), `research-other-systems.md` (feature survey),
`research-repo.md` (CI, Pages, pre-push, permissions) and `research-tech.md` (technology choices).

**Note A, the pre-push hook.** Screenshots depend on the fonts and graphics stack of the machine
that takes them, and emoji already render as empty boxes on the development server, so local
captures will not match CI's until both use the pinned font set (milestone 2). Baselines therefore
come only from CI, and the hook, from milestone 2, does two things:

- **Blocks:** a baseline PNG pushed without a review record that names its hash fails the push.
  Seconds, no browser. It is a convenience, since `--no-verify` exists.
- **Captures, opt-in** (`PREPUSH_VISUAL=1`): for affected packages, capture and compare locally. It
  becomes the default only if local captures match CI byte for byte and a typical run stays under
  about a minute.

**Why Git LFS, from the start.** In plain git every baseline version stays in history, which is
estimated to grow by 110 to 210 MB in year one before more browsers, carried by every clone; and
moving to LFS later is a history rewrite (`git lfs migrate import`) that breaks every branch and
every recorded commit hash. So the owner chose LFS before the first baseline. It fits: the Team
plan gives 250 GiB of LFS storage and 250 GiB of bandwidth a month, the estimate is about 0.2 GiB
stored and 1 to 5 GiB a month downloaded (only the capture job fetches images, for its own
project, through the Actions cache), and the organisation's $0 budget blocks rather than bills.
The tooling covers the failure modes: capture stops on a pointer file instead of reporting every
image changed, the review server refuses to start without git-lfs, and the pre-push hook uploads
the images. A separate repository or a submodule was rejected: two-repository accepts, pointer
conflicts, and no images on the pull request. `roadmap.md` ("Storage") and `design.md` section 7
have the detail.

**One diff engine.** The compare step uses pixelmatch, because 14 stories set
`diffIncludeAntiAliasing` and pixelmatch detects anti-aliasing; `tools/pixel-diff.mjs`'s hand-rolled
loop is replaced by it in milestone 4 rather than kept beside it. pixelmatch is vendored into
`visual-review/trusted/vendor/` (it has no dependencies of its own). A size change is reported as
"changed" with both sizes, never as an error, since full-height captures change size whenever content height does.
