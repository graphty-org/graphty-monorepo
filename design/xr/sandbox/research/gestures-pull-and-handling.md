# Research 2: hand gestures, pinch-and-pull, two-hand handling and the held copy

Scope: what already exists that the XR technique sandbox can reuse for (1) gestures, (6) pull to
grow a neighborhood and (10) handling the graph (grab and turn, two-hand scale, a small held copy
in the off hand). The sandbox is built on Babylon.js (the repository is on @babylonjs/core 8.56.2;
9.x is current on npm). Every claim about code below comes from reading the source, cloned or
unpacked under `tmp/xr-sandbox/research-src/`.

## Recommendation per technique

### Gestures (technique 1)

- Static poses: start with a small rule set in the Meta finger-feature style (curl per finger plus
  palm direction), because rules are readable and do not depend on hand size. fingerpose's curl
  estimator does exactly the curl half and is MIT; use it after mapping WebXR joints to its 21
  landmarks. Keep handy.js's pose library (plain JSON, MIT) as a second recognizer behind a
  toggle, so the owner can compare "rule" against "template" recognition.
- Motion gestures (a flick, a circle, a stroke): $Q from the UW $-family, fed with the index
  fingertip (hands) or the controller tip (controllers), projected onto the view plane, started
  and ended by a pinch or trigger. It is BSD, dependency-free and needs one template per gesture.
- Try @clickon/xr-extension in its own sandbox page only, because it insists on owning the XR
  experience and targets Babylon 6. Record whether it survives Babylon 8 and Android XR.
- Do not commit Jackknife: its license forbids redistribution.
- Every recognizer needs the same three guards, none of which handy.js or fingerpose has:
  hysteresis between "begin" and "end" thresholds, a minimum hold time (about 150 ms) before a
  pose counts, and suppression while the hand is pinching or grabbing something.

### Pull to grow a neighborhood (technique 6)

No library does this; it is assembly:

- Pinch detection: reuse `isPinching` / `pinchStrength` from graphty-element's InputUtils for
  hands, and the browser's `select` events (Quest Browser and Chrome on Android XR both report a
  hand pinch as select) for the start and end edges. Take IWSDK's rule of at most one edge per
  frame so a quick pinch never toggles twice.
- Pull distance: distance of the pinch point from where the pinch started, smoothed with
  1eurofilter, mapped to hops with a dead zone and fixed steps (for example 0-6 cm = 0 hops,
  then one hop per 8 cm) so the "1 hop: 6" readout does not flicker at a boundary. Add
  hysteresis on each step boundary.
- Hop counts: `@graphty/algorithms` breadth-first search over the graph-format snapshot gives
  every node's hop distance from the pinched node once at pinch start; the pull then only reads
  that array.
- Release commits; a pinch that ends inside the dead zone cancels.

### Handling the graph (technique 10)

- Grab and move with one hand or controller: Babylon `SixDofDragBehavior` on an invisible grab
  volume around the graph, with `WebXRNearInteraction` and `isNearGrabbable` for grabbing up
  close and the far pointer for grabbing at a distance. Its one-pointer path is already smoothed.
- Two-hand scale and turn: first try `allowMultiPointer = true` as shipped, and record the two
  known gaps for the owner to judge on the headset: rotation is yaw only, and the two-hand path
  is unsmoothed. The fix, if needed, is ours: drive the transform from graphty-element's
  `twoHandGestureDelta` (full 3D rotation, already tested) or a Babylon port of
  @pmndrs/handle's two-pointer math, filtered by 1eurofilter. A sandbox toggle can switch between
  the stock behavior and ours so the owner can feel the difference.
- Held copy in the off hand: no library fits Babylon, but it is small. Draw the miniature as a
  second thin-instance mesh under a TransformNode scaled about 1/40 and anchored to the off-hand
  grip (controllers) or palm (hands, via `HandConstraintBehavior`). Give it the SAME
  Float32Array of instance matrices as the full graph (`thinInstanceSetBuffer` with the same
  array), so it costs no layout work; `Mesh.clone` copies the buffer once and would go stale.
  Edges: one LineSystem or GreasedLine rebuilt only when the layout settles. A small box shows
  the part of the graph in front of the viewer; picking in the copy acts on the full graph. The
  published evidence that this is worth trying for graphs: Drogemuller et al. 2018 found
  Worlds-in-Miniature the least physically demanding and preferred for overview tasks such as
  triangle counting (https://research.monash.edu/en/publications/evaluating-navigation-techniques-for-3d-graph-visualizations-in-v/).
- BoundingBoxGizmo on the held copy is an optional extra for precise scaling; its handles need to
  be enlarged for hands.

## Things to watch on the devices

- Babylon runs left-handed unless `scene.useRightHandedSystem` is set (graphty-element does not
  set it), and converts WebXR poses by flipping z. handy.js poses were recorded in three.js's
  right-handed space: mirror z when matching, or every pose reads as the other hand.
- handy.js matches raw millimeter distances, recorded on one person's hand on a Quest. On a
  different hand or on Galaxy XR's tracker, distances shift; normalize by a hand length (wrist to
  middle fingertip) before matching.
- The Babylon forum reports finger overlap during a pinch on Quest with the default hand mesh
  (https://forum.babylonjs.com/t/webxr-fingers-overlapping-during-pinch-gesture/55325). That
  is cosmetic for recognition (joints are fine) but visible; if it shows, use joint spheres
  instead of the skinned hand.
- Tracking noise: the one-pointer SixDof path lerps at 0.2 per frame; nothing else in Babylon
  filters hand input. Any value we show as a number (pull distance, hop count) or apply as a
  transform (two-hand scale) gets a 1eurofilter.
