# CLAUDE.md

This file provides guidance to Claude Code when working with the @graphty/graphty-element package.

Read `design/graphty-element/agent-reference.md` (from the repository root) before you add or change an entry point,
an import reached by a Node-safe entry point, an extension point, acceleration, a test project or a story, or when
you need the package layout, the architecture or the debugging screenshot commands.

## Project Overview

graphty-element is a Web Component library (`<graphty-element>`) for 3D/2D graph visualization: TypeScript (ES2022,
strict), Lit, Babylon.js and Vite, with layouts, style layers, AI integration (`./ai`) and XR support. It publishes a
map of entry points, not one barrel; the source of each subpath is the same-named `.ts` file at the package root.

## Essential Commands

```bash
npm run dev / storybook / docs:dev   # need PORT: start through servherd with PORT={{port}} (root CLAUDE.md)
npm test -- --project=<name>         # one test project (names below)
npm run coverage:fast                # quick coverage (default project only)
npm run lint                         # ESLint + TypeScript check (lint:fix to fix)
npm run build                        # library build + ./bundle build + declarations; rewrites jsx.ts
npm run api:report                   # after build, when the public API changed
```

## Rules

### Entry points and imports

- `./session`, `./schema`, `./catalog`, `./commands`, `./extend`, `./format`, `./logging` (and the empty `./react`)
  must resolve in Node with no Babylon.js, Lit or DOM. A value import that reaches a mesh, material, scene,
  `LitElement` or `document` from anything they reach fails `test/packaging/node-safe-entries.test.ts`, far from the
  file you edited. Use `import type` when you only need a type.
- `webgpu.ts` is the only file allowed to import the optional peer `@graphty/webgpu-graph-algorithms`.
- `jsx.ts` is generated by `npm run build`; after changing a public property, attribute or event, build and commit
  it (`test/packaging/jsx-types.test.ts` fails until you do).

### Extension points

- The supported set is closed: palette, file format, camera, layout, algorithm, logging, all exported from
  `./extend`. Anything else registrable is internal.
- An extension must be able to do everything its built-in peer can (catalog entry, addressable key, progress and
  cancellation, options, `GraphtyError` codes, typed against a published entry point). A capability not exercised
  by `test/browser/extensions/` is not promised.

### Error model

Every failure the element reports is a `GraphtyError` carrying a `GraphtyErrorCode` from `src/errors/codes.ts`. The
code is the contract; the message may change in any release. Sibling packages' errors are re-reported as one of
these codes with the original as `cause`. There is no `E_NOT_READY`: every method is safe before the element is
ready, and work queues until it is.

### Every change goes through the dispatcher

Undo covers every change a project saves because there is one path for changes: the session's dispatcher
(`src/session/project/Dispatcher.ts`). Project state is frozen outside it, and the strict build (every test) throws
on a write that did not come through a command.

- A new public member that changes the graph, a style, a setting or anything a project saves dispatches a command;
  it never writes a manager, record or map itself, and never records its own undo. List it in
  `src/session/commands/doors.ts` (`test/session/history/doors.test.ts` and `test/browser/doors.test.ts` fail
  otherwise).
- A new op declares `undoable`, or `exempt` with a reason, in its definition under `src/session/commands/` and in
  `COMMANDS` (`commands.ts`); an undoable op needs a round-trip fixture in `test/session/history/fixtures.ts`
  (`test/session/history/vocabulary.test.ts`).
- Exempt means it changes nothing a project file saves (camera, selection, a moving layout, a device session). When
  in doubt it is undoable.

Consumer guide: `docs/guide/undo.md`; design: `design/undo/undo-design.md`.

### Acceleration

- `src/acceleration/` owns acceleration end to end (registry, `AccelerationController`, `Capabilities`); a consumer
  writes no probe, construction or device-loss code. Nothing there names a GPU type; WebGPU arrives only through
  `./webgpu`.
- Only members listed in `src/acceleration/narrow.ts` are offered to the device, each above its measured floor in
  `src/acceleration/types.ts`.
- `src/testing/fakeAccelerator.ts` is the one fake accelerator, shared by tests and stories; write no second one.

### Test projects

- `default` (happy-dom, unit), `browser` and `storybook` (Playwright, 5 CI shards each), `interactions`,
  `minimum-work` and `xr` (in the CI browser shards): run on pull requests when affected.
- `lifecycle` (autosave across reload, close, crash and kill; needs `npm run build`): its own shard,
  `graphty-element-lifecycle`, full run only.
- `llm-regression` (real, paid LLM calls): only in release.yml candidate runs, never on a pull request or master
  push.
- A new test that waits for the final picture of work split across frames joins `MINIMUM_WORK_TESTS` in
  `vitest.config.ts`.

## Common Pitfalls

- **Entry point contamination**: see "Entry points and imports" above.
- **The color helpers are total and do not throw** (`hexToRgb` returns `null`, `interpolatePalette` returns
  `MISSING_DATA_COLOR` `#ff00ff`); only an empty palette throws. Delete old try/catch or `undefined` pre-checks
  around them rather than copying them. Magenta on screen is a bug: fix the layer's selector so the unmeasured
  element is never visited; do not pick a prettier color.
- **Manager pattern**: always use manager methods (`styleManager.addLayer(layer)`), never direct manipulation
  (`graph.styles.layers.push(layer)` bypasses cache invalidation).
- **Algorithm registration**: every algorithm class calls `Algorithm.register(MyAlgorithm)` with a static
  `namespace` and `type`.

## Testing Guidelines

- `assert` is the house style (`import { assert, describe, it } from "vitest"`); use `expect` only where it earns
  its place (`expect.each`, whole-array `toEqual`, async matchers). Import both explicitly even though
  `globals: true`.
- Visual tests run sequentially (`--workers=1`).
- Temporary files (screenshots, debug scripts) go in `./tmp`. Never create `__screenshots__` under `./test` unless
  intended for commit (failure screenshots go to `tmp/vitest-screenshots`).
- Tests wait on conditions and assert on counted work; the `local/no-test-timing` lint rule enforces it.
- A new public method is classified in `test/cost-coverage/method-classes.ts`; a mutating one needs a counted-work
  test (`assertScalesLinearly` in `test/helpers/cost.ts`) registered in a sibling `<name>.counted-work.ts` module,
  or `test/cost-coverage/cost-coverage.test.ts` fails. Covering a method deletes its file in
  `test/cost-coverage/not-yet-covered/`; when another open pull request edits the same module, add
  `<name>.<topic>.counted-work.ts` instead.

## A story is a test, and a capability must never lose its last door quietly

The history behind each rule is in the reference file.

- **A story is a test.** Never delete one, hollow one out or leave it named for something it no longer draws. A
  story pinning behavior that is going away is replaced by one pinning the new behavior, and the removal is recorded
  in `stories/story-roster.json`.
- **A capability that loses its only public route is a blocking finding, recorded before the change lands**: a row
  in `design/element-api/capability-losses.md` and an entry in `src/catalog/unreachable.ts`, not a code comment or
  a report paragraph.
- **An agent that computes a loss list writes it to a file before it reports**, and puts "what I could not do" at
  the top of its report.
- **When a contract test goes red, write the answer down; never loosen the test.**
  `test/contracts/story-roster.test.ts`, `test/contracts/config-reachability.test.ts` and
  `test/browser/channel-paints.test.ts` each go green only when the reason exists in a file in the repository.
- **A story named after a style channel paints that channel** (`test/contracts/story-demonstrates-its-subject.test.ts`).
  The honest fixes are to put the missing layers back, or rename the story and edit the roster in the same change.
- **A waiver that records a defect expires.** Entries in `src/catalog/unreachable.ts` are `by-design` (permanent) or
  `defect` (owner and expiry; `test/contracts/waiver-expiry.test.ts` goes red the day after). When arguable, it is a
  defect. Agents write `WAIVER_OWNER_UNASSIGNED` as the owner, never a person's name.

## Rules moved from the root CLAUDE.md

These apply to every consumer of graphty-element's styling, acceleration and API, not only to work in this folder.

### WebGPU

- Never create fallbacks if WebGPU isn't supported. The GPU package throws (`E_NO_WEBGPU`, `E_NO_ADAPTER`, `E_TOO_LARGE`, ...) and never runs a CPU path; the CPU packages' dispatchers choose the CPU only when no accelerator was injected (`design/webgpu/webgpu-acceleration-plan.md` section 2.4).
- **graphty-element owns WebGPU detection, construction and lifecycle**, per the Architectural Principles above. `@graphty/webgpu-graph-algorithms` is an OPTIONAL peer dependency of graphty-element: present, the element uses it; absent, the element runs the CPU path and says so. A consumer never writes probe, construct, inject or device-loss code, and the graphty app gets no special privileges here -- whatever the app can do, a third-party consumer can do the same way.
- This OVERRULES design 9.1 (`design/webgpu/webgpu-acceleration-plan.md:2870-2899`), whose dependency diagram ends at the app and makes the app the only importer of the GPU package. That section is superseded, not deleted; the decision record is `design/decisions/`.
- "Never create fallbacks" is about SILENT DEGRADATION, not about capability detection. Detecting that WebGPU is unavailable and running the CPU implementation is correct and required. Catching a GPU error mid-run and quietly finishing on the CPU is not: that hides a real failure and makes a benchmark meaningless.

### Graph Styling

- Node and edge appearance MUST be applied through a style layer, as a layer handed to
  graphty-element through the StyleManager
- It MUST NOT be applied manually under any circumstance -- never by mutating a mesh, a
  material, or a node or edge object
- The failure mode: styling applied outside the layer system is invisible to the layer list,
  cannot be reordered, removed or persisted, and is silently lost at a dataset boundary

### Algorithm Styles

- An algorithm's suggested style layers MUST write ONLY to the nodes and edges that are part of
  that algorithm's own result. Dijkstra styles the nodes and edges ON the path; every other node
  and edge MUST be left exactly as the layers beneath it painted them, UNMODIFIED
- "Part of the result" means the element carries a value this algorithm produced. Degree colours
  every node because every node HAS a degree; Dijkstra colours the path because only path
  elements have `isInPath == true`. An element the algorithm has nothing to say about is not
  the algorithm's to paint -- not even to a default, a muted grey, or a full opacity
- Two ways a layer breaks this, both silent:
    - an empty `selector: ""` matches EVERY node or edge, so the layer's `calculatedStyle` runs
      on the whole graph. Calculated values are last-writer-wins, so the write lands whatever the
      value is -- including the value the expression returns for "not in my result"
    - a helper with an un-highlighted branch (`blueHighlight(false)` returns `#CCCCCC`) turns
      "this element is not part of my result" into a paint instruction. So does an input that is
      `undefined` before the algorithm has even run
      Scope the layer with a selector that matches only the elements carrying a result
      (``algorithmResults.graphty.dijkstra.isInPath == `true` ``), so a non-result element is never
      visited at all
- Dimming, fading, greying or hiding what an algorithm did NOT select is a READER's choice, not
  the algorithm's. It belongs to the caller -- a story, the app, a user-added layer -- and MUST
  NOT ship in `suggestedStyles`
- Why: layers stack bottom to top, and `applySuggestedStyles(["a", "b"])` appends a's layers and
  then b's, so the last algorithm applied wins every property it writes. One algorithm that
  writes to everything erases every algorithm under it -- and stacking algorithms is the entire
  point of style layers

### Public API review

graphty-element's public API is committed as a report: `graphty-element/api/<entry>.api.md`, one
per typed entry point in its package.json `"exports"` (`index` for `.`), written by
@microsoft/api-extractor from the built `.d.ts` files. A pull request that changes the API shows the
change as a diff of those files.

**"Public API report (graphty-element)"** (ci.yml's Checks job) fails when the
built API differs from the committed report. Build, then run `npm run api:report` in graphty-element
and commit the report with the change. An agent whose pull request changes the report says so in
the pull request description: which entry points, what was added, changed or removed, and whether
it is breaking.

The same check fails when the report adds a property typed plain `string` to a result type -- a type
whose name ends in `Result`, `Summary`, `Estimate`, `Recommendation` or `Explanation`, or one a
`GraphSession` method returns -- compared with the merge base with origin/master. Use an exported
string-literal union of codes or a `CodedFact` `{ code, params }` instead. Identifiers, names of the
consumer's data and catalog names are allowed by `PLAIN_STRING_ALLOWLIST` in `tools/api-report.mjs`,
and a descriptor's `description` is catalog data. Fields that already exist never fail.

### Module System

- ES modules are the default format
- Bundled distributions: `dist/{package}.js`
- graphty-element is ESM-only. It publishes a map of entry points rather than one barrel, and
  five of them -- `./session`, `./schema`, `./catalog`, `./extend` and `./format` -- must stay
  free of Babylon.js, Lit and the DOM so they run in Node. A test fails the build if one of
  them stops being. A consumer with no bundler loads `./bundle`, a single self-contained file
  built by `vite.bundle.config.ts`; that replaced the UMD build, which is gone
