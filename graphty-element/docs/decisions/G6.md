## 3. The minNodes measurement (design 13 row P12), dev box, 2026-09-22

Command: `LD_LIBRARY_PATH=<libEGL tree> XDG_RUNTIME_DIR=/tmp node scripts/measure-min-nodes.mjs
--adapter nvidia --sizes <...> --frames 60`. Hardware: RTX 4070 SUPER, headless Chromium through
ANGLE's Vulkan backend. Raw output: `tmp/m6/t9/nvidia-a.json` (500 / 1000 / 2000) and
`tmp/m6/t9/diag5000.json` (5000).

Frame time is the median `requestAnimationFrame` delta while the layout is WORKING, in
milliseconds; lower is better. Every graph has average degree 10.

| nodes (avg degree 10) | CPU median frame ms | GPU median frame ms | GPU / CPU | runs x sampled frames |
| --- | --- | --- | --- | --- |
| 500 | 50.0 | 50.0 | 1.00 | 3 x 60 |
| 1000 | 116.7 | 116.7 | 1.00 | 3 x 60 |
| 2000 | 216.6 | 183.3 | 0.85 | 3 x 60 |
| 5000 | 566.7 | 466.6 | 0.82 | 1 x 5 -- ONE run, read it with the third note below |
| 10000 | not measured | not measured | -- | -- |
| 20000 | not measured | not measured | -- | -- |

Crossover: 500, the smallest size measured. Default set to: 0 (`ACCELERATION_MIN_NODES_DEFAULT`,
`src/acceleration/types.ts`, whose JSDoc carries this table's first four rows). No size's
median has the accelerator slower than the CPU, so there is no size below which the element should
decline it (the third note below says which single run does not fit that sentence).

The largest size's readback share of the frame: NOT MEASURED, and not estimated.
`scripts/measure-min-nodes.mjs` times whole `requestAnimationFrame` deltas from inside the page,
which cannot be decomposed into the position readback, the force computation, the publish and the
draw. The field matters -- design 7.21 names the readback as what raising `iterationsPerStep` buys
back, and that is why the rule exists -- so leaving it empty would read as zero. Separating it needs
a timestamp query or a counter inside the accelerator rather than a frame clock in the page, and
that instrument does not exist in this phase.

Three things a reader should not take from this table:

- **It is frame time, not layout throughput.** At 500 and 1000 nodes both arms read the same
  multiple of the display interval, which means the frame is spent somewhere other than the force
  computation -- publishing positions and drawing them. A tie is recorded as a win for the
  accelerator on purpose (it costs nothing extra), and it is also the honest answer: at these
  sizes the layout is not what the frame is waiting for.
- **The two largest sizes are unmeasured, and the reason is mounting, not layout.** Loading 5,000
  nodes and 25,000 edges into the element takes 53-84 seconds in this browser, and the cost grows
  faster than the graph; six mounts at 10,000 and at 20,000 would measure the element's mesh
  construction rather than its layout. The default does not turn on those sizes -- the crossover
  is at the bottom of the range, not the top -- so they are recorded as a follow-up rather than
  guessed at. The mount cost itself is worth a look by someone: see section 6.
- **The protocol was shortened, and one arm of it is not stable.** The plan (PD-23) specifies the
  median of 300 frames after the first 30, three runs per arm. This ran 60 frames after the first
  30 at every size, three runs per arm at 500 / 1000 / 2000 and a single run of five frames at
  5000. The window also closes early if the layout settles inside it, because a frame time measured
  after the arrangement has come to rest is the idle renderer's on every path -- a guard that has
  never fired: every arm behind both tables in this section printed NOT SETTLED. Two of the three
  sizes that got three runs repeated exactly -- 50.0 / 50.0 / 50.0 on both arms at 500, and
  183.3 / 183.3 / 183.3 on the accelerated arm at 2000. The third did not: at 1,000 nodes the
  accelerated arm read 116.7 / 183.35 / 100.0 ms, a 1.8x spread, against a CPU arm that read
  116.75 / 116.7 / 116.6. Its median is the 116.7 the table above reports as an exact tie, and that
  row is the one a 300-frame window could move. It cannot move the DEFAULT: the crossover rule asks
  for the smallest size at which the accelerated arm is at or below the CPU, that size is 500 --
  the smallest measured, where both arms repeated 50.0 three times -- and 0 is already the lowest
  the default can be. The script takes the full protocol's numbers as arguments for anyone who
  wants them.

SwiftShader, the same script under `--adapter swiftshader`, one run of 30 working frames per arm on
2026-09-22 (raw output `tmp/m6/t9-fix2/swiftshader.json`). It is recorded for information only and
sets nothing: software WebGPU is a CPU rasteriser wearing a device's clothes, so the accelerated arm
is the same processor doing the same work through a driver.

| nodes (avg degree 10) | CPU median frame ms | software device median frame ms | ratio |
| --- | --- | --- | --- |
| 500 | 49.95 | 50.00 | 1.001 |
| 1000 | 83.40 | 83.35 | 0.999 |

The adapter reported vendor `google` and the accelerated arm reached `active` at both sizes, so
these are a software device's numbers and not an arm that quietly ran on the CPU. They say what
PD-23 expects of software WebGPU: it neither wins nor loses, both arms read the same multiple of the
display interval, and the two rows differ by a single frame quantum -- once in each direction. That
last detail is the whole reason PD-23 forbids SwiftShader from setting the default: the crossover
rule applied to these two rows alone would return 1,000 rather than 500, purely from quantisation
noise.

The `iterationsPerStep` auto-raise (M6-T4) engages above 250,000 nodes, which no measured size
reaches; that rule is covered by its unit test, not by a measurement.

## 5. Baselines committed

Chromatic has not been run on this branch. Two new stories are snapshotted when it runs --
`stories/LayoutGpu.stories.ts`'s `ForceAtlas2Fake` and `SpringFake`, both on the deterministic fake
accelerator, so the picture is the same on every machine. One thing to know before reading those
two: this fake's movement is a rigid translation along x, which the bridge's refit removes on the
way out, so both pictures are the seeded arrangement framed at the configured radius. The fake is
no less useful for it -- each story's `play` asks the fake itself whether the layout ran on it --
but a reader comparing the two shots to the CPU ones should not expect the forces to have moved
anything.

EVERY force-layout baseline is expected to MOVE, and all of them are now safe to take. Three
changes moved them, in this order.

Spring and ForceAtlas2 became simulations that keep stepping rather than one-shot engines that
arranged the graph once, so their arrangements differ from the committed baselines on shape alone.

The camera fix moved the ForceAtlas2 frame and nothing else: Spring's camera stayed at z -253.7
with the far plane at the 10,000 default, where ForceAtlas2's went to -20953.8 and 41230.8.

The envelope fix then moved both, and is what makes the ForceAtlas2 picture worth a baseline at
all. Every simulation layout is now published fitted to its `scalingFactor`, so ForceAtlas2's
camera came back to -199.4 with the default far plane and its nodes grew from 0.033 pixels to
3.46; Spring's camera moved from -253.7 to -244.0 and its nodes from 2.72 pixels to 2.83. The
retaken shots are `tmp/m6/T10-envelope/`: `layout-3d--force-atlas-2.png`, `layout-3d--spring.png`
and `layout-2d--force-atlas-2.png`. Earlier gates said no ForceAtlas2 baseline should be accepted
while the story drew 196 dark pixels of an arrangement that was really there; it draws 11,657 now,
and that reservation is lifted.

Two repairs to the envelope landed after those shots were taken and MOVE NEITHER of them, which is
why they were not retaken. A row a pin or a drag is holding is now left out of the measurement as
well as out of the write, and no story holds a row -- a story loads, settles and is photographed,
so the rows measured are the same rows as before. And `scale`, which Spring and spring-electrical
publish as "Scale", now reaches the radius the arrangement is published at instead of being divided
back out by the refit; every story leaves it at its default of 1, which multiplies nothing. A story
that sets it WILL move, by exactly the factor it sets.

The graphty app's Chromatic run also takes new pictures: `graphty/src/stories/StatusBarAcceleration.stories.tsx`
is new, and `graphty/chromatic.config.json` turns `onlyChanged` off for the build that accepts them.

- **The graphty app did not compile against this element (row 20), and the element was where the
  fix belonged. CLOSED on 2026-09-22 by the three exports.** `graphty/src/components/shell/defaults/accelerationSettings.ts` and
  `shell/panel/SettingsOverlay.tsx` import `ACCELERATION_POLICIES`, `ACCELERATION_POLICY_DEFAULT`

  included, finds zero hits. `pnpm run typecheck` in `graphty/` fails with 11 errors -- two
  unresolved imports in each of those files, one more in the settings test, and the `unknown`,
  `undefined` and implicit-`any` fallout of the missing guard and the missing list. The app is doing
  what the root CLAUDE.md asks: its own comment says an app-side `"auto"` would be a copy of the
  element's initialiser, free to disagree with it the day the element changes its mind, so it
  refused to write one. The element now publishes all three -- `ACCELERATION_POLICIES`,
  `ACCELERATION_POLICY_DEFAULT` and `isAccelerationPolicy`, declared in

  `tsc --noEmit` in `graphty/` now exits 0, and the app writes no policy literal anywhere. They are
  published API on an entry point third parties consume, so the sign-off below covers them.
- **ForceAtlas2 rendered nothing, on the GPU and on the CPU alike (row 10). CLOSED on 2026-09-22
  by two fixes.** Both ForceAtlas2 paths settled into a box about 23,000 scene units across, and
  two separate things went wrong with that box.

  The first was framing, and an earlier draft of this gate misdiagnosed it. It said the bridge
  drops `scalingFactor` on the way out. It does not: `layout/src/simulation/forceatlas2.ts:740`
  writes `owner[3 * i] = pos[3 * i] * scale + cx` against a seed that divides by the same scale,
  and `src/managers/LayoutManager.ts` hands the simulation `scale: options.scalingFactor` (default
  100). `OrbitCameraController` and `TwoDCameraController` now derive the camera's far plane from
  the measured bounding box instead of leaving Babylon's default 10,000, and the fit is no longer
  cut down to `maxZoomDistance`, which stays the interactive zoom-out ceiling and follows the
  fitted graph. Pinned by `test/cameras/OrbitCameraController.test.ts` and
  `test/cameras/TwoDCameraController.test.ts`, both asserting `camera.isCompletelyInFrustum` over
  a box tens of thousands of units across.

  The second was that **a node is one scene unit across whatever the layout does**, which is true
  of every visual size in the element: node size, edge width, label size and arrow size are all
  absolute scene units tuned for the plus-or-minus-100 box the element's fourteen one-shot layouts
  publish into. Those reach it because `@graphty/layout` rescales their output into a unit ball
  (`layout/src/utils/rescale.ts`) and the element multiplies by `scalingFactor`. The simulations
  are the only layouts that never rescale -- `layout/src/simulation/forceatlas2.ts` says so in its
  header -- and a ForceAtlas2 equilibrium grows with the graph, so the same multiplier was applied
  to coordinates already in the thousands.

  The decision taken was to normalise, in the ELEMENT rather than in the layout package, whose
  stated contract is that it never rescales what it computes. `SimulationLayoutEngine` now runs the
  simulation in an array of its own and `publishPositions()` maps it into the element's: the
  arrangement's widest radius about its own centre becomes the layout's `scalingFactor`,
  remeasured at every publish so a settling graph holds its apparent size instead of flying out of
  frame, with a single node and an all-coincident seed both publishing at their own size rather
  than dividing by a radius of zero. Everything written INTO the simulation -- a drag, a pin, a
  `setNodePosition`, the seed -- arrives in scene units and is divided back out. The simulation's
  own settle rule, trace and statistics are untouched, because they are computed in its units and
  its units do not move. Nothing in the layout package changed.

  THE RADIUS IS MEASURED OVER THE ROWS THE PUBLISH WRITES, and over no others. A drag writes the
  pointer's scene position back into the simulation, so a node dragged outside the envelope is
  outside it in the simulation's units too -- while its scene coordinate stays under the pointer,
  because a held row is not published over. Measured, it set the radius every OTHER row was
  divided by: on a settled 40-node ForceAtlas2 at `scalingFactor` 100, with nothing stepping
  between the write and the publish, dragging one node to x 400 took the other 39 from a radius of
  99.993 to 25.626 -- the graph shrinking under a pointer that had not moved, and the camera
  refitting to the bigger box shrinking it again. It compounded, too: the write is divided by
  whatever scale the last publish left behind, so moving the same pointer back in to x 150 landed
  further out in the simulation than x 400 had and took them to 17.227. A held row is now left out
  of the measurement for the same reason it is left out of the write. When that leaves nothing to
  measure -- every row of the graph held -- the bridge keeps the map it had rather than resetting
  it to the identity, because the next `setNodePosition` still has to divide a scene coordinate
  back into units that did not move. The cost of the new rule is the other end of the same stick:
  the fewer free rows there are the less there is to fit, so a reader who pins almost everything
  has taken the size out of the layout's hands, and two free rows a hair apart are spread to the
  full radius exactly as a two-node graph would be.

  THE RADIUS IS ALSO EVERY SIZE CONTROL THE LAYOUT PUBLISHES, multiplied together, which is
  `publishedRadius` in `src/managers/LayoutManager.ts`. The refit fits the arrangement to that
  radius and leaves no other way for a reader to change how big the graph comes out, so a
  multiplier that reached only the simulation was divided straight back out: Spring published
  `scale` as a slider labelled "Scale" and a settled 30-node Spring measured a published radius of
  100.000 at `scale` 1 and 100.000 at `scale` 10. It measures 100.000 and 1000.000 now, because
  `scale` multiplies the radius -- which is what it meant when these layouts were one-shot engines,
  where the arrangement was fitted into a box of `scale` and then multiplied by `scalingFactor` --
  and spring-electrical's identically labelled control means the same thing. ForceAtlas2 publishes
  no `scale`, so its radius is its `scalingFactor` alone.

  WHAT A PIN COSTS, because it was tried the other way first. A held row is not published over --
  which is the element's existing rule, `LayoutEngine.writeNodePosition` refusing a layout-intent
  write to a pinned row for every one of the seventeen engines -- so it keeps its scene position
  while the arrangement around it is refitted, and the two can drift apart. Writing the row back
  into the simulation on every refit closes that gap and costs far more than it is worth: a
  simulation treats a written position as a disturbance and reheats, so ForceAtlas2 with one
  pinned node cleared its settle window every frame and ran the whole sixty-second budget on
  SwiftShader without once reporting itself at rest, taking the four cases after it down with it
  because the node was still pinned. A one-per-cent threshold on the write rescued spring and
  spring-electrical and left ForceAtlas2 still timing out, because the write also changes the
  arrangement, which changes the refit, which asks for another write. The write is gone. A pin is
  a scene-unit promise and it is kept; how far the arrangement moves under it is not part of that
  promise.
