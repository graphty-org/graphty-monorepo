## 2. What the app now contains, and why it is consuming rather than owning

The element's gate asserts, as its item 20, that "the app carries no acceleration code". That was
true before this phase and is deliberately no longer true; the element's record already says so.
This section is the reconciliation, because the two records must not disagree about the same tree.

The root `CLAUDE.md` line that governs it: "Reading a property the element exposes and rendering it
(a status chip, a settings control that writes element config) IS consuming the element and is
allowed. Deciding, probing, constructing or recovering is not."

What the app gained, and which side of that line each piece falls on:

| What | Where | Why it is consuming |
| --- | --- | --- |
| the element's optional peer, installed | `graphty/package.json` `dependencies` | a consumer installs the peers its dependency declares. The app imports the package nowhere; knip's `graphty` block says exactly that |
| one activation import | `src/main.tsx:9` | the element's documented whole integration. No guard, no try/catch, no `navigator.gpu` |
| the reader's policy, remembered | `shell/defaults/accelerationSettings.ts`, key `graphty.shell.acceleration.v1` | the element's own `acceleration` accessor says it never persists this and that remembering it is the host's storage. The stored word is validated with the element's `isAccelerationPolicy` and falls back to the element's `ACCELERATION_POLICY_DEFAULT`; no policy literal is written in the app |
| a three-way control | `shell/panel/SettingsOverlay.tsx`, `AccelerationSettingsPane` | a Mantine `SegmentedControl` whose options are `ACCELERATION_POLICIES.map(...)`. It draws the element's list; it does not hold one |
| the policy on the tag | `Graphty.tsx`, `canvas/CanvasRegion.tsx`, `types/jsx.d.ts` | writing an attribute the element publishes, typed `AccelerationPolicy` from the element. A JSX prop rather than an effect so it is in force before `connectedCallback` starts the probe |
| the status, held and drawn | `AppShell.tsx`: one `graphty-capabilities-change` listener on the shell frame, one read of `session.capabilities.acceleration` | the element's own document, kept as state and rendered. The read beside the listener is not a fallback and not a probe: the document is correct at any time, and a rejected probe can settle before a passive effect runs |
| the chip's words | `shell/statusbar/formatAcceleration.ts` and the `issues` slot | a pure function from the element's document to two strings and an ink. It asks the machine nothing and keeps no state |
| a lost device, reported | `AppShell.tsx`, `statusCompletion` | derived from `state === "error"`, shown in the app's one existing toast. The app does not catch the failure, does not retry and does not re-attach; the toast leaves when the element publishes its next transition |
| two stories | `src/stories/StatusBarAcceleration.stories.tsx` | the chip drawn from a fixed status. No element, no peer, no adapter |

What the app does NOT contain, checked rather than asserted: the five-string grep of item 9 prints
one line. There is no adapter request, no `registerAccelerator`, no `acceleratorRegistry`, no
device-loss retry, no threshold arithmetic and no CPU fallback anywhere in `graphty/src`.

The one judgement the app makes on its own is presentational and stays inside the line:
`formatAcceleration` returns `null` for `probing`, so nothing is drawn until the element has
finished looking. That is a decision about when to show a chip, not about whether to use a GPU.

## 5. Findings, owner decisions

- The `metricCost` accelerator constant of the integration plan's M7 cell was not built (DEP-M7-C):
  the cost model is the element's (`session.estimate`), and a per-metric GPU rate belongs in
  `graphty-element/src/session/cost/estimate.ts` once an algorithm runs on the GPU.
- The app sets no `acceleration-min-nodes`; a Settings control for the element's threshold is a
  product question for the owner: open.
- One sentence of Task M7-T7 was not written, because it lives in a package another session was
  editing while this record was made. `graphty-element/docs/guide/acceleration.md` should gain,
  under its API table: "`ACCELERATION_POLICIES`, `ACCELERATION_POLICY_DEFAULT` and
  `isAccelerationPolicy` are exported from `@graphty/graphty-element/session` for a host that draws
  a control." The three symbols exist and are exported; only the guide line is missing.
- An accessibility defect found and fixed in review, recorded because the shape of it will recur:
  the three-way control is a radiogroup, and Mantine's `Input.Wrapper` names its child by putting
  its own id on a `<label for>`, which only a control that reads the wrapper's context picks up.
  `SegmentedControl` does not, so the group was announced with no name -- three options and nothing
  saying what they decide. It now takes its name and its description from the wrapper's generated
  ids through `aria-labelledby` and `aria-describedby`, and the label is drawn as a `div` so no
  `for` dangles. Pinned by `SettingsOverlay.test.tsx` "names the acceleration control and carries
  its explanation".
- Element gaps outside this seam, left for the version 2 branch's clean-up, each one a comment in
  the app explaining why the element could not be used:
  - no JSX typing shipped by the element: `graphty/src/types/jsx.d.ts` declares
    `React.JSX.IntrinsicElements["graphty-element"]` itself, now with seven typed props, while
    `graphty-element/react.ts` is the reserved and empty entry for exactly that.
  - no neighbour verb on the element's data surface: `shell/analysis/graphShape.ts:23,188` says so
    and keeps `edgeEndpointId` / `edgeEndpoints` for the inspector's neighbour list.
  - the element's channel table is exported from no entry point: `src/utils/channelControls.ts:17-23`
    states that `CHANNEL_DESCRIPTORS` in `graphty-element/src/session/styles/channels.ts` already
    holds every fact its own table holds, "and it is exported from no entry point of the package",
    so the app's table "is a second copy of a table the element owns, and it can drift from what the
    element can actually draw with nothing able to catch it". This is the forbidden copy, with the
    bug report written in place, and it is the one worth filing first.
  - no `element.ready`: `Graphty.tsx` polls the session every 50 ms (`SESSION_POLL_MS`) for
    `style:changed`.
  - format sniffing in the app: `Graphty.tsx`'s `detectFormatFromFilename` and
    `detectFormatFromContent`. Beside them, `components/LoadDataModal.tsx:20` declares
    `type FormatType = "auto" | "json" | "graphml" | "gexf" | "csv" | "gml" | "dot" | "pajek"` --
    a hand copy of a list the element publishes as `session.catalog.formats()`
    (`graphty-element/src/catalog/types.ts:680`), which nothing in the app reads. A format the
    element adds or retires goes unnoticed here.
  - `shell/analysis/elementBridge.ts` duck-types the element because the app's handle type carries
    an index signature; `Graphty.tsx`'s `GraphtyElementType` re-declares ten element members by hand
    although the element exports `GraphtyElement`. This phase took its one new member (`session`)
    off the exported type through `Pick<>` and added none by hand.
  None of these was introduced or widened by this phase; all of them predate it and none touches
  acceleration.
- App gap outside this seam: a run that rejects (`session.runs.start` under `acceleration="required"`
  with no accelerator rejects with `E_NO_ACCELERATOR`) has no surface in the app;
  `runCommunityDetection` and `runDegreePass` are awaited with no catch. The chip's tooltip is what a
  reader sees; the rejection is not.
- M7-T1 Step 3: the bare import survived the bundle. See item 13 for what that does and does not
  prove, given that the element's `sideEffects` list already names `./webgpu.ts`.
